## Full decisions

### D-1: Sidebar adapter is a separate `cmuxSidebar` struct plus a `sidebarAwareHeader` wrapper, composed alongside `cmuxHeader`

- **Question:** Spec D1 commits two sidebar entries (status pill + progress bar) keyed off the orchestrator's authoritative knowledge of the current step and iteration counter. Where does that mirroring code live — as a method-set extension on the existing `cmuxHeader`, a decorator that wraps `cmuxHeader`, or a separate struct composed alongside `cmuxHeader` with a thin wrapper that observes `RunHeader` calls?
- **Decision:** Phase 4 ships **two new types** in `src/cmd/pr9k/`. (a) A `cmuxSidebar` struct holding a `cmuxctl.CmuxClient`, a `cmuxctl.Workspace` handle, a `*logger.Logger`, and two caches (`lastStepName` for the error-mode marker; `progressPushed` so `ClearAll` knows whether the bar was ever set). Its method set: `PushStep(ctx, name) error`, `PushProgress(ctx, iter, maxIter) error`, `EnterErrorMode(ctx) error`, `ClearProgress(ctx) error`, `ClearAll(ctx) error`, plus an internal `pushStatus(ctx, value)`. (b) A `sidebarAwareHeader` type that wraps `*cmuxHeader`, satisfies `workflow.RunHeader`, and on every relevant call delegates to `cmuxHeader` and then issues the matching sidebar push. The two types live in a new file `src/cmd/pr9k/cmux_sidebar.go` so the existing `cmux_workflow.go` stays focused. **No method is added to the `workflow.RunHeader` interface**; the wrapper observes the existing call sequence.
- **Rationale:** SRP — `cmuxHeader`'s job is to translate orchestrator state into `StateHeader` messages on the interaction channel (Phase 2/3 transport, in-process IPC, ack-tracking semantics). The sidebar surface has a different transport (cmux v2 JSON-RPC over Unix socket via `cmuxctl.CmuxClient`), different error semantics (non-timeout errors are logged-and-continue per spec D5; timeouts remain fatal per parent D15), and different lifecycle events (iteration→finalize boundary that header processing does not surface as a single event). Keeping the two concerns separate avoids overloading `cmuxHeader` with a second transport. LSP — adding a new method to `RunHeader` (e.g., `EnterFinalize()`) would force every implementation (including `StatusHeader` in standard mode) to provide a do-nothing method; observing the existing call sequence via a thin wrapper is the LSP-preserving alternative. The wrapper pattern matches the existing adapter idiom in `src/cmd/pr9k/` (`cmuxHeader`, `newKeyHandlerAdapter`).
- **Evidence:** software-architect S1 + S3 (claim ledger entries C1, C3 — see [implementation-iteration-history.md](implementation-iteration-history.md) R1). Verified code: `src/cmd/pr9k/cmux_workflow.go` defines `cmuxHeader` and its five-method `RunHeader` implementation; `src/internal/workflow/run.go` declares the `RunHeader` interface — there is one production implementation per mode (`StatusHeader` in standard mode, `cmuxHeader` in cmux mode), so adding a method would touch both. `docs/coding-standards/concurrency.md` (snapshot-then-unlock pattern for cached state). `docs/coding-standards/api-design.md` (adapter types, compile-time interface assertions).
- **Rejected alternatives:**
  - **Extend `cmuxHeader` with the sidebar transport methods directly** — rejected (SRP); `cmuxHeader` would carry two transports, two error policies, and two lifecycle event sets in one struct; testing and future evolution become tangled.
  - **Decorate `cmuxHeader` (wrap and replace it as the orchestrator's `RunHeader`)** — partially what `sidebarAwareHeader` does; the rejected variant is a *replacement* decorator that owns both surfaces internally; the chosen design composes — `sidebarAwareHeader` delegates to `*cmuxHeader` for header concerns and to `*cmuxSidebar` for sidebar concerns, so each cooperator stays single-purpose and independently testable.
  - **Add a new method to `RunHeader` (e.g., `BeginFinalize()`) so the orchestrator can signal the iteration→finalize transition directly** — rejected (LSP); `StatusHeader` in standard mode would gain a do-nothing implementation just to satisfy the interface, and the existing `RenderFinalizeLine` call sequence already carries the signal observably.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** Reopen if a third sidebar consumer appears (Rule of Three) — at that point the four-method extension on `CmuxClient` (D-3) plus the adapter wrapper pattern should be re-evaluated against a dedicated `CmuxSidebar` sub-interface.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-2, D-3, D-5, D-6, D-7, D-13, D-14
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, Runtime Behavior), Decomposition and Sequencing (W2, W3)

### D-2: Error-mode marker fires by augmenting the existing `OnModeChange` closure in place, reading from a cached step name

- **Question:** Spec D13 commits the error-mode marker: when the orchestrator enters `ModeError`, the status pill's value gains `" — awaiting input"`. The Phase 3 wiring (`docs/plans/cmux-rebuild/phase-3-interactive-error-recovery/feature-implementation-plan.md` D-6) already registers an `OnModeChange` closure that pushes `StateFooter`. How does Phase 4 add the sidebar push without breaking Phase 3's behavior, given that `KeyHandler.SetOnModeChange` is a single-field assignment and a second call overwrites the first?
- **Decision:** The existing `OnModeChange` closure in `runCmuxWorkflowAdapted` is **augmented in place** — it becomes a single closure that (a) calls `ch.SendStateFooter(...)` (Phase 3 behavior, unchanged) AND (b) calls `sidebar.EnterErrorMode(ctx)` when `mode == ui.ModeError`. The closure reads the latest step name from a `lastStepName` cache on `cmuxSidebar`, populated by every `PushStep` call on the wrapper. No change is made to the `OnModeChange` callback signature; no second hook is registered.
- **Rationale:** junior-developer F3 confirmed `KeyHandler.SetOnModeChange` writes a single field (`src/internal/ui/ui.go:86`, `:131-135`); a second call would silently overwrite Phase 3's footer push. The only safe extension is to compose both effects into one closure at the registration site. The cached step name solves a second problem: `OnModeChange`'s signature is `(Mode, shortcutLine string)` with no step name carried, but the marker must apply to the failing step's name — caching on every `PushStep` is sufficient because the orchestrator pushes the step name on `SetStepState(idx, StepActive)` immediately before the step runs, and `ModeError` is entered only after a step has been pushed. ISP — no signature change required.
- **Evidence:** software-architect S2 (claim ledger C2). junior-developer F3 (claim ledger C9). Verified code: `src/internal/ui/ui.go:86` (`onModeChange func(Mode, string)`); `src/internal/ui/ui.go:131-135` (`SetOnModeChange` writes the single field). Phase 3 implementation plan [D-6](../../phase-3-interactive-error-recovery/artifacts/implementation-decision-log.md#d-6-establish-setonmodechange--the-key-adapter-goroutine-before-workflowrun-starts-drain-the-footer-keystroke-goroutine-on-context-cancel-via-waitgroup) for the existing closure semantics (synchronous, fires outside `h.mu`).
- **Rejected alternatives:**
  - **Add a second hook field to `KeyHandler` (e.g., `SetOnModeChangeSidebar`)** — rejected; doubles the `KeyHandler` surface for one piece of functionality, leaks sidebar-mirroring concern into a UI primitive that has no other coupling to cmux mode.
  - **Change `OnModeChange`'s signature to carry the active step name** — rejected (ISP); the signature is consumed by standard mode (Phase 3 footer push) which has no need for the step name; broadening the signature for a single cmux-mode consumer is the wrong scope.
  - **Detect error mode by polling some shared state from `cmuxSidebar`** — rejected; race-prone and adds complexity where the existing synchronous hook already fires exactly when needed.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** Reopen if Phase 5 needs a *third* effect on mode change (e.g., a notification fire) that does not compose cleanly into the same closure, at which point a `KeyHandler.AddOnModeChange` slice may become warranted.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-7
- **Referenced in plan:** Implementation Approach (Architecture and Integration Points, Runtime Behavior), Decomposition and Sequencing (W3), RAID Log (Risks)

### D-3: `CmuxClient` gains four new methods directly; no `CmuxSidebar` sub-interface

- **Question:** The sidebar adapter needs to call cmux's `set-status` / `clear-status` / `set-progress` / `clear-progress` RPCs. Are the new method wrappers added directly to the existing `CmuxClient` interface (`src/internal/cmuxctl/client.go`), or partitioned behind a new `CmuxSidebar` sub-interface that `CmuxClient` embeds?
- **Decision:** Four new methods are added directly to `CmuxClient`: `WorkspaceSetStatus(ctx context.Context, ws Workspace, key, value string) error`, `WorkspaceClearStatus(ctx context.Context, ws Workspace, key string) error`, `WorkspaceSetProgress(ctx context.Context, ws Workspace, fraction float64, label string) error`, `WorkspaceClearProgress(ctx context.Context, ws Workspace) error`. No `opts` parameter for icon/color/priority (spec D12 defers them). No `CmuxSidebar` sub-interface.
- **Rationale:** ISP applies to clients of an interface, not authors. `CmuxClient` today is the single contract for everything pr9k asks cmux to do — workspace lifecycle, surface management, and (with Phase 4) sidebar updates. The four sidebar methods have exactly one production caller (`cmuxSidebar`) and one test caller (the W2 unit tests), Rule of Three is not met, and a single-implementation interface is the YAGNI-rule named anti-pattern. The version-pin capability check (D-4) is the operational mechanism that gates whether the methods are callable at runtime — the interface partition adds no safety. Omitting `opts` matches spec D12 ("pr9k does not override the optional sidebar status-entry parameters") — the larger version (an `opts` struct) fails the YAGNI evidence test (no operator-described need).
- **Evidence:** software-architect S4 (claim ledger C4). Verified code: `src/internal/cmuxctl/client.go` declares `CmuxClient` with 8 RPC methods today and a single `RealClient` implementation; `FakeClient` is the one test double (claim ledger C14, decision D-12). YAGNI rule doc `plugins/han/references/yagni-rule.md` (single-implementation-interface anti-pattern; symmetry/completeness is not evidence). Spec [D12](../decision-log.md#trivial-decisions) (pr9k does not override optional pill parameters).
- **Rejected alternatives:**
  - **Introduce a `CmuxSidebar` sub-interface embedded into `CmuxClient`** — rejected (single-implementation-interface anti-pattern); one production caller, one test double, no second concrete use.
  - **Add an `opts` parameter for icon/color/priority on `WorkspaceSetStatus`** — rejected; spec D12 defers these parameters; carrying them in the wire wrapper now would invite premature use and fail the YAGNI evidence test (no operator-described need for any default).
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** Reopen if a third concrete consumer of sidebar-specific RPCs appears (Rule of Three) or if cmux exposes a new sidebar method whose signature does not fit `CmuxClient`'s shape.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-4, D-6, D-12
- **Referenced in plan:** Implementation Approach (External Interfaces), Decomposition and Sequencing (W1, W2), Testing Strategy

### D-4: Capability check stays identify-only; the cmux version pin moves 0.64.6 → 0.64.7

- **Question:** Spec D15 says "the Phase 1 capability check is extended to cover Phase 4's sidebar methods." Discovery notes confirmed the current preflight is identify-only (`src/internal/cmuxctl/preflight.go`) — there is no per-method `system.capabilities` enumeration to extend. Does Phase 4 add per-method probing, or move the cmux version pin and document the change in scope?
- **Decision:** Preflight remains identify-only. The minimum cmux version pin is bumped from 0.64.6 to 0.64.7 in three locations atomically: `src/internal/cmuxctl/client.go` package docstring, `src/internal/cmuxctl/preflight.go:65` (the unsupported-version error string), and `docs/how-to/setting-up-cmux.md:5` (the Tested-against line). The implementation surfaces the actual scope honestly in documentation: "the capability check verifies cmux v2 is reachable; per-method capability probing remains deferred." Per-method `system.capabilities` enumeration is deferred to `## Deferred (YAGNI)` in the plan.
- **Rationale:** Per-method enumeration over the four new sidebar methods plus the eight existing methods is a symmetry/completeness anti-pattern (YAGNI rule doc): Phases 1–3 shipped without it, the version-pin alternative satisfies the same evidenced need (detect a cmux that does not expose the methods pr9k calls) with strictly less surface, and the simpler-version test of the YAGNI rule prefers the version pin. The honest documentation of the actual capability-check scope is what closes the "literal reading of parent D18 / spec D15 says one thing; code does another" gap — without it the next reader inherits a false invariant.
- **Evidence:** software-architect S5 (claim ledger C5). junior-developer F4, F5 (version-pin locations, capability-check assumption gap). Verified code: `src/internal/cmuxctl/preflight.go:65` (current unsupported-version error names `0.64.6`); `src/internal/cmuxctl/client.go` package docstring (names `0.64.6`); `docs/how-to/setting-up-cmux.md:5` (Tested-against line names `v0.64.6`). YAGNI rule doc `plugins/han/references/yagni-rule.md` (simpler-version test; named anti-patterns). Discovery notes "Capability check vs cmux version (gap)" section.
- **Rejected alternatives:**
  - **Add per-method `system.capabilities` enumeration in preflight** — rejected (simpler-version test); the version pin satisfies the same evidence at a fraction of the implementation surface; symmetry/completeness against parent D18's literal wording is not evidence per the YAGNI rule. Deferred to `## Deferred (YAGNI)` with reopen trigger "a cmux minor release removes or renames a method pr9k calls and a runtime failure surfaces that the version pin did not prevent."
  - **Leave the pin at 0.64.6 and rely on runtime failure** — rejected; the sidebar surface was confirmed against 0.64.7 per spec D1 evidence; pinning a version where the surface is not confirmed risks the operator running pr9k against a cmux that silently misses the methods, surfacing as the "log-and-continue" failure (spec D5) and a sidebar that just doesn't update.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** A cmux minor release removes or renames a method pr9k calls and a runtime failure surfaces that the version pin did not prevent — at that point the deferred per-method enumeration is reopened.

### D-5: `cmuxctl.CmuxClient` and `cmuxctl.Workspace` are threaded through the orchestrator composition root from `cmuxOrchestratorHooks` → `runCmuxOrchestratorWith` → `runCmuxWorkflowAdapted`

- **Question:** `cmuxSidebar` (D-1) needs a `CmuxClient` and a `Workspace` handle to issue sidebar RPCs. Today `cmuxOrchestratorHooks` constructs a `Run` closure that discards the workspace handle (`func(rctx, _ Workspace)` at `src/cmd/pr9k/cmux_pane.go:46`), and `runCmuxWorkflowAdapted` (`src/cmd/pr9k/cmux_workflow.go:124`) takes neither parameter. What threading carries the client and workspace to the new adapter?
- **Decision:** The orchestrator composition root is threaded explicitly. (a) `cmuxOrchestratorHooks` captures the production `*cmuxctl.RealClient` from the `main.go --cmux` branch alongside `ctx` and `projectDir`; the captured client and the workspace handle from the `Run` closure (no longer discarded) are both passed forward. (b) `runCmuxOrchestratorWith` gains two parameters — `client cmuxctl.CmuxClient` and `ws cmuxctl.Workspace`. (c) `runCmuxWorkflowAdapted` gains the same two parameters. Every call site (including tests in `src/cmd/pr9k/`) updates. The interface (`cmuxctl.CmuxClient`) is passed, not the concrete `*RealClient` — DIP.
- **Rationale:** This is the structural prerequisite that unblocks D-1, D-6, D-7. Without it the sidebar adapter has nothing to call. The Run-closure underscore (`_ Workspace`) at `cmux_pane.go:46` is the literal sign of the gap — the workspace handle is already produced by the cmux RPC layer and was discarded because nothing downstream used it; Phase 4 is the first phase that needs it. Threading the *interface* `CmuxClient` (not `*RealClient`) keeps tests honest — the existing `FakeClient` already implements `CmuxClient` and will implement the four new methods after D-12.
- **Evidence:** software-architect S6 (claim ledger C6). junior-developer F1, F2, F11 (workspace handle discarded, client not threaded, test-file cascade). Verified code: `src/cmd/pr9k/cmux_pane.go:46` (`func(rctx, _ Workspace)` — the underscore is the gap); `src/cmd/pr9k/cmux_workflow.go:124` (current `runCmuxWorkflowAdapted` signature with no client or workspace parameter). `docs/coding-standards/api-design.md` (DIP — depend on the interface).
- **Rejected alternatives:**
  - **Construct a second `CmuxClient` inside `runCmuxWorkflowAdapted` from environment** — rejected; two clients on the same socket would race for the single-goroutine sequential queue inside `RealClient`; also wasteful — the orchestrator already owns the production client.
  - **Stash the client in a package-level variable from `main.go`** — rejected; global state, untestable, breaks the `cmuxctl` package's no-singleton stance.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** Reopen if Phase 5 or Phase 6 needs a third pane-side process to hold the client — at that point the composition root should be re-evaluated against a shared-state pattern.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-1, D-6, D-7
- **Referenced in plan:** Implementation Approach (Architecture and Integration Points), Decomposition and Sequencing (W3), RAID Log (Issues)

### D-6: Cleanup ordering — `sidebar.ClearAll(ctx)` runs in `runCmuxWorkflowAdapted` immediately after `workflow.Run` returns, using the parent context

- **Question:** Spec D6 commits to clearing both sidebar entries on every graceful run-end path. Where in `runCmuxWorkflowAdapted`'s teardown does the clear run, and which context does it use (the parent `ctx`, or the post-cancel `keyCtx` used to stop the key-adapter goroutine)?
- **Decision:** `sidebar.ClearAll(ctx)` is called from `runCmuxWorkflowAdapted` immediately after `workflow.Run` returns and `keyHandler.SetMode(ui.ModeDone)`, **before** `keyCancel()` and `wg.Wait()`, and before the outer `runCmuxOrchestratorWith` broadcasts `WorkspaceDone`. The call uses the parent `ctx`, not `keyCtx`, so the per-call timeout (parent D15) operates against a non-cancelled context.
- **Rationale:** Clearing before `keyCancel()` keeps the sidebar-clear's `ctx` derivation alive for the duration of the four RPC calls (two clears) — the parent D15 per-call timeout applies, and a cancelled `keyCtx` would cause the call to short-circuit through context cancellation rather than reach cmux. Clearing before `WorkspaceDone` is the user-visible invariant — when the operator's other workspace sees the pr9k workspace transition to "done," the sidebar entries are already gone. `concurrency.md`'s snapshot-then-unlock pattern is satisfied by `cmuxSidebar` caching `progressPushed` as a bool — `ClearAll` reads it without holding a long lock.
- **Evidence:** software-architect S7 (claim ledger C7). Verified code: `src/cmd/pr9k/cmux_workflow.go` existing teardown sequence (`workflow.Run` returns → `keyHandler.SetMode(ui.ModeDone)` → `keyCancel()` → `wg.Wait()`). `docs/coding-standards/concurrency.md` (snapshot-then-unlock). Spec [D6](../decision-log.md#d6-sidebar-entries-are-cleared-on-every-graceful-run-end-path), [parent D15](../../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal).
- **Rejected alternatives:**
  - **Clear after `keyCancel()` and `wg.Wait()`, before `WorkspaceDone`** — rejected; `keyCtx` would be cancelled at that point, and if `ClearAll` derives from `keyCtx` the RPC would not reach cmux; using parent `ctx` works but the earlier placement is simpler (no second context to reason about).
  - **Clear after `WorkspaceDone` broadcasts** — rejected; user-visible inversion (workspace marked done before its sidebar state clears) and races against the outer `runCmuxOrchestratorWith` teardown.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** Reopen if Phase 6's non-graceful-path work changes the teardown sequence (the same sidebar-clear is what Phase 6 calls from the abort path per spec D17, but its ordering may differ).
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-7
- **Referenced in plan:** Implementation Approach (Runtime Behavior), Decomposition and Sequencing (W3)

### D-7: `cmuxSidebar` construction is hoisted to `runCmuxOrchestratorWith`; a `defer sidebar.ClearAll(context.Background())` runs on every exit path

- **Question:** D-6 commits to a graceful-path clear inside `runCmuxWorkflowAdapted`. What protects the sidebar from being left stale on paths that bypass `workflow.Run`'s normal return — a panic in the inner function, an early-return on adapter construction failure, or any other path the Phase 6 abort work will introduce later? Where is `cmuxSidebar` constructed, and what defer-discipline applies?
- **Decision:** `cmuxSidebar` is constructed in `runCmuxOrchestratorWith` immediately after the cmux client and workspace handle are captured (D-5), **before** `runCmuxWorkflowAdapted` is called. A `defer sidebar.ClearAll(context.Background())` is registered at construction time. `runCmuxWorkflowAdapted` receives the `*cmuxSidebar` as a parameter and is responsible for the graceful-path clear inside its teardown (D-6); the outer `defer` is the safety net for non-graceful paths. `context.Background()` is used in the defer because the parent `ctx` may be cancelled by the time the defer fires.
- **Rationale:** OCP — Phase 6's abort-path work calls the same `ClearAll` without modifying `runCmuxWorkflowAdapted`'s internals; the hoisted construction is the extension point. The defer is a best-effort safety net; the graceful-path clear inside `runCmuxWorkflowAdapted` is the spec D6 commitment. Two clears in sequence are safe because the second runs against already-cleared cmux state, which is a no-op per cmux's latest-wins-per-key semantics (spec T1) — non-timeout errors are logged-and-continue per spec D5.
