Load-bearing mechanics that the [Phase 4 feature specification](../feature-specification.md) relies on. **Scope note:** these notes complement, not replace, the parent feature's technical notes. In particular, [parent T1](../../artifacts/feature-technical-notes.md#t1-cmux-programmatic-interface-shape) names "sidebar status / progress / log" as one of six cmux API categories; this Phase 4 file goes one level deeper into the shape of the status and progress surfaces specifically, because Phase 4 is the first phase that calls them.

## T1: cmux sidebar surface shape

- **Context:** the Phase 4 spec commits to (a) addressing the step status entry by a stable, pr9k-prefixed key so it coexists with other tools' pills without collision ([D2](decision-log.md#d2-pr9k-owns-its-sidebar-entries-under-a-stable-pr9k-prefixed-key)); (b) populating cmux's progress surface as a fraction plus a `"N / M"` label ([D3](decision-log.md#d3-progress-entry-uses-cmuxs-fraction-plus-label-progress-surface)); (c) suppressing the progress surface entirely when the iteration total is unknown rather than publishing a misleading fraction ([D4](decision-log.md#d4-unbounded-iteration-count-suppresses-the-progress-entry-the-status-entry-continues-unchanged)); and (d) clearing entries on run end by re-addressing them via the same key ([D6](decision-log.md#d6-sidebar-entries-are-cleared-on-every-run-end-path)). All four commitments are dictated by the specific shape of cmux's sidebar surfaces in v0.64.7 — not by a pr9k policy.
- **Technical detail:** cmux's sidebar exposes two distinct workspace-scoped surfaces relevant to Phase 4.
  - **Status entries** are keyed pills attached to a workspace. Each entry is identified by a caller-supplied string key, and the caller may set, update, or remove its own entries by re-addressing them with the same key. Multiple tools can attach pills to the same workspace — cmux's documentation explicitly mentions `claude_code`, `codex`, `build`, and `deploy` as example keys other tools use — and a workspace's row in the sidebar shows the union of all tools' pills. There is no caller-isolation or namespacing in cmux itself; isolation is by convention via key prefixes. Optional parameters per pill include an icon name, a color hex string, and a sort priority (higher appears first). The pill's value is a free-form short string. cmux's behavior on a `set` of an existing key is "latest wins"; there is no append model on this surface.
  - **Progress** is a single workspace-scoped progress bar. Its value is a 0.0–1.0 fraction; it accepts an optional free-form label that renders next to the bar. There is exactly one progress bar per workspace — the surface is not keyed and not append-only. Clearing it removes the bar from the workspace's sidebar row entirely. There is no built-in "indeterminate" mode for this surface; the absence of a progress call is the only honest representation of "no known total".
  - Both surfaces are pushed via cmux v2's JSON-RPC socket (or the equivalent `cmux` CLI subcommands that resolve to the same RPCs) and target a workspace by its cmux handle ([parent D-R2](../../artifacts/decision-log.md#d-r2-cmux-v2-protocol-is-the-contract-of-record)). They are subject to the same socket transport, per-call timeout, and error envelope as every other cmux v2 method ([parent T1](../../artifacts/feature-technical-notes.md#t1-cmux-programmatic-interface-shape), [parent D15](../../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal)).
