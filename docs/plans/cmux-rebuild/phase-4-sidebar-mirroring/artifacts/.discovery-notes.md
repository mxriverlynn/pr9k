## Touch Points (code the implementation will extend)

### `src/internal/cmuxctl/` — cmux v2 RPC surface

- **`client.go`** — `CmuxClient` interface. Today has 8 RPC methods (SystemIdentify, WorkspaceCurrent, WorkspaceList, WorkspaceCreate, WorkspaceClose, WorkspaceSelect, SurfaceSplit, SurfaceList). Phase 4 adds workspace-scoped sidebar status + progress mutators. Note: cmux v2 method names are wire-level identifiers; the names this plan settles on must match cmux 0.64.7's actual `set-status` / `set-progress` / `clear-status` / `clear-progress` RPCs.
- **`real.go`** — `RealClient` is a single-goroutine sequential queue (per-call timeout, JSON-RPC line protocol). Adding methods is structurally trivial: a thin `do(ctx, method, params)` call per RPC and a typed wrapper.
- **`fake.go`** — `FakeClient` test double. Every existing method has a hand-written fake; Phase 4 adds its four new RPCs here too.
- **`preflight.go`** — Phase 1's capability check. **Important context:** the current implementation is *identify-only* — a successful `SystemIdentify` with a non-empty `socket_path` is treated as full capability proof. There is no per-method enumeration. Parent D18 says the check confirms "every method pr9k will call" — the current code does NOT match that literal commitment for any method. Phase 4 spec D15 says the capability check is "extended to cover Phase 4's sidebar methods", but the existing check has no method-list to extend. This is an open question the team must resolve (see Gaps below).
- **`runphase1.go`** — Phase 1 lifecycle (workspace create → split panes → orchestrate). Owns the workspace handle the sidebar update RPCs target.

### `src/cmd/pr9k/cmux_workflow.go` — orchestrator-side RunHeader adapter

- **`cmuxHeader` struct** — `workflow.RunHeader` adapter that translates orchestrator state into `StateHeader` messages on the interaction channel. **Five methods:** `SetPhaseSteps`, `SetStepState(idx, state)`, `RenderInitializeLine(stepNum, stepCount, stepName)`, `RenderIterationLine(iter, maxIter, issueID)`, `RenderFinalizeLine(stepNum, stepCount, stepName)`.
- **`runCmuxWorkflowAdapted`** — composes all the cmux-mode adapters: `runner.SetSender` for log fan-out, `cmuxHeader` for header, `KeyHandler.SetOnModeChange` for footer mode pushes, and a key-adapter goroutine for intent forwarding. Phase 4's sidebar adapter is built in this same composition path.
- **`keyHandler.SetOnModeChange(fn func(Mode, string))`** — Phase 3's extension point. Fires synchronously on every `SetMode` / `ForceQuit` outside `h.mu` with the new mode + shortcut line. Phase 4 can chain a second hook here for the error-mode marker push.

### `src/internal/ui/orchestrate.go` — error-mode entry/exit

- **`runStepWithErrorHandling`** — the function that calls `header.SetStepState(idx, StepFailed)` then `h.SetMode(ModeError)` then waits on `h.Actions` then `h.SetMode(ModeNormal)`. The KeyHandler's `OnModeChange` fires twice in this excursion — once on `ModeError` entry, once on `ModeNormal` exit. **Important:** this file is shared between standard mode and cmux mode; Phase 4 should not couple it to sidebar concerns.

### `src/internal/workflow/run.go` — RunHeader contract + iteration→finalize transition

- `RunHeader` interface — five methods listed above; declared in `internal/workflow` so the package the cmux adapter implements does not import `internal/ui`.
- The iteration → finalize transition happens around line 637 (`header.SetPhaseSteps(finalizeNames)` is the first finalize-phase call). The first `RenderFinalizeLine` follows immediately.
- The iteration counter advances at `RenderIterationLine(iter, cfg.Iterations, "")` (line 494 entering iter, line 609 after issue ID resolution).

### Header / step-name caching for the sidebar

- For the iteration phase, `SetStepState(idx, StepActive)` is called per step (orchestrate.go:92) but does NOT carry the step name — the name comes from the prior `SetPhaseSteps(names []string)` (run.go:499). The sidebar mirror needs to cache `names` and key into it on `SetStepState` to know what step name to push. The initialize / finalize phases pass step name directly via `RenderInitializeLine` / `RenderFinalizeLine`.
- The latest step name pushed is also what the error-mode marker should suffix `— awaiting input` onto.

### Capability check vs cmux version (gap)

- **Parent D18** commits to "every method pr9k will call" — per-method enumeration.
- **Current code** does identify-only.
- **Phase 4 spec D15** assumes the capability check enumerates methods.

## Gaps Explicitly Searched For And Not Found

- **No per-method capability check exists today.** Searched `src/internal/cmuxctl/preflight.go` and `system.capabilities` / similar identifiers — `system.capabilities` is mentioned in `docs/plans/cmux-rebuild/investigation.md` Round 1 (per parent D18 evidence) but no Go code calls it. The current production preflight is identify-only.
- **No existing sidebar / pill / progress code anywhere in pr9k.** Phase 4 is the first phase that touches these cmux surfaces.
- **No existing "current step name" cache outside the standard-mode `StatusHeader`.** The cmux-mode `cmuxHeader` stores the step *names list* (via `SetPhaseSteps`) and per-index state (`states[]`) but does not separately cache "the latest active step's name string". The sidebar mirror will need to derive or cache that itself.
- **No existing `EnterErrorMode(stepName)` / `ExitErrorMode()` API.** The orchestrator transitions via `KeyHandler.SetMode(ModeError)` / `SetMode(ModeNormal)`; Phase 3's `OnModeChange` callback signature is `(Mode, shortcutLine string)` — no step name carried.
- **No existing `EnterFinalize()` signal on the RunHeader interface.** The transition is detectable from the sequence of calls (`SetPhaseSteps(finalizeNames)` is the first finalize-phase call, immediately followed by `RenderFinalizeLine`).
