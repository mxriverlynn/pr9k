# Feature Specification: Phase 1 — Cmux Mode Launch and Workspace Lifecycle

Phase 1 of the [pr9k cmux mode build outline](../build-phase-outline.md). Adds an opt-in launch mode in which pr9k stands up a recognizably-named cmux workspace with a four-pane scaffold, holds it open while the operator inspects it, and tears it down cleanly with their prior workspace restored — all without running any workflow content inside.

This phase is the foundation for every later phase. The four panes Phase 1 stands up are the renderers Phase 2 brings to life with real workflow content. The workspace lifecycle Phase 1 exercises is what Phase 6 hardens against failure. The workspace naming pattern Phase 1 commits to is what Phase 7's orphan advisory recognizes.

## Outcome

When the operator launches pr9k with cmux mode requested, against a target repository, from inside a cmux session, one of two things happens — either pr9k aborts with a precondition error that names the specific failure, or a fresh cmux workspace appears with a four-pane scaffold (a small header pane on top, a tall log pane in the middle, a small footer pane on the bottom, and a hidden orchestrator pane). The three visible panes each display a static placeholder label that identifies the pane's role and signals it is not yet running real content ([D3](artifacts/decision-log.md#d3-visible-placeholders-identify-pane-role-and-signal-placeholder-state)). The workspace remains open as long as the operator wants to look at it ([D4](artifacts/decision-log.md#d4-launching-process-blocks-until-workspace-dismissed)); switching focus to another cmux workspace and back leaves the pr9k workspace intact. When the operator dismisses the pr9k workspace using cmux's own workspace-close controls, focus returns to the cmux workspace they were in before the launch ([parent D22](../artifacts/decision-log.md#d22-prior-workspace-is-captured-and-restored)), and the terminal session that launched pr9k returns to a free prompt.

Phase 1 does not run any pr9k workflow content. The orchestrator pane hosts a placeholder process whose only job is to keep the pane alive until the workspace is dismissed ([D1](artifacts/decision-log.md#d1-orchestrator-pane-runs-a-placeholder-during-phase-1)). The standard pr9k log artifacts under `.pr9k/logs/` are not produced during a Phase 1 launch because no workflow runs. The four-pane scaffold, the preflight checks, the workspace naming, and the dismissal handshake are the entirety of what Phase 1 delivers.

## Actors and Triggers

- **Primary actor:** the human operator running pr9k against a target repository, from a shell inside a cmux session.
- **Trigger:** the operator launches pr9k with the cmux launch flag on the existing run invocation ([parent D25](../artifacts/decision-log.md#d25-launch-surface-is-the-cmux-flag)).
- **Preconditions:**
  - cmux is installed on the host and its programmatic interface is reachable ([parent T1](../artifacts/feature-technical-notes.md#t1-cmux-programmatic-interface-shape)).
  - The pr9k invocation is itself running inside a cmux session, so it is permitted to connect to cmux's interface ([parent T2](../artifacts/feature-technical-notes.md#t2-cmux-access-model)).
  - cmux is reachable, responsive, and exposes the capabilities pr9k needs ([parent D18](../artifacts/decision-log.md#d18-startup-capability-check)).
  - All existing preconditions for a pr9k run still apply (target repository present, `config.json` resolvable, etc.) — Phase 1 does not change the standard preflight surface; it adds cmux-specific checks on top of it.

## Primary Flow

1. The operator launches pr9k in cmux mode, pointing at a target repository, from a shell inside a cmux pane.
2. pr9k records which cmux workspace the operator was in before launch so that workspace can be returned to focus on dismissal ([parent D22](../artifacts/decision-log.md#d22-prior-workspace-is-captured-and-restored)). If the launching cmux session contains no workspace other than the launching pane (no prior workspace to capture), pr9k records that state and skips the explicit focus-restore step on dismissal, letting cmux apply its default focus behavior ([D10](artifacts/decision-log.md#d10-no-prior-workspace-state-handled-gracefully)).
3. pr9k probes cmux: confirms it is reachable, that pr9k is permitted to drive it, and that cmux exposes every capability pr9k will call in this phase ([parent D18](../artifacts/decision-log.md#d18-startup-capability-check), [parent T1](../artifacts/feature-technical-notes.md#t1-cmux-programmatic-interface-shape)). If any check fails, pr9k aborts before creating any workspace, prints a precondition error to the launching terminal that names the specific failure condition (see [Edge Cases](#edge-cases-and-failure-modes)), and exits with a non-zero status ([parent D3](../artifacts/decision-log.md#d3-cmux-availability-is-a-hard-precondition-not-a-fallback)).
4. *(Phase 1 does not include an orphan-workspace startup advisory; that capability ships in Phase 7 of the build outline. The parent feature spec's Primary Flow step that prints an orphan advisory is therefore absent from Phase 1's flow.)*
5. pr9k asks cmux to create a fresh workspace whose name follows the `pr9k-<sanitized-repo-basename>-<nanosecond-timestamp>` pattern, ensuring two concurrent or rapid launches do not collide and the operator can later distinguish workspaces in cmux's workspace list ([parent D29](../artifacts/decision-log.md#d29-workspace-name-pattern)). The repo basename is sanitized before inclusion so it contains only characters cmux accepts in workspace names ([D11](artifacts/decision-log.md#d11-repo-basename-sanitized-before-use-in-workspace-name)). If cmux nonetheless rejects the resulting name as a duplicate (the same-nanosecond collision that the timestamp precision reduces but does not strictly eliminate), pr9k regenerates the timestamp once and retries; a second collision is treated as a partial-setup failure ([D12](artifacts/decision-log.md#d12-workspace-name-collision-retried-once-then-fails)). pr9k prints the new workspace name to the launching terminal as a one-line confirmation so the operator has a paper trail ([D2](artifacts/decision-log.md#d2-launching-terminal-prints-the-workspace-name)).
6. pr9k asks cmux to lay out four panes in the new workspace — the orchestrator pane (kept hidden), the header pane on top, the log pane in the middle, the footer pane at the bottom ([parent D4](../artifacts/decision-log.md#d4-three-pane-vertical-layout), [parent D13](../artifacts/decision-log.md#d13-orchestrator-runs-in-a-hidden-cmux-pane)) — and to spawn one placeholder process inside each pane ([parent T3](../artifacts/feature-technical-notes.md#t3-cmux-surfaces-are-processes-not-paintable-canvases)).
7. Each visible placeholder process displays a static label identifying its pane role (e.g., "header", "log", "footer") and a clear signal that the pane is a Phase 1 placeholder, not real content ([D3](artifacts/decision-log.md#d3-visible-placeholders-identify-pane-role-and-signal-placeholder-state)). The orchestrator pane's placeholder produces no visible output by default; it exists to keep the pane alive and to provide a diagnostic surface if the operator reveals it via cmux's pane-show controls ([D1](artifacts/decision-log.md#d1-orchestrator-pane-runs-a-placeholder-during-phase-1)).
8. The launching pr9k process waits for either (a) the pr9k workspace disappearing from cmux's workspace list, or (b) any of the four placeholder processes exiting — whichever happens first ([D9](artifacts/decision-log.md#d9-dismissal-observation-contract), [D4](artifacts/decision-log.md#d4-launching-process-blocks-until-workspace-dismissed)). Either observation is treated as workspace dismissal. The launching terminal session remains attached to pr9k for the duration; the operator does not get a free shell prompt back until one of those two events fires.
9. The operator inspects the workspace, may switch focus to another cmux workspace and back (the pr9k workspace persists through focus changes), and eventually dismisses the workspace. The two dismissal gestures cmux exposes — closing the workspace itself, or closing all its panes individually — both reach pr9k's dismissal observation contract from step 8 (the workspace-close gesture removes the workspace from the workspace list; the close-each-pane sequence terminates the placeholder processes). There is no in-workspace dismissal shortcut in Phase 1 — the footer placeholder does not respond to keystrokes ([D5](artifacts/decision-log.md#d5-no-in-workspace-dismissal-affordance-in-phase-1)).
10. On dismissal, pr9k closes the pr9k workspace explicitly if it still exists (so cmux is left consistent regardless of which dismissal gesture the operator used), then explicitly selects the prior workspace recorded in step 2 — if the captured prior workspace still exists. If pr9k recorded "no prior workspace" in step 2, or if the captured prior workspace no longer exists at restore time, pr9k skips the explicit focus-restore and lets cmux apply its default behavior ([D10](artifacts/decision-log.md#d10-no-prior-workspace-state-handled-gracefully)). The launching pr9k process exits with a zero status, freeing the launching terminal session.

## Alternate Flows and States

### Operator launches with cmux mode but cmux preflight fails

- **Entry condition:** any of the five distinguishable cmux-preflight failures occur (cmux not installed, cmux installed but not running, pr9k is not a cmux descendant, cmux socket is disabled, cmux is reachable but missing a required capability).
- **Sequence:** pr9k prints a precondition error to the launching terminal that names the specific failure condition and any operator-actionable detail (the missing capability names, the offending socket path, etc.). No cmux workspace is created. The operator's cmux session is otherwise untouched — no panes spawn, no focus changes happen.
- **Exit:** pr9k exits with a non-zero status. The operator's prior cmux workspace remains in focus because pr9k never left it.

### Operator switches focus away from the pr9k workspace and back

- **Entry condition:** while the four-pane scaffold is up and the launching pr9k process is waiting, the operator switches to a different cmux workspace via cmux's own workspace navigation, then later switches back to the pr9k workspace.
- **Sequence:** the pr9k workspace persists with all four panes intact ([parent T5](../artifacts/feature-technical-notes.md#t5-cmux-workspace-persists-after-pane-exit)). The placeholder processes continue running. The launching pr9k process continues waiting for dismissal. No state changes during the focus excursion.
- **Exit:** workspace state is identical when the operator returns; dismissal proceeds normally when the operator chooses to dismiss.

### Operator sends SIGINT, SIGTERM, or SIGHUP to the launching pr9k process

- **Entry condition:** the operator hits Ctrl-C in the launching terminal, sends SIGINT/SIGTERM to the pr9k process via another route, or causes the parent shell to deliver SIGHUP (typically by closing the launching terminal window in a shell that has `huponexit`-style behavior). SIGHUP delivery is shell-configuration-dependent; if the parent shell does not forward SIGHUP, the pr9k process becomes an orphaned process running until the operator dismisses the workspace through some other route ([D6](artifacts/decision-log.md#d6-double-signal-leaves-an-orphan-workspace-no-cleanup-attempted)).
- **Sequence:** on the first such signal pr9k attempts a graceful shutdown: closes the workspace it created (which terminates the placeholder pane processes), restores focus to the prior workspace if one was captured and still exists, and exits with a non-zero status. If the workspace-close call during shutdown teardown fails (e.g., because the operator simultaneously dismissed the workspace from cmux's controls), pr9k ignores the error and continues to the focus-restore step. If a second signal of any of the three kinds arrives before graceful shutdown completes, pr9k exits immediately; the workspace persists as an orphan ([D6](artifacts/decision-log.md#d6-double-signal-leaves-an-orphan-workspace-no-cleanup-attempted)). The operator dismisses the orphan manually using cmux's own controls.
- **Exit:** non-zero exit either way; orphan workspace possible on double-signal.

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| cmux is not installed on the host. | pr9k aborts before contacting cmux, prints "cmux is not installed" with a pointer to the cmux setup how-to, and exits non-zero. No workspace is created. ([parent D3](../artifacts/decision-log.md#d3-cmux-availability-is-a-hard-precondition-not-a-fallback)) |
| cmux is installed but its socket is not reachable (cmux is not running). | pr9k aborts and prints "cmux is installed but not running; start cmux and try again." No workspace is created. |
| cmux is reachable but pr9k is not a descendant of a cmux process (default access mode rejects pr9k). | pr9k aborts and prints "cmux mode must be launched from inside a cmux session" plus the offending socket path so the operator can verify it ([parent T2](../artifacts/feature-technical-notes.md#t2-cmux-access-model)). |
| cmux is reachable but its socket is explicitly disabled in cmux's configuration. | pr9k aborts and prints "cmux socket is disabled in cmux configuration; re-enable it and try again." |
| cmux is reachable but does not expose every capability pr9k requires for Phase 1 (version skew or breaking change). | pr9k aborts and prints "cmux version is incompatible with pr9k cmux mode" plus the names of the missing capabilities, so the operator knows what to update ([parent D18](../artifacts/decision-log.md#d18-startup-capability-check)). |
| A cmux API call hangs and does not return within the per-call timeout during Phase 1's launch sequence (preflight or workspace creation). | pr9k treats the timeout as fatal and exits with a non-zero status. The timeout is fixed in the 5–10 second range and not operator-configurable in this release ([parent D15](../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal), [parent D27](../artifacts/decision-log.md#d27-cmux-per-call-timeout-value)). If the timeout fires after the workspace already exists, pr9k attempts to tear it down before exit. ([parent T1](../artifacts/feature-technical-notes.md#t1-cmux-programmatic-interface-shape)) |
| cmux's API rejects a request after the workspace has been created (a pane-split, pane-spawn, or pane-hide call). | pr9k tears down the partially-built workspace via the workspace-close API, restores focus to the prior workspace, prints the failing call's diagnostic to the launching terminal, and exits non-zero. The operator's cmux session is left in the state they started in, except for the diagnostic on their launching terminal. No orphan workspace from this failure mode — cleanup is bounded to the work pr9k itself created during this launch. |
| The placeholder process in a visible or hidden pane exits unexpectedly during the waiting phase (step 8 of Primary Flow). | The pane shows the placeholder's exit status per cmux's standard pane-lifecycle behavior ([parent T5](../artifacts/feature-technical-notes.md#t5-cmux-workspace-persists-after-pane-exit)). The launching pr9k process treats this as one of the two dismissal-observation events ([D9](artifacts/decision-log.md#d9-dismissal-observation-contract)): closes the workspace, restores the prior workspace if applicable, exits with a non-zero status. (Phase 6 generalizes display-loss handling; Phase 1's behavior here is the simpler subset.) ([D7](artifacts/decision-log.md#d7-phase-1-placeholder-exit-collapses-to-workspace-dismissal)) |
| The operator dismisses the pr9k workspace (either by closing it or by closing all its panes) before pane setup completes. | The in-flight cmux API call either errors out because its target object no longer exists or hits the per-call timeout ([parent D15](../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal)). Either outcome routes through the partial-setup teardown path (above row): pr9k tears down anything still in place, restores focus to the prior workspace, prints a one-line notice to the launching terminal, and exits with a non-zero status. The workspace cannot be partially adopted by the operator — once dismissed, the launch is over. |
| The launching cmux session contains no workspace other than the launching pane (no prior workspace to capture in step 2). | pr9k proceeds with the launch normally. On dismissal, the explicit focus-restore step is skipped; cmux's default focus behavior applies ([D10](artifacts/decision-log.md#d10-no-prior-workspace-state-handled-gracefully)). |
| The captured prior workspace no longer exists at restore time (the operator closed it from another cmux session during pr9k's lifetime, or cmux itself removed it). | pr9k's workspace-select call fails; pr9k ignores the failure, prints no error, and exits with the status it would have exited with otherwise. cmux's default focus behavior applies ([D10](artifacts/decision-log.md#d10-no-prior-workspace-state-handled-gracefully)). |
| Two concurrent pr9k cmux launches produce the same workspace name (same-nanosecond collision in the timestamp). | pr9k regenerates the timestamp once and retries the workspace creation. A second collision is treated as a partial-setup failure with the same teardown and exit behavior as any other rejected cmux API call ([D12](artifacts/decision-log.md#d12-workspace-name-collision-retried-once-then-fails)). |
| The target repository's basename contains characters cmux rejects in workspace names (spaces, slashes, control characters, certain Unicode), or is empty (e.g., the operator passed `--project-dir /`). | pr9k sanitizes the basename before constructing the workspace name: characters outside the cmux-accepted set are replaced with a single hyphen, runs of hyphens are collapsed, leading and trailing hyphens are trimmed. If the sanitized result is empty (the basename contained no accepted characters), pr9k substitutes the literal string `repo` and continues ([D11](artifacts/decision-log.md#d11-repo-basename-sanitized-before-use-in-workspace-name)). The operator sees the sanitized name in the launching-terminal confirmation line. |
| A prior crashed launch left an orphan pr9k workspace in cmux's workspace list. | Phase 1 does not detect or advise on orphans — the startup advisory is deferred to Phase 7. A fresh workspace is created with a unique name per the workspace name pattern ([parent D29](../artifacts/decision-log.md#d29-workspace-name-pattern), [D12](artifacts/decision-log.md#d12-workspace-name-collision-retried-once-then-fails)), so the new launch does not collide with the orphan. The operator dismisses the orphan manually. |

## User Interactions

- **Affordances:**
  - **Header pane (visible, top):** read-only static placeholder label identifying the pane as the header pane and as Phase 1 placeholder content. No interactive behavior.
  - **Log pane (visible, middle):** read-only static placeholder label identifying the pane as the log pane and as Phase 1 placeholder content. No interactive behavior. cmux's native per-pane mouse selection works inside this pane against the placeholder text — operators can confirm selection works, but no streaming log content exists in Phase 1.
  - **Footer pane (visible, bottom):** read-only static placeholder label identifying the pane as the footer pane and as Phase 1 placeholder content. No control shortcuts are wired in Phase 1; the keyboard state machine ships in Phase 2 ([D5](artifacts/decision-log.md#d5-no-in-workspace-dismissal-affordance-in-phase-1)).
  - **Orchestrator pane (hidden):** kept off-screen by default. Operators can reveal it via cmux's own pane-show controls if they want to inspect placeholder state; it will show no visible activity in Phase 1.
  - **Dismissal gestures:** the operator dismisses the pr9k workspace using cmux's own controls — either the workspace-close gesture (closes the whole workspace at once) or the close-pane gesture applied to one or more of the four panes. Both routes reach pr9k's dismissal observation contract ([D9](artifacts/decision-log.md#d9-dismissal-observation-contract)) and produce the same outcome: workspace teardown and prior-workspace restore (if applicable). The exit status is zero for the workspace-close path and non-zero for the close-pane path (treated as placeholder exit per [D7](artifacts/decision-log.md#d7-phase-1-placeholder-exit-collapses-to-workspace-dismissal)). The exact cmux key bindings depend on the pinned cmux version and are documented in the cmux setup how-to ([OI-3](#open-items)).
  - **Launching terminal:** prints the new workspace's name as a one-line confirmation after creation ([D2](artifacts/decision-log.md#d2-launching-terminal-prints-the-workspace-name)); otherwise silent. On dismissal, returns to a shell prompt. On preflight failure, prints the specific abort message and returns to a shell prompt.
  - **Cmux workspace list:** the new pr9k workspace appears with the `pr9k-<sanitized-repo-basename>-<nanosecond-timestamp>` name ([D11](artifacts/decision-log.md#d11-repo-basename-sanitized-before-use-in-workspace-name)) so the operator can locate it among other workspaces.

- **Feedback:**
  - Successful launch: workspace name printed to the launching terminal, then the cmux workspace appears with focus on it.
  - Preflight failure: a single error line on the launching terminal that names the specific failure condition; no workspace appears.
  - Workspace dismissal: the launching terminal returns to a free shell prompt; cmux focus returns to the prior workspace.
  - No notifications, no sidebar entries, and no log artifacts are produced in Phase 1 — those are Phases 4, 5, and 2 respectively.

- **Error states:**
  - Preflight failure: described above.
  - Partial setup failure: the partially-built workspace is torn down; an error diagnostic appears on the launching terminal.
  - Placeholder process unexpected exit: workspace is closed, prior workspace restored, non-zero exit. The cmux pane's exit status remains visible in the (now-closed) workspace history per cmux's lifecycle.

## Out of Scope

- **Any real workflow execution.** Phase 1 stands up the four-pane scaffold with placeholder content only. Real workflow execution ships in Phase 2.
- **Streaming log output in the log pane.** Phase 1's log pane shows static placeholder text. Streaming output ships in Phase 2.
- **Header pane step checkboxes and iteration counter.** Phase 1's header pane shows static placeholder text. Real header content ships in Phase 2.
- **Footer pane keyboard state machine, shortcut hints, status-line script.** Phase 1's footer pane shows static placeholder text and does not respond to keystrokes. Footer behavior ships in Phase 2; error-mode recovery ships in Phase 3.
- **Cmux sidebar entries.** No sidebar status or progress entries are pushed in Phase 1. Sidebar mirroring ships in Phase 4.
- **Cmux notifications.** No notifications fire in Phase 1. Lifecycle notifications ship in Phase 5.
- **Robust failure handling for orchestrator pane loss, channel stalls, hung cmux calls during a running workflow.** Phase 1 only covers failure handling for the launch sequence and basic placeholder lifecycle. Generalized failure handling ships in Phase 6.
- **Orphan workspace startup advisory.** Phase 1 does not detect or advise on orphan workspaces from prior crashed launches. The startup advisory ships in Phase 7.
- **In-workspace dismissal shortcut.** Phase 1's footer placeholder does not respond to keystrokes; dismissal happens exclusively via cmux's own workspace-close controls. The keyboard-driven dismissal path ships with the rest of the keyboard state machine in Phase 2.
- **Automatic cleanup of orphan workspaces.** Deferred per the parent specification.
- **`pr9k workflow` (the workflow builder) in cmux mode.** Cmux mode applies to the run loop only ([parent D9](../artifacts/decision-log.md#d9-cmux-mode-applies-to-the-run-loop-only-not-the-workflow-builder)); the workflow builder is unaffected by Phase 1.

## Open Items

- **OI-1: Named minimum-supported cmux version.** The capability check is method-presence-based and admits any cmux build that exposes the required methods, but the cmux setup how-to and the Phase 1 release notes need a concrete "tested against version X" line so operators have a target to install. Tracked in the parent build outline as [OQ-1](../build-phase-outline.md#oq-1).
  - **Resolves when:** the team picks a cmux release to pin as the floor (recommendation in the parent build outline: pin to the current latest cmux release and re-evaluate per release).
  - **Blocks implementation:** No — the capability check works regardless. Yes for the setup how-to and release notes that ship with Phase 1.
- **OI-2: CI testing strategy for cmux mode.** cmux is a graphical application; the standard pr9k CI runners cannot launch it. The team needs to decide whether Phase 1's coverage relies on mocked cmux interactions, a live cmux smoke test on a capable runner, or both. Tracked in the parent build outline as [OQ-2](../build-phase-outline.md#oq-2).
  - **Resolves when:** the team commits to a testing approach (recommendation in the parent build outline: mock cmux's programmatic interface for Phase 1 through 5; revisit for Phase 6).
  - **Blocks implementation:** No — Phase 1 can be implemented and manually demoed without a CI strategy in place. Yes for the durability of the Phase 1 test suite.
- **OI-3: cmux setup how-to must document the workspace-dismissal gesture(s).** Phase 1's only dismissal path is "cmux's own workspace-close controls" (or per-pane close, both of which reach the dismissal observation contract per [D9](artifacts/decision-log.md#d9-dismissal-observation-contract)). The Phase 1 demoable in the build-phase outline assumes the operator knows what gesture to use. The cmux setup how-to that ships with Phase 1 must name the specific cmux keyboard or UI gesture(s) operators use to close a workspace, so the demo is reproducible without external context. The exact gesture depends on which cmux version is pinned per [OI-1](#open-items).
  - **Resolves when:** the cmux setup how-to is written and lists the gesture(s) the pinned cmux version exposes for workspace dismissal.
  - **Blocks implementation:** No for the code; yes for the operator-facing docs that ship with Phase 1.

## Summary

- **Outcome delivered:** the operator can launch pr9k in cmux mode, observe a recognizably-named cmux workspace appear with a four-pane scaffold, dismiss it cleanly via either of cmux's standard dismissal gestures, and return to their prior workspace — with no workflow content running inside.
- **Primary actors:** the human operator running pr9k against a target repository from inside a cmux session.
- **Decisions settled by evidence:** 12 — see [artifacts/decision-log.md](artifacts/decision-log.md). (Parent decisions D2, D3, D4, D13, D18, D22, D25, D29 are inherited unchanged.)
