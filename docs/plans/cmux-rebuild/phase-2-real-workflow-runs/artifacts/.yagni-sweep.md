## Items moved to "Deferred (YAGNI)" or replaced with simpler implementations

### YAGNI-1: Heartbeat indicator forwarding across the process boundary

- **Item:** A 1Hz pusher goroutine in the orchestrator polling `pipeline.LastEventAt()` and pushing it over the interaction channel; the header pane process maintains its own atomic-or-mutex-protected timestamp updated from the channel and renders `⋯ thinking (Ns)` on silent claude turns.
- **Failure:** Evidence test fails. The heartbeat indicator is a nice-to-have visible suffix on the header pane's iteration line during silent claude turns. There is no spec commitment that the indicator must appear in cmux mode; behavioral analyst B13 surfaced the gap and concurrency analyst C7 confirmed the cross-process cost. No incident, no measured workload, no operator-described need names the indicator's absence as a problem. The simpler version (drop the indicator in cmux mode) satisfies the spec's primary commitments — header still shows step state, iteration counter still advances; only the per-step silence suffix is absent.
- **Resolution:** Defer with reopening trigger. Phase 2 ships without heartbeat forwarding; header pane renders without the `⋯ thinking` suffix.
- **Reopen when:** An operator reports that long silent claude turns in cmux mode look indistinguishable from a hung run (a real-use signal), OR Phase 4 (sidebar mirroring) adds infrastructure that makes forwarding cheap.
- **Source:** R1 — behavioral-analyst B13, concurrency-analyst C7, test-engineer S2.

### YAGNI-2: Schema-shape validation on the interaction channel

- **Item:** JSON-schema validation of every message crossing the interaction channel (orchestrator-to-pane state pushes, pane-to-orchestrator intents).
- **Failure:** Same anti-pattern Phase 1 named: parent D18 accepts method-presence checking for cmux RPCs; standard `json.Unmarshal` zero-values handle unknown / missing fields. No incident, no spec commitment to schema validation. Same author owns both ends of the channel — no external contract to validate against.
- **Resolution:** Defer with reopening trigger. Standard `json.Unmarshal` (or whatever serialization Phase 2 chooses) is the simpler version.
- **Reopen when:** Cross-version skew between orchestrator and display panes becomes possible (e.g., a rolling release of pr9k where panes from version N are spawned by an orchestrator from version N+1), OR a documented incident shows a confusing message-shape error in production.
- **Source:** R1 — implicit YAGNI-candidate following Phase 1 precedent (Phase 1 YAGNI-2).

### YAGNI-3: Per-pane scrollback persistence to disk after workflow completion

- **Item:** The log pane's scrollback buffer persisted to a side file on workflow completion so the operator can review it after dismissing the workspace.
- **Failure:** Evidence test fails. The spec's D17 commits to log file artifacts under `.pr9k/logs/` which already contain every log line; per-pane scrollback persistence would duplicate that content with no additional information. No named operator need.
- **Resolution:** Defer with reopening trigger. Phase 2's log pane process holds scrollback in memory until the workspace is dismissed (the existing `viewport.Model` ring buffer pattern).
- **Reopen when:** Operators report that the `.pr9k/logs/` content does not match what they saw in the log pane during a run.
- **Source:** R1 — junior-developer OQ-6 (raised as a question, not a recommendation; resolved by reuse of existing artifacts).

### YAGNI-4: Configurable handshake-timeout value

- **Item:** A CLI flag or `config.json` field for operators to tune the readiness-handshake timeout.
- **Failure:** Named anti-pattern: "speculative configuration knob." No operator has described a need; the default Phase 2 chooses (recommend: equal to the cmux per-call timeout 5–10s from parent D27, with the actual Phase 2 number landing as plan decision) satisfies the spec without an operator-facing tuning surface.
- **Resolution:** Defer with reopening trigger. Hard-code the handshake timeout in Phase 2.
- **Reopen when:** An operator reports the default trips false-positives on slow startups, OR Phase 6 introduces a broader stall-threshold configuration surface.
- **Source:** R1 — implicit YAGNI candidate (concurrency C1 surfaced the timeout requirement; configurability not proposed).

### YAGNI-5: Live cmux integration test in CI for Phase 2

- **Item:** A live-cmux smoke test that exercises the four-process architecture end-to-end.
- **Failure:** Already deferred by build-outline OQ-2 to Phase 6. Test-engineer S1 confirms.
- **Resolution:** Defer (matches build-outline OQ-2 recommendation).
- **Reopen when:** Phase 6 starts and CI integration-test infrastructure decision lands.
- **Source:** R1 — test-engineer S1 (inherited from Phase 1's YAGNI-4).

### YAGNI-6: Cross-pane drift measurement / SLO

- **Item:** Instrumentation that measures and asserts the actual cross-pane drift across the three panes, with an SLO that the drift stays under the T4-stated "single-digit-millisecond" budget.
- **Failure:** Named anti-pattern: "SLOs and error budgets for traffic the system doesn't yet receive." T4 commits to the budget; no operator has reported observable desync as a problem; no production traffic exists.
- **Resolution:** Defer with reopening trigger. Phase 2 honors T4 by topology (per-connection goroutines) rather than by measurement.
- **Reopen when:** An operator reports visible cross-pane desync, OR Phase 4 (sidebar mirroring) creates a meaningful third measurement point.
- **Source:** R1 — test-engineer S3 (cross-pane drift bound verification).

### YAGNI-7: Status-line script diagnostic forwarding to orchestrator log

- **Item:** A protocol message that carries `statusline.Runner` diagnostic strings (script start errors, exec failures, timeout warnings) from the footer pane process to the orchestrator's logger so they appear in `.pr9k/logs/<run>.log`.
- **Failure:** Simpler-version test: passing `nil` as the `*logger.Logger` argument to `statusline.New` makes `r.logLine()` a no-op. The status-line script's standard error output is already visible to the operator in the footer pane on script failure (the runner displays it). The on-disk log loses the runner's internal diagnostics, but no operator has named that as a need; the runner's diagnostics are operator-script-development aids, not run-correctness signals.
- **Resolution:** Replace with simpler version. The footer's `statusline.Runner` is constructed with `nil` logger in cmux mode; runner diagnostics are silent in the on-disk log.
- **Reopen when:** An operator reports they need to see runner diagnostics in the persisted log file (e.g., for a status-line script that fails only on long-running production runs).
- **Source:** R1 — behavioral-analyst B10, concurrency-analyst C6.

### YAGNI-8: A new `cmuxpane` package (or set of sub-commands) for each pane renderer

- **Item:** A dedicated `internal/cmuxpane/{header,log,footer,orchestrator}` package with full Bubble Tea models per pane, and matching `pr9k cmux-{header,log,footer}` sub-commands.
- **Failure:** Simpler-version test. The standard run loop already has `ui.StatusHeader`, the log panel renderer in `internal/ui`, and the footer's keyboard state machine in `internal/ui/keys.go`. Phase 2 reuses these renderers; the per-pane sub-commands need only thin entry points (read interaction-channel messages, drive the existing renderer with the received state). A bespoke `cmuxpane` package for each pane would duplicate the existing renderers.
- **Resolution:** Replace with simpler version. Add per-pane entry points (sub-commands or single binary with a flag) that reuse the existing `internal/ui` renderers; the new code is the interaction-channel client wrapping the existing renderer, not a new renderer.
- **Reopen when:** A specific pane's rendering needs diverge materially from its standard-TUI counterpart (e.g., the footer pane's help-modal layout in cmux mode is genuinely different and warrants its own component).
- **Source:** R1 — junior-developer OQ-2 framing + behavioral B13 (heartbeat-skip enables renderer reuse with one small adaptation).
