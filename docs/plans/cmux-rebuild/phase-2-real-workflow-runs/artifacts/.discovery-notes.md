## Tech stack

- **TUI framework:** Bubble Tea (`github.com/charmbracelet/bubbletea`) + Lip Gloss + `bubbles/viewport`, in `--alt-screen` + `WithMouseCellMotion` mode. Standard run loop only; cmux mode is intentionally Bubble-Tea-free.
- **CLI framework:** spf13/cobra (`internal/cli`).
- **Test runner:** `go test -race ./...` (the `-race` flag is mandatory per `docs/coding-standards/testing.md`).

- **CI surface:** `make ci` runs test + lint + format + vet + vulncheck + mod-tidy + build.

## Phase 1 — what is already in the codebase

The cmux-rebuild branch already shipped Phase 1. Phase 2 builds directly on this code.

### `internal/cmuxctl` package (`src/internal/cmuxctl/`)

- **`client.go`** — defines `CmuxClient` interface (10 RPCs: `SystemIdentify`, `WorkspaceCurrent`, `WorkspaceList`, `WorkspaceCreate`, `WorkspaceClose`, `WorkspaceSelect`, `SurfaceSplit`, `SurfaceSpawn`, `SurfaceHide`, `SurfaceList`) plus `Identity`, `SplitOpts`, `PaneInfo` types.
- **`real.go` (352 lines)** — `RealClient` JSON-RPC 2.0 over Unix domain socket. Single-goroutine sequential queue. Per-call timeout closes the socket on fire; teardown re-opens for the final `WorkspaceClose`. Uses `net.DialUnix` (per recent fix `ae6adbe1d` to avoid GO-2026-4971).
- **`fake.go` (204 lines)** — `FakeClient` test double, `sync.Mutex`-protected, scriptable per-method behavior.
- **`preflight.go` (135 lines)** — five-condition preflight (cmux not installed, not running, ancestry, socket disabled, capability mismatch) + `CMUX_SOCKET_PATH` env validation. `Prober` interface for testability.
- **`runphase1.go` (221 lines)** — `RunPhase1(ctx, client, projectDir, out, dismissalCfg)`. Captures prior workspace, sanitizes basename (`SanitizeBasename`), composes name `pr9k-<sanitized>-<nanosecond-UTC-timestamp>`, creates workspace with one collision retry, spawns four panes orchestrator-first (each runs `sh -c '<placeholder-printf> && tail -f /dev/null'`), hides the orchestrator, starts the `DismissalObserver`, blocks until dismissal or ctx cancel. Teardown via `sync.Once`: `WorkspaceClose`, focus-restore, observer `Wait`.
- **`dismissal.go` (201 lines)** — `DismissalObserver` — 500ms poll, single-flight, fires on workspace-removed OR any pane shows `Exited: true`. Three consecutive poll timeouts → fatal sentinel. `shuttingDown` flag + channel priming to suppress self-close double-fire.

### Existing standard-run-loop integration points Phase 2 must honor

Phase 2's orchestrator process will reuse the standard run loop's machinery. Key existing types:

- **`workflow.Run(executor StepExecutor, header RunHeader, keyHandler *ui.KeyHandler, cfg RunConfig) RunResult`** — `internal/workflow/run.go` line 316. The main orchestration entry point. Takes:
  - `StepExecutor` interface (`workflow.Runner` implements it; `SetSender(func(string))` callback drains each emitted log line)
  - `RunHeader` interface (`*ui.StatusHeader` implements it; methods: `RenderInitializeLine`, `RenderIterationLine`, `RenderFinalizeLine`, `SetPhaseSteps`, `SetStepState`)
  - `*ui.KeyHandler` — the keyboard state machine (modes: `ModeNormal`, `ModeError`, `ModeQuitConfirm`, `ModeNextConfirm`, `ModeDone`, `ModeSelect`, `ModeQuitting`, `ModeHelp`)
  - `RunConfig` with `WorkflowDir`, `Iterations`, `Env`, `ContainerEnv`, `InitializeSteps`, `Steps`, `FinalizeSteps`, `LogWidth`, `RunStamp`, `Runner` (status-line)
- **`logger.NewLogger(projectDir)`** — `internal/logger`. Creates per-run log file under `<projectDir>/.pr9k/logs/<run-stamp>.log` and provides `RunStamp()` accessor for artifact-directory naming. Phase 1 deliberately bypasses this; Phase 2 must reintroduce it because spec commits log artifacts unchanged in cmux mode (parent D17).
- **`statusline.Runner`** — `internal/statusline`. Spec D26 says the status-line script runs unchanged. The runner is goroutine-based, accepts a `Sender` for re-render notifications and a `ModeGetter` for the stdin payload, runs the script on its own cadence + `Trigger`. In standard mode the script runs **in the pr9k process**; for Phase 2 it must run **in the footer pane's process**.
- **`ui.KeyHandler`** — `internal/ui/ui.go`. Owns the keyboard mode field (mutex-protected), exposes `Cancel()`, `SetMode()`, `ForceQuit()`, `Mode()`, `PrevMode()`, `SelectJustReleased()`, `ShortcutLine()`, `SetStatusLineActive()`. Used by `internal/ui/keys.go`'s `keysModel` which translates `tea.KeyMsg` into intents.
- **`ui.StatusHeader`** — `internal/ui/header.go`. Owns the step checkbox grid + iteration line. Pointer-mutable; the workflow goroutine calls its methods directly. Has a `HeartbeatReader` for "thinking" indicator on silent claude turns.
- **`ui.LogLinesMsg`** — Bubble-Tea message type that carries batched log lines into the standard TUI's log panel via the `program.Send` path. The standard run already coalesces bursts in a `drain` goroutine.
- **`workflow.Runner.SetSender(func(string))`** — every log line emitted by the subprocess goes here. Phase 2 needs an analogue that sends to the log-pane process.

## Open Question 3 (from build-phase-outline.md)

OQ-3 (blocks Phase 2): **What is the mechanism for the local interaction channel between orchestrator and display panes?**

- **Recommendation (in source):** **Option A — A Unix domain socket per workspace owned by the orchestrator, with each display pane process connecting on startup.** Reasoning: mature, easy to test, works for both directions of traffic, easy to detect loss (broken connection); fits the multi-process topology cleanly (each display pane process is spawned by cmux but knows where to find the orchestrator's socket via an environment variable or command-line argument); loss detection is the socket's broken-connection signal; the same socket carries the readiness handshake.

This is the load-bearing decision Phase 2 must settle definitively. **Treat OQ-3's Option A recommendation as a strong-default that the team may either confirm or override with evidence** — it has not yet been formally committed as a Phase 2 decision.

## Spec commitments Phase 2 must deliver (per build-outline)

1. Hidden orchestrator pane runs the workflow engine — same phase semantics, step definitions, iteration counter, exit codes as the standard display.
2. Header pane shows step checkbox progress + iteration counter; updates live.
3. Log pane shows streaming output within the existing latency budget; pane-local scrollback when focused.
4. Footer pane shows status line + shortcut hints + supports basic running-state shortcuts (quit two-step `q`/`y`, help, next-iteration confirmation, skip current step).
5. Readiness handshake gates the workflow's first step — orchestrator waits until every visible pane signals it is rendering before pushing the first state.
6. Log artifacts on disk byte-for-byte same as standard-display run.

Plus the spec's Coordinations table commits:
- Bidirectional local interaction channel with stall-threshold loss detection (OQ-4 calls the stall-threshold value out as a Phase 6 question; Phase 2 must at minimum define the channel shape and the readiness handshake protocol).
- Display panes converge to orchestrator's latest state (eventual consistency, single-digit-ms drift acceptable per T4).
- Intents are serial and ordered by arrival.

## Explicit gaps the team should be aware of

- **No `feature-specification.md` was authored specifically for Phase 2.** The source is the Phase 2 section of `build-phase-outline.md`, plus the parent feature spec, plus parent technical notes T3 and T4 which name display-process-update independence and the readiness-handshake requirement.
- **OQ-3 (interaction channel mechanism)** has a strong-default Option A recommendation but is not formally a committed decision. The team should treat it as committable on evidence.
- **OQ-4 (stall-threshold value) is deferred to Phase 6** by the build outline. Phase 2 must define the channel and the handshake but not the loss-detection threshold value.
- **The status-line script must run in the footer pane process** for Phase 2 per spec D26. The existing `statusline.Runner` is goroutine-based and expects to live in the same process as the rest of the TUI. The team must decide whether to lift the runner into the footer's process unchanged, refactor it, or wrap it.
- **Live-cmux integration testing is deferred to Phase 6** per build-outline OQ-2 recommendation. Phase 2's test surface is `FakeClient` plus any new test doubles for the interaction channel. The package shape should keep the door open for live tests later.
- **Version bump for Phase 2 release-readiness** — Phase 1's plan called for `0.10.0 → 0.11.0` but the file in this branch still reads `Version = "0.10.0"`; that is either a deliberate hold or a not-yet-shipped change. The team should clarify whether Phase 2 lands in its own release bump or absorbs the deferred Phase 1 bump.
