# Implementation Decision Log: Phase 5 — Lifecycle Notifications

This file records every implementation decision committed while planning Phase 5 — Lifecycle Notifications. Behavioral and implementation statements live in [../feature-implementation-plan.md](../feature-implementation-plan.md) — this file captures the question, rationale, evidence, and rejected alternatives for each decision. Round-by-round history lives in [implementation-iteration-history.md](implementation-iteration-history.md).

Phase 5 inherits the spec's evidence-settled decisions (spec [D1–D13](../feature-specification.md) full; spec D14–D18 trivial) unchanged; this log records only **implementation** decisions made while planning *how* to deliver them. The dominant inputs are: (a) the parallel `cmuxSidebar` precedent from Phase 4; (b) the cmux v2 notification dispatch shape verified at commit `2f96c15c2` (six candidate methods documented in the build outline at line 269); (c) the existing `cmuxctl.RealClient` queue with its untyped `fmt.Errorf` timeout string; (d) the existing `cmux_footer_machine.go` state machine that handles `q`/`y` quit-confirmation locally and does not surface `q` to the orchestrator; (e) the user's OQ-1 resolution adopting Option 2 (extend `interactionchannel` with two new intent types) over the spec-narrowing alternative.

## Full decisions

### PD-1: `cmuxNotifier` is a new struct parallel to `cmuxSidebar`

- **Question:** spec [D1](../decision-log.md#d1-three-notification-classes-and-their-targeting) commits three notification classes targeting the pr9k workspace. Where does that firing code live — as a method-set extension on `cmuxSidebar`, a decorator that wraps `cmuxSidebar`, or a separate struct composed alongside `cmuxSidebar`?
- **Decision:** Phase 5 ships **one new type** in `src/cmd/pr9k/cmux_notifier.go`. `cmuxNotifier` owns a `cmuxctl.CmuxClient`, a `cmuxctl.Workspace`, a `*logger.Logger`, a read-only sidebar pointer (for `LastStepName()`), a `sync.Mutex`, and per-error-mode-session state (`errorActive bool`, `snapshotName string`, `cancelRefire context.CancelFunc`, `resolved chan struct{}`). Method set: `FireCompletion(ctx)`, `FireRunAborted(ctx)`, `EnterErrorMode(ctx, stepName)`, `ExitErrorMode()`, `RestartErrorModeTimer(ctx)`, plus an internal `firePersistent(ctx)`. The struct is constructed in `runCmuxOrchestratorWith` parallel to `*cmuxSidebar` and passed into `runCmuxWorkflowAdapted`.
- **Rationale:** SRP — `cmuxSidebar`'s job is to push status pill + progress bar values to cmux's persistent sidebar surface (passive monitor). `cmuxNotifier`'s job is to fire transient interrupt notifications with a re-fire cadence. Different transports (sidebar uses `WorkspaceSetStatus`/`WorkspaceClearStatus`/`WorkspaceSetProgress`/`WorkspaceClearProgress`; notifier uses `WorkspaceNotify`), different lifecycle events (sidebar pushes on every step transition; notifier fires only on the three named lifecycle moments), different state machines (sidebar caches `lastStepName` / `progressPushed`; notifier owns a re-fire timer and a `resolved` channel). Keeping the two concerns separate avoids overloading either struct. Phase 4 [D-1](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-1-sidebar-adapter-is-a-separate-cmuxsidebar-struct-plus-a-sidebarawareheader-wrapper-composed-alongside-cmuxheader) used the same reasoning (separate `cmuxSidebar` from `cmuxHeader`); Phase 5 applies it again for the same reason.
- **Evidence:** R1 — `software-architect` A1 + `junior-developer` JD-006 + spec [D14](../decision-log.md#trivial-decisions) ("notifications and sidebar updates are independent side-by-side effects of the same orchestrator lifecycle event — the orchestrator emits both for error-mode entry / exit, and neither blocks or coalesces with the other"). `docs/coding-standards/concurrency.md` (snapshot-then-unlock pattern for cached state). `docs/coding-standards/api-design.md` (adapter types, compile-time interface assertions). Verified code: `src/cmd/pr9k/cmux_sidebar.go` (the existing parallel adapter pattern Phase 5 mirrors).
- **Rejected alternatives:**
  - **Extend `cmuxSidebar` with the notification transport methods directly** — rejected (SRP); `cmuxSidebar` would carry two transports, two error policies (sidebar D7 is per-call log-and-continue; notifier needs the additional D10 abort-path-non-fatal exception and the D16 post-resolution-non-fatal exception), and two lifecycle event sets in one struct; testing and Phase 6 evolution become tangled.
  - **Decorate `cmuxSidebar` (wrap it as the notifier interface)** — rejected; the two surfaces are conceptually independent per spec D14, not a layered concern.
  - **Add a new method to a shared cmux adapter interface (e.g., `CmuxLifecycle`)** — rejected (premature abstraction); Rule of Three not met (two concrete consumers, one each); the YAGNI rule's simpler-version test prefers two parallel structs over a shared interface.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** reopen if a third lifecycle adapter appears (Rule of Three) — at that point a shared `CmuxLifecycle` interface may become evidence-justified. The `NotifierPort` deferral (see plan's Deferred (YAGNI)) is reopened by the same trigger.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** PD-2, PD-5, PD-6, PD-9, PD-10, PD-12, PD-13, PD-15
- **Referenced in plan:** Outcome, Context (Future-state concern), Implementation Approach (Architecture and Integration Points, Runtime Behavior), Decomposition and Sequencing (W4)

### PD-2: One new `WorkspaceNotify` method covers all three notification classes

- **Question:** the spec commits three notification classes (completion, run-aborted, error-mode). Are they three distinct RPC methods on `cmuxctl.CmuxClient`, or one method that takes the class as a parameter?
- **Decision:** **One** new method on `CmuxClient`: `WorkspaceNotify(ctx context.Context, ws Workspace, class NotificationClass, body string) error`. `NotificationClass` is a typed string constant in the same package with three values: `NotificationCompletion`, `NotificationRunAborted`, `NotificationErrorMode`. The class is internal to pr9k — `cmuxNotifier` composes the per-class body text per spec [D2](../decision-log.md#d2-notification-text-is-repo-name-plus-lifecycle-verb-error-text-incorporates-the-footer-pane-directive)'s canonical wording, and `RealClient` translates the call into cmux's verified `notification.*` wire method. Class semantics (urgency, cadence, persistence) live in `cmuxNotifier`, not in the wire wrapper.
- **Rationale:** ISP applies to clients of an interface, not authors. The three notification classes share an identical wire shape (workspace handle, text body) and an identical timeout policy; their differences are pr9k-side semantics (when to fire, whether to re-fire, what to do on timeout). Three separate methods would duplicate the wire wrapper three times for no operator-visible behavior change. The single method matches Phase 4's "no opts parameter" stance ([Phase 4 D-3](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-3-cmuxclient-gains-four-new-methods-directly-no-cmuxsidebar-sub-interface)) — pr9k does not expose cmux's optional urgency/icon parameters to the operator in this release.
- **Evidence:** R1 — `software-architect` A2 (single method covers all three classes; class semantics live in `cmuxNotifier`). YAGNI rule doc `plugins/han/references/yagni-rule.md` (single-implementation-interface anti-pattern; symmetry/completeness is not evidence — three methods would be a completeness anti-pattern). Spec [D14](../decision-log.md#trivial-decisions) (notifications and sidebar updates are independent side-by-side effects); spec [D2](../decision-log.md#d2-notification-text-is-repo-name-plus-lifecycle-verb-error-text-incorporates-the-footer-pane-directive) (text is composed pr9k-side, not cmux-side). Verified code: `src/internal/cmuxctl/client.go` (existing `CmuxClient` with 12 methods, none of which take a class parameter — Phase 5 introduces the pattern).
- **Rejected alternatives:**
  - **Three separate methods on `CmuxClient` (`WorkspaceNotifyCompletion`, `WorkspaceNotifyRunAborted`, `WorkspaceNotifyErrorMode`)** — rejected (DRY); three wrappers that duplicate timeout, error classification, and serialization logic for no operator-visible benefit.
  - **One method with a free-form `class string`** — rejected (typed-string-constant precedent per `docs/coding-standards/go-patterns.md`); typed constants catch typos at compile time.
  - **Introduce a `CmuxNotifier` sub-interface embedded into `CmuxClient`** — rejected (single-implementation-interface anti-pattern); one production caller (`cmuxNotifier`), one test double (`FakeClient`), no second concrete use. Phase 4 [D-3](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-3-cmuxclient-gains-four-new-methods-directly-no-cmuxsidebar-sub-interface) precedent.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** reopen if cmux exposes per-class semantics on the wire (e.g., a `notification.create_persistent` method distinct from `notification.create_oneshot`), at which point the single method's translation layer in `RealClient` would need a class dispatch.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** PD-3, PD-4
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, External Interfaces), Decomposition and Sequencing (W2), Testing Strategy

### PD-3: `Preflight` is extended with one probe call to `WorkspaceNotify`

- **Question:** spec [D8](../decision-log.md#d8-the-phase-1-capability-check-is-extended-to-cover-phase-5s-notification-methods) commits the Phase 1 capability check to verify Phase 5's notification methods. The current `Preflight()` is identify-only (`src/internal/cmuxctl/preflight.go`); cmux v2 has no `system.capabilities` enumeration RPC. What mechanism realizes spec D8?
- **Decision:** `Preflight` issues **one probe call** to `client.WorkspaceNotify(ctx, Workspace{}, NotificationCompletion, "")` after the existing `SystemIdentify` step succeeds. An `isMethodNotFound(err)` helper checks `*CmuxError` for `Code == "method_not_found"` OR `Code == "unknown_method"`. If the helper matches, `Preflight` fails the launch with a method-named error per spec D8: `"cmuxctl: cmux build does not expose required notification method WorkspaceNotify (notification.create_for_target); upgrade cmux"`. Any other error from the probe (zero-workspace rejection, network error, anything else) is treated as method-exists and the probe passes. Only the one new method (`WorkspaceNotify`) is probed; per-method enumeration of the other 12 `CmuxClient` methods stays deferred (Phase 4 YAGNI carries forward).
- **Rationale:** the probe-once mechanism gives a method-named, actionable preflight error per spec D8 without per-method enumeration's surface cost. A benign call with a zero workspace handle is the minimum exercise that proves the method exists on the wire — cmux's error envelope tells us "method missing" vs. "method exists but rejected this input." The two-candidate code check (`"method_not_found"` OR `"unknown_method"`) defends against the manual cmux integration gate revealing a different code than expected; the helper is symmetric to how Phase 4's `WorkspaceList` workaround handled the `"id"/"ref"` discrepancy. Probing only the one new method (not all 13) is the YAGNI-correct scope — Phase 4's identify-only check + version pin already covers the existing methods.
- **Evidence:** R1 — `software-architect` A3 + `behavioral-analyst` B5 (two specialists converged on the same mechanic). Existing `classifyIdentifyError` helper in `src/internal/cmuxctl/preflight.go` (already demonstrates the code-inspection pattern for known codes — `auth_required`, `auth_failed`, `auth_unconfigured`). Spec [D8](../decision-log.md#d8-the-phase-1-capability-check-is-extended-to-cover-phase-5s-notification-methods) (method-named error required). [Phase 4 D-4](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-4-capability-check-stays-identify-only-the-cmux-version-pin-moves-0646--0647) precedent for the version-pin alternative (per-method enumeration deferred). YAGNI rule doc `plugins/han/references/yagni-rule.md` (simpler-version test).
- **Rejected alternatives:**
  - **Per-method enumeration over all 13 `CmuxClient` methods** — rejected (symmetry / completeness anti-pattern); Phase 4 YAGNI deferral stands. Phase 5 probes only the one new method.
  - **Leave `Preflight` identify-only and rely on D7 runtime detection** — rejected; trades a clear preflight failure for a silent runtime degradation. Spec D8 explicitly requires the method-named preflight error.
  - **Single-candidate `isMethodNotFound` (only `"method_not_found"`)** — rejected; the discovery notes flagged that the exact code is not cited in the cmux source available at planning time. The two-candidate helper closes the gap pre-emptively.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** reopen if a cmux release surfaces a third candidate code, OR the manual cmux integration gate reveals that neither candidate matches; at that point the helper is adjusted to the actual code per [parent D-R4](../../artifacts/decision-log.md#d-r4-manual-cmux-integration-gate) precedent.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1, R2 (R2 confirmed the two-candidate strategy)
- **Dependent decisions:** PD-4
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, Runtime Behavior), Decomposition and Sequencing (W2), Definition of Done, Open Items (OI-2)

### PD-4: Typed `*cmuxctl.TimeoutError` replaces the `fmt.Errorf` timeout string

- **Question:** `cmuxctl.RealClient` returns timeout errors as `fmt.Errorf("cmuxctl: %s timed out after %s", method, duration)` — a plain error with no typed sentinel. Phase 5 must distinguish "timeout" from "other error" to apply spec D7 (non-timeout = log-and-continue) vs. parent D15 (timeout = fatal) vs. spec D10 (abort-path call timeout = log-and-continue even on timeout). How is the distinction encoded?
- **Decision:** introduce an exported typed error `*cmuxctl.TimeoutError` in `internal/cmuxctl` and return it from the `RealClient` timeout site instead of the current `fmt.Errorf`. `cmuxNotifier`, `cmuxSidebar`, and any future caller use `errors.As(err, &te)` to detect timeouts. As part of the same change, `cmuxSidebar`'s existing `errors.Is(err, context.DeadlineExceeded)` timeout-detection (a pre-existing latent defect that does not catch queue-level timeouts — the `RealClient` queue's timeout fires `fmt.Errorf`, not `context.DeadlineExceeded`) is corrected to `errors.As(err, &te)`. The classifier distinguishes four cases: `nil`, `*TimeoutError`, `context.Canceled` / `context.DeadlineExceeded` (in-flight calls during shutdown — treated non-fatal because the caller's context is already cancelled), and other.
- **Rationale:** typed error matches Phase 4's `*PlaintextError` / `*CmuxError` precedent in `cmuxctl`. String-matching the existing error message is brittle (a one-character change to the format string breaks the classifier) and fails `docs/coding-standards/error-handling.md`'s implicit contract that callers should not parse error messages. The four-specialist convergence (R1 — A4, C4, B3, JD-003) on the typed-error approach is the strongest evidence signal in R1. The pre-existing latent defect in `cmuxSidebar` makes the fix opportunistic — Phase 5 introduces the typed error and fixes a Phase 4 bug at the same time, both protecting the spec D7/D10/D16 distinctions and removing a misclassification hazard from sidebar code.
- **Evidence:** R1 — `software-architect` A4 + `concurrency-analyst` C4 + `behavioral-analyst` B3 + `junior-developer` JD-003 (four specialists converged). Verified code: `src/internal/cmuxctl/real.go` (current timeout site emits `fmt.Errorf`); existing `*PlaintextError` and `*CmuxError` precedent in the same package; `src/cmd/pr9k/cmux_sidebar.go` (the existing `errors.Is(err, context.DeadlineExceeded)` check that does not catch queue-level timeouts — verified during discovery). `docs/coding-standards/error-handling.md` (typed error preference; package-prefixed messages). Spec [D7](../decision-log.md#d7-non-timeout-notification-errors-are-logged-and-the-run-continues-timeouts-remain-fatal-per-parent-d15) (classification required); spec [D10](../decision-log.md#d10-abort-path-notification-calls-treat-every-failure-including-timeout-as-non-fatal-explicit-exception-to-parent-d15) (abort-path exception requires distinguishing timeout); spec [D16](../decision-log.md#trivial-decisions) (post-resolution non-fatal requires distinguishing timeout).
- **Rejected alternatives:**
  - **Exported sentinel `ErrCmuxTimeout` via `errors.Is`** — rejected; sentinels carry no per-instance data (method name, duration), forcing duplicate logging at every call site; the typed error keeps the data with the error.
  - **String-match the existing `fmt.Errorf` message** — rejected; brittle, fails the error-handling standard, and the Phase 4 latent defect was caused by exactly this kind of weak classification.
  - **Leave the existing `fmt.Errorf` in place and rely on `context.DeadlineExceeded`** — rejected; the queue-level timeout in `RealClient` does not fire `context.DeadlineExceeded` (the queue cancels its own context internally), which is why `cmuxSidebar`'s pre-existing check is latently defective.
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** reopen if `cmuxctl` evolves to multiplex calls (the current queue is single-goroutine sequential) — at that point the timeout-vs-cancel distinction may need finer-grained typed errors.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** PD-5, PD-9, PD-10, PD-12
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, Runtime Behavior — Error paths), Decomposition and Sequencing (W1), Definition of Done

### PD-5: The re-fire timer lives on `cmuxNotifier`; context cancellation stops it

- **Question:** the error-mode notification's 60-second re-fire timer needs a goroutine. Where does the goroutine live (inside the `OnModeChange` closure? on `cmuxNotifier`? on `cmuxSidebar`?), how is its lifecycle scoped (started when? stopped when?), and how is the goroutine cleaned up on panic / abort paths?
- **Decision:** the timer goroutine is owned by `cmuxNotifier`, started inside `EnterErrorMode` via `context.WithCancel(ctx)` (the per-session child context), stopped via `cancelRefire()` called from `ExitErrorMode`, and defended by `defer notifier.ExitErrorMode()` registered at the construction site in `runCmuxOrchestratorWith` (mirroring `defer sidebar.ClearAll(...)`). The goroutine uses `time.NewTicker(60 * time.Second)` constructed once at error-mode entry and applies `ctx.Err()` after `ticker.C` fires to avoid one spurious RPC call on race with cancellation. `cmuxNotifier` carries its own `sync.Mutex` covering `errorActive`, `snapshotName`, `cancelRefire`, and `resolved`; both the key-adapter goroutine (which signals timer stop / restart) and the orchestrator goroutine (which calls `EnterErrorMode` from the `OnModeChange` callback) touch these fields, so a mutex is required.
- **Rationale:** keeping the timer goroutine inside `cmuxNotifier` (not inside the closure) preserves SRP per PD-1 and gives the goroutine a clean stop-signal — `context.WithCancel(ctx)` is the idiomatic Go pattern for "stop this goroutine when the parent does or when I say so." The outer `defer` mirrors Phase 4 [D-7](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-7-cmuxsidebar-construction-is-hoisted-to-runcmuxorchestratorwith-a-defer-sidebarclearallcontextbackground-runs-on-every-exit-path) and provides the panic / abort safety net Phase 6 will reuse. The `ctx.Err()` guard after `ticker.C` is the `concurrency.md`-prescribed defense against the well-known race where the ticker fires concurrent with cancellation and the goroutine issues one spurious call before the next `select` iteration sees `ctx.Done()`. The single mutex (not multiple field-specific mutexes) keeps the snapshot-then-unlock pattern simple — reads are short, and the cross-field invariants (e.g., "if `errorActive` is true, `cancelRefire` is non-nil") are easier to maintain under one lock.
- **Evidence:** R1 — `software-architect` A5 + `concurrency-analyst` C1, C3, C7, C8 (multi-specialist convergence on the goroutine ownership and the mutex coverage). `docs/coding-standards/concurrency.md` (snapshot-then-unlock; `ctx.Err()` guard after timer fires; non-blocking channel sends). [Phase 4 D-7](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-7-cmuxsidebar-construction-is-hoisted-to-runcmuxorchestratorwith-a-defer-sidebarclearallcontextbackground-runs-on-every-exit-path) precedent. Verified code: `src/cmd/pr9k/cmux_pane.go` (the `runCmuxOrchestratorWith` construction site and the `defer sidebar.ClearAll(context.Background())` registration pattern).
- **Rejected alternatives:**
  - **Timer goroutine inside the `OnModeChange` closure (as a local closure)** — rejected (lifecycle scope); the closure runs for the duration of one mode change call, not the duration of the error-mode session. A goroutine spawned inside the closure would either leak (no stop signal) or require a global flag (race-prone).
  - **Timer goroutine inside `cmuxSidebar`** — rejected (SRP per PD-1); the sidebar's existing concerns are pushing status / progress values, not maintaining a re-fire cadence.
  - **Stop signal via a `chan struct{}` instead of `context.WithCancel`** — rejected; the goroutine already needs `ctx.Done()` for parent-cancellation cleanup, so adding a second channel is redundant; the cancellable child context is the idiomatic Go pattern.
  - **Per-field mutex** — rejected; the cross-field invariants (e.g., "`errorActive` and `cancelRefire` are coupled") become harder to maintain under multiple locks; the snapshot-then-unlock pattern with one mutex is the standards-prescribed default.
- **Specialist owner:** `concurrency-analyst`.
- **Revisit criterion:** reopen if Phase 6 introduces a multi-goroutine notifier (e.g., parallel notification surfaces for non-cmux backends), at which point per-field locks or per-channel state may become necessary.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** PD-6, PD-10, PD-12
- **Referenced in plan:** Outcome, Context (Future-state concern), Implementation Approach (Architecture and Integration Points, Runtime Behavior), Decomposition and Sequencing (W4), RAID Log (Risks R3, R5), Definition of Done

### PD-6: Three-step ordering of error-mode effects is enforced by sequential statements in the `OnModeChange` callback

- **Question:** spec [D12](../decision-log.md#d12-error-mode-effects-are-ordered-footer-broadcast-state-bit-and-timer-notification-call) commits an ordering: footer broadcast first → state bit + timer second → notification call third. The existing `OnModeChange` closure in `runCmuxWorkflowAdapted` already runs footer broadcast (Phase 3) then sidebar mutation (Phase 4). Where does Phase 5's notifier mutation slot in?
- **Decision:** the existing `OnModeChange` closure is **augmented in place** by appending one new statement after the existing sidebar call. When `mode == ui.ModeError`, the closure runs:
  1. **Footer broadcast** (Phase 3 — unchanged): `ch.SendStateFooter(...)`.
  2. **Sidebar mutation** (Phase 4 — unchanged): `sidebar.EnterErrorMode(ctx)`.
  3. **Notifier mutation** (Phase 5 — new): `notifier.EnterErrorMode(ctx, sidebar.LastStepName())`.
  Both (2) and (3) are spec D12's step 3 — but with sidebar called first to preserve Phase 4's existing behavior. The three statements run sequentially in the same goroutine; spec D12 ordering is enforced structurally. `notifier.EnterErrorMode` fires the initial notification call synchronously inside its body — not in a spawned goroutine — so the state bit (`errorActive = true`) is set before the call begins, which preserves the timer-stop contract from spec [D5](../decision-log.md#d5-resolution-of-the-error-prompt-stops-re-fire-immediately) (the operator's stop signal must find a state to flip).
- **Rationale:** sequential statements in a synchronous callback are the simplest correct mechanism for the spec D12 ordering. Phase 4 [D-2](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-2-error-mode-marker-fires-by-augmenting-the-existing-onmodechange-closure-in-place-reading-from-a-cached-step-name) already established the augment-in-place pattern; adding a third statement does not warrant a slice-of-hooks refactor (Phase 4 RAID R3 trigger — "fourth independent effect that does not compose cleanly" — is not met by Phase 5's single addition). Sidebar called before notifier (rather than the reverse) preserves Phase 4's existing test assertions about call ordering; both effects are "step 3" relative to spec D12's pre-call setup ordering. Calling `notifier.EnterErrorMode` synchronously (not in a spawned goroutine) is the spec D12 + edge-case-explorer EC2/EC3 commitment — the state bit must be set before the call begins, otherwise the stop signal from the operator's resolution intent has no state to flip and the timer never stops.
- **Evidence:** R1 — `behavioral-analyst` B4 + `software-architect` A6 + `concurrency-analyst` C2 (three-specialist convergence on the sequential-statements approach). Spec [D12](../decision-log.md#d12-error-mode-effects-are-ordered-footer-broadcast-state-bit-and-timer-notification-call) (ordering commitment). [Phase 4 D-2](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-2-error-mode-marker-fires-by-augmenting-the-existing-onmodechange-closure-in-place-reading-from-a-cached-step-name) (augment-in-place precedent). Phase 4 RAID [R3](../../phase-4-sidebar-mirroring/feature-implementation-plan.md#risks) (slice-of-hooks reopen trigger — not met by Phase 5).
- **Rejected alternatives:**

### PD-7: Two new `IntentType` values make spec D5 implementable in cmux mode

- **Question:** spec [D5](../decision-log.md#d5-resolution-of-the-error-prompt-stops-re-fire-immediately) commits the re-fire timer to stop on the **first quit keystroke** (`q`), not on the `y` confirmation. In cmux mode the footer pane handles `q`/`y` quit-confirmation locally and emits `IntentQuit` only after `y` confirms (verified at `src/cmd/pr9k/cmux_footer_machine.go:94-113`). The orchestrator never sees the first `q` keystroke or the cancelled-quit transition. How is spec D5's first-keystroke timer-stop implementable in cmux mode without narrowing the spec?
- **Decision:** extend `internal/interactionchannel` with two new `IntentType` values (working names — final naming below):
  - `IntentErrorQuitInitiated` — emitted by the footer pane when `q` is pressed in `ModeError`, **before** the state transition to `ModeQuitConfirm`. Carries the timer-stop signal.
  - `IntentErrorQuitCancelled` — emitted by the footer pane when `n` or `esc` is pressed in `ModeQuitConfirm` and the previous mode was `ModeError`. Carries the timer-restart signal.

  The footer state machine in `cmux_footer_machine.go` emits the first intent in `handleError` when `q` is pressed (line 94+ area); emits the second intent in `handleQuitConfirm` when `n`/`esc` is processed and the prior mode was `ModeError`. The orchestrator's `keyAdapterLoop` (in `cmux_workflow.go`) gains two new branches: `IntentErrorQuitInitiated → notifier.ExitErrorMode()`; `IntentErrorQuitCancelled → notifier.RestartErrorModeTimer(ctx)`. For `c` (continue) and `r` (retry) in `ModeError`, the existing `IntentContinue` and `IntentRetry` intents already fire at the first keystroke; the `keyAdapterLoop` is augmented to call `notifier.ExitErrorMode()` on those as well.

  **Final naming:** the working names from the user's OQ-1 question were `IntentResolutionStarted` / `IntentResolutionCancelled`. This plan names them `IntentErrorQuitInitiated` and `IntentErrorQuitCancelled` to narrow the semantic scope — the names explicitly identify the error-mode quit path, distinguishing them from the generic `IntentQuit` (which carries `y`-confirmed quit) and from continue/retry resolution intents. Spec D5 remains the behavioral commitment; no spec narrowing.
- **Rationale:** the user-selected mechanic (OQ-1 Option 2) extends the IPC contract additively to preserve spec D5 verbatim, rather than narrowing the spec to "stops on `IntentQuit`" (the alternative `concurrency-analyst` C6 surfaced and `behavioral-analyst` B11 contradicted). Two specialists disagreed in R1 (C6 vs. B11); the disputed claim was settled by evidence (footer state machine code at `cmux_footer_machine.go:94-113`) confirming C6's reading; user input on OQ-1 selected Option 2 to keep the spec behavior intact. Per `docs/coding-standards/versioning.md`, the IPC protocol is internal to one process tree and not part of pr9k's public API surface, so the contract change is mechanically additive (new intent types; existing intents unchanged) and does not require a CLI / config schema bump beyond the patch level. Narrower naming (`ErrorQuitInitiated` / `ErrorQuitCancelled` rather than `ResolutionStarted` / `ResolutionCancelled`) reflects the actual emit conditions and distinguishes from continue/retry intents, which also resolve the error mode but flow through existing channels.
- **Evidence:**
  - User input on 2026-05-21 selecting Option 2 (IPC extension) over Option 1 (spec narrowing) — see [iteration history R2](implementation-iteration-history.md#oq-1--resolved-user-input-2026-05-21).
  - Verified code at `src/cmd/pr9k/cmux_footer_machine.go:94-113` (footer state machine routes `q` from `ModeError` to `ModeQuitConfirm` locally, emits `RecordIntent(IntentQuit)` only on `y` confirmation or restores prior mode on `n`/`esc`).
  - Verified code at `src/cmd/pr9k/cmux_workflow.go:215-253` (`keyAdapterLoop` only receives `IntentQuit`, never `q` directly).
  - R1 disputed claim resolution (`concurrency-analyst` C6 verified correct; `behavioral-analyst` B11 retracted).
  - Spec [D5](../decision-log.md#d5-resolution-of-the-error-prompt-stops-re-fire-immediately) (first-keystroke timer-stop + cancelled-quit timer-restart).
  - `docs/coding-standards/versioning.md` (the IPC protocol is internal; additive changes do not bump semver).
- **Rejected alternatives:**
  - **Narrow spec D5 to "timer stops on `IntentQuit` (after `y`)"** — rejected (user input on OQ-1 selected Option 2); would change operator-observable behavior (the operator who started to quit then changed their mind would never get a re-fire, contradicting spec D5's cancelled-quit restart commitment).
  - **Have the orchestrator poll the footer pane's internal state via a new query intent** — rejected (race-prone, complex); the additive emit-on-transition pattern is the simpler-correct mechanism.
  - **Add the timer-stop semantics to `IntentQuit` (with a payload field "from-error-mode")** — rejected; widens the semantic load on a heavily-used existing intent; the typed-intent pattern in `interactionchannel` prefers distinct values to overloaded ones.
  - **Working names `IntentResolutionStarted` / `IntentResolutionCancelled`** — rejected (broader than the actual emit conditions); the names should reflect the specific footer-state transitions they signal, not all resolutions (continue and retry also resolve the error mode).
- **Specialist owner:** `concurrency-analyst` (for the goroutine routing) + `software-architect` (for the IPC extension shape).
- **Revisit criterion:** reopen if a future phase needs the orchestrator to react to non-error-mode quit cancellations (e.g., a quit from `ModeNormal` is cancelled and some state must be restored) — at that point a generic `IntentQuitCancelled` may supersede the error-mode-scoped variant; until then the narrower scope is preferred.
- **Dissent (if any):** `behavioral-analyst` B11 originally assumed the orchestrator's `OnModeChange` saw `ModeQuitConfirm → ModeError` transitions; this was retracted in R1 after the footer-machine code reading. The decision proceeded without dissent after evidence resolved the disagreement.

### PD-9: Terminal notifications fire inside `runCmuxWorkflowAdapted` between `workflow.Run` returning and `sidebar.ClearAll`

- **Question:** spec [D11](../decision-log.md#d11-run-aborted-and-completion-notifications-fire-before-workspaceclose-while-the-workspace-handle-is-still-valid) commits completion + run-aborted notifications to fire before `WorkspaceClose`. Two natural call sites: (a) inside `runCmuxWorkflowAdapted` immediately after `workflow.Run` returns, with branching on `ExitReason`; (b) outside `runCmuxWorkflowAdapted` in `RunPhase1`'s teardown path. Which site, and where in the existing sequence does the call land?
- **Decision:** the terminal notification fires **inside `runCmuxWorkflowAdapted`, between `workflow.Run` returning and `sidebar.ClearAll(ctx)` running**. The mapping from `workflow.RunResult.ExitReason` to notification class is an explicit `switch` block at that site per [PD-8](#trivial-decisions): `Completed → FireCompletion`, `LoopBroken → FireCompletion`, `UserQuit → FireRunAborted`. `notifier.ExitErrorMode()` is called immediately before `FireRunAborted` on the `UserQuit` branch to ensure the re-fire timer is stopped before the abort path issues the run-aborted notification (per [PD-10](#pd-10-the-re-fire-timer-is-stopped-before-the-abort-path-issues-firerunaborted)). The notification fires before `sidebar.ClearAll(ctx)` so spec D11 is satisfied (the workspace handle is still valid, and the sidebar clear remains the user-visible "run-end" signal that arrives after the notification).
- **Rationale:** keeping the firing site inside `runCmuxWorkflowAdapted` matches Phase 4's pattern of inner-function cleanup ([Phase 4 D-6](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-6-cleanup-ordering--sidebarclearallctx-runs-in-runcmuxworkflowadapted-immediately-after-workflowrun-returns-using-the-parent-context)) — the function that knows the workflow's exit reason is the function that fires the matching notification. The relative ordering "notification then `ClearAll`" is structurally cleaner than the reverse: an operator activating the notification arrives at a workspace whose sidebar still shows the run state (which then clears moments later), preserving the "interrupt the operator while context still exists" UX intent of spec D11.
- **Evidence:** R1 — `behavioral-analyst` B2 + `software-architect` A6 (two-specialist convergence on the inside-`runCmuxWorkflowAdapted` site). [Phase 4 D-6](../../phase-4-sidebar-mirroring/artifacts/implementation-decision-log.md#d-6-cleanup-ordering--sidebarclearallctx-runs-in-runcmuxworkflowadapted-immediately-after-workflowrun-returns-using-the-parent-context) precedent. ### PD-10: The re-fire timer is stopped BEFORE the abort path issues `FireRunAborted`

- **Question:** spec [D10](../decision-log.md#d10-abort-path-notification-calls-treat-every-failure-including-timeout-as-non-fatal-explicit-exception-to-parent-d15) treats `FireRunAborted`'s call as non-fatal even on timeout. If the re-fire timer is still running when `FireRunAborted` is issued, it could produce a re-fire call mid-abort (which would also be treated as abort-path under broad readings of D10). What ordering prevents the timer from firing during shutdown?
- **Decision:** in the `UserQuit` branch of the `runCmuxWorkflowAdapted` return-site switch (PD-9), `notifier.ExitErrorMode()` is called **before** `notifier.FireRunAborted(ctx)`. `ExitErrorMode` is idempotent on inactive state (returns immediately if `errorActive` is false). The ordering guarantees that no re-fire call is in flight when the abort path's `FireRunAborted` call is issued, eliminating the structural race that would otherwise let a re-fire call collide with the abort sequence. The narrow reading of "abort-path call" (per PD-16) means only `FireRunAborted` itself is abort-path; the early `ExitErrorMode` ensures that classification is unambiguous.
- **Rationale:** without this ordering, two race conditions emerge: (1) a re-fire call issued microseconds before `ExitErrorMode` could classify under broad readings of D10 as abort-path (since the abort path is already underway), silently swallowing what should be a logged failure; (2) the `resolved` channel coordination between the timer goroutine and the abort path becomes ambiguous (the timer might check `resolved` after `cancelRefire` ran but before `FireRunAborted` started, producing a behaviorally-correct but mechanically-confusing trace). Calling `ExitErrorMode` first cleanly separates the two phases: the timer is stopped (and any in-flight call is moved into post-resolution-non-fatal territory per PD-12); then `FireRunAborted` issues exactly one call that is the only abort-path call.
- **Evidence:** R1 — `behavioral-analyst` B6 (timer must be stopped before the abort path issues `FireRunAborted`); `software-architect` A7 (narrow reading of "abort-path" per PD-16); `concurrency-analyst` C2 (synchronous ordering of state changes inside the orchestrator goroutine). Spec [D10](../decision-log.md#d10-abort-path-notification-calls-treat-every-failure-including-timeout-as-non-fatal-explicit-exception-to-parent-d15) (abort-path scope). Spec [D16](../decision-log.md#trivial-decisions) (post-resolution-non-fatal). Verified code: `src/cmd/pr9k/cmux_workflow.go` (the existing teardown sequence Phase 5 extends).
- **Rejected alternatives:**
  - **Stop the timer after `FireRunAborted` returns** — rejected; produces the race conditions described in Rationale.
  - **Treat any cmux call after the abort decision is taken as abort-path** (broader reading of D10) — rejected by PD-16; broader readings risk silently swallowing late-stage failures that should be logged.
  - **Synchronize via a shared "abort-active" flag the timer goroutine checks** — rejected (race-prone); the existing `cancelRefire` mechanism is the idiomatic Go pattern and does not require a second flag.
- **Specialist owner:** `behavioral-analyst`.
- **Revisit criterion:** reopen if Phase 6 introduces additional abort-path cmux calls (e.g., a display-loss handler that itself fires multiple cmux RPCs) — at that point the abort-path scope and the per-call non-fatal exception list may need explicit enumeration.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** PD-12, PD-16
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, Runtime Behavior — Error paths), Decomposition and Sequencing (W4), Definition of Done

### PD-12: In-flight call after resolution is treated as non-fatal via a `resolved` channel

- **Question:** spec [D16](../decision-log.md#trivial-decisions) commits the outcome of an in-flight notification call that lands after the operator answered the prompt to be non-fatal regardless of result (success, non-timeout error, or timeout). What mechanism realizes this commitment given that the cmux `RealClient` queue is single-goroutine sequential and the timer goroutine may have a call mid-flight when the operator's resolution intent arrives?
- **Decision:** each error-mode session allocates a `resolved chan struct{}` on `cmuxNotifier` at `EnterErrorMode` entry. The resolution path (`ExitErrorMode`) closes the channel synchronously, before the timer goroutine is cancelled. The timer goroutine, after its `WorkspaceNotify` call returns, executes:

```go
select {
case <-resolved:
    // resolution happened during our call; treat outcome as non-fatal regardless of err
    if err != nil { log.Log("cmuxNotifier", fmt.Sprintf("re-fire after resolution: %v", err)) }
    return
default:
    // normal classification: timeout = fatal, non-timeout = log-and-continue
    classify(err)
}
```

A fresh `resolved` channel is allocated on every `EnterErrorMode` (including `RestartErrorModeTimer` after a cancelled quit), captured into the timer goroutine's local scope at session start so a stale-session call cannot collide with a fresh-session channel (the [RAID R5](../feature-implementation-plan.md#risks) concern).
- **Rationale:** the `resolved` channel is the idiomatic Go signal for "I no longer care about this call's outcome." Closing the channel rather than sending on it is the standards-prescribed pattern (`docs/coding-standards/concurrency.md` — non-blocking channel sends); multiple consumers can observe the close. Capturing `resolved` into the goroutine's local variable at session start defends against the RAID R5 stale-session collision: if the timer goroutine from session A is in flight when session B starts (because the operator answered session A's prompt, continued the workflow, and a later step entered session B), session A's goroutine sees session A's closed channel and treats its outcome non-fatal, while session B's fresh goroutine has session B's fresh channel.
- **Evidence:** R1 — `behavioral-analyst` B8 (`resolved chan struct{}` closed on first-keystroke resolution; `select { case <-resolved: ... default: ... }` after the call returns). `docs/coding-standards/concurrency.md` (non-blocking channel sends; closeable idempotency). Spec [D16](../decision-log.md#trivial-decisions) (post-resolution non-fatal commitment). Spec [D5](../decision-log.md#d5-resolution-of-the-error-prompt-stops-re-fire-immediately) (operator may see at most one additional notification if a call was mid-flight at the stop moment).
- **Rejected alternatives:**
  - **Synchronize via a `sync.Mutex`-protected boolean `resolved bool`** — rejected; the timer goroutine would need to hold the lock for the entire RPC duration (5+ seconds under load) or release-and-reacquire (introducing a TOCTOU window).
  - **Send on the channel instead of closing** — rejected; only one consumer per send, so additional goroutines (e.g., a future Phase 6 abort handler) could not observe the resolution signal.
  - **Abort the in-flight call at the resolution moment** — explicitly rejected by spec [D5](../decision-log.md#d5-resolution-of-the-error-prompt-stops-re-fire-immediately) ("Abort any in-flight notification RPC at the stop moment — rejected; risks half-applied state on cmux's side for no operator-visible benefit").
- **Specialist owner:** `concurrency-analyst`.
- **Revisit criterion:** reopen if cmux supports a cancellation primitive on its notification surface (currently it does not) — at that point the in-flight-call tolerance pattern may simplify to "cancel and discard" rather than "let it finish and ignore."
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** —
- **Referenced in plan:** Outcome, Implementation Approach (Runtime Behavior — Error paths), Decomposition and Sequencing (W4), RAID Log (Risks R5), Definition of Done

### PD-13: `cmuxSidebar` gains a `LastStepName()` accessor

- **Question:** spec [D13](../decision-log.md#d13-step-name-is-snapshotted-at-error-mode-entry-not-recomputed-at-each-re-fire) commits the failing step name to be snapshotted at error-mode entry, not recomputed at each re-fire. The candidate source is `cmuxSidebar.lastStepName` (existing Phase 4 field). How does `cmuxNotifier.EnterErrorMode` access it?
- **Decision:** `cmuxSidebar` gains a new exported method:

```go
func (s *cmuxSidebar) LastStepName() string {
    s.mu.Lock(); defer s.mu.Unlock()
    return s.lastStepName
}
```

`cmuxNotifier.EnterErrorMode` reads via `sidebar.LastStepName()` at error-mode entry, captures into `cmuxNotifier.snapshotName`, and reuses across every 60-second re-fire of the same session. A subsequent error-mode session (after the operator answers the first with continue/retry) calls `LastStepName()` again at that fresh entry, snapshots that fresh value, and uses it across the second session's re-fires.
- **Rationale:** snapshot-then-unlock per `docs/coding-standards/concurrency.md` — the accessor reads under the existing sidebar mutex without holding the lock for the entire snapshot duration; the snapshot itself lives on `cmuxNotifier`'s mutex once captured. Spec D13's edge-case-explorer EC4 concern (the field is mutable across step transitions; recomputing at each re-fire exposes the spec to future code paths that mutate the field outside the normal step-transition flow) is addressed by snapshotting once at entry. A new exported accessor (rather than direct field access) keeps `cmuxNotifier` decoupled from `cmuxSidebar`'s internal mutex.
- **Evidence:** R1 — `software-architect` A6 + `behavioral-analyst` B9 (two-specialist convergence on the accessor pattern). Spec [D13](../decision-log.md#d13-step-name-is-snapshotted-at-error-mode-entry-not-recomputed-at-each-re-fire) (snapshot-at-entry). [Spec-stage EC4](../artifacts/team-findings.md#f9-step-name-was-mutable-across-re-fires) (`cmuxSidebar.lastStepName` mutability concern). `docs/coding-standards/concurrency.md` (snapshot-then-unlock).
- **Rejected alternatives:**
  - **Direct field access from `cmuxNotifier`** — rejected; couples the two structs to each other's mutex and violates encapsulation.
  - **Recompute at each re-fire** — rejected per spec D13 (mutation hazard).
  - **Push the step name into `cmuxNotifier` from the `OnModeChange` callback site** — rejected; the callback signature does not carry the step name, and threading it through would require either widening the callback signature (LSP/ISP concern from Phase 4 D-2) or capturing it from a closed-over variable (race-prone if multiple step transitions could occur between captures).
- **Specialist owner:** `software-architect`.
- **Revisit criterion:** reopen if a future phase introduces a step-name source other than `cmuxSidebar` (e.g., a separate run-state-cache adapter), at which point the accessor pattern may need to move to a shared interface.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
