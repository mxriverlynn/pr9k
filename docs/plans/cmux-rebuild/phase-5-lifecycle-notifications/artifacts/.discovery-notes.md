## Touch Points (code the implementation will extend)

### `src/internal/cmuxctl/` — cmux v2 RPC surface

- **`client.go`** — `CmuxClient` interface. Currently has 12 RPC methods (SystemIdentify, WorkspaceCurrent, WorkspaceList, WorkspaceCreate, WorkspaceClose, WorkspaceSelect, SurfaceSplit, SurfaceList, WorkspaceSetStatus, WorkspaceClearStatus, WorkspaceSetProgress, WorkspaceClearProgress). **There is no notification method today.** The build outline (Phase 5 section, line 269) names the verified cmux v2 notification surface at commit `2f96c15c2` as: `notification.create`, `notification.create_for_caller`, `notification.create_for_surface`, `notification.create_for_target`, `notification.dismiss`, `notification.list`. Phase 5 must pin which of these targets the pr9k workspace (current spec wording says "the workspace handle is the target" — strongly indicating `notification.create_for_target` if cmux accepts a workspace UUID/ref as the target type, or one of the other variants if not). **This pinning must be verified against the cmux source at the pinned commit before the wire call is committed (parent D-R2 precedent).**
- **`real.go`** — `RealClient` is a single-goroutine sequential queue. **Per-call timeout: `DefaultTimeout = 8 * time.Second`** (line 16). The queue serializes all calls — concurrent notification calls do not race with each other or with sidebar calls; they queue.
  - Timeout semantics: when a call times out, `disconnect()` is called and the call returns `cmuxctl: <method> timed out after <duration>`. This is the timeout error string Phase 5's classifier will need to detect to apply [D7](feature-specification.md) (non-timeout = log-and-continue) vs. [D10](feature-specification.md) (abort-path call = log-and-continue even on timeout).
  - Error types returned: `*PlaintextError` (plaintext "ERROR: …" line from cmux), `*CmuxError` (structured `{ok:false,error:{code,message}}` envelope), and ordinary wrapped errors (read/write/dial). Timeout errors are currently a plain `fmt.Errorf` — there is **no typed timeout error** today; if Phase 5 needs to distinguish timeouts from other failures programmatically, the simplest path is a new typed error or an exported sentinel. The current `errors.Is` / `errors.As` taxonomy in this package does not yet have one for timeouts.
- **`fake.go`** — `FakeClient` test double. Every existing method has a hand-written fake (counters, recorder slices, configurable `Func` overrides). Phase 5 adds at least one new fake method (the notification call).
- **`preflight.go`** — Phase 1's startup capability check. **`Preflight()` is identify-only:** a successful `SystemIdentify` with a non-empty `socket_path` is the entire capability proof. There is no per-method enumeration. The Phase 5 spec (D8) says the check is "extended to cover Phase 5's notification methods" — same gap noted in Phase 4 discovery. Spec language ("the same actionable, method-named error parent D18 produces") implies an enumeration, but cmux v2 has no `system.capabilities` enumeration call (parent build outline). **This is a clarifying question the implementation team must settle.**
- **`runphase1.go`** — Phase 1 lifecycle. Owns the workspace handle the notification calls target. The workspace handle is threaded into the orchestrator via `runCmuxOrchestratorWith(ctx, socketPath, projectDir, ackTimeout, ch, client, ws)` (Phase 4 work).

### `src/cmd/pr9k/cmux_workflow.go` — orchestrator-side composition

- **`runCmuxWorkflowAdapted`** — composes the cmux-mode adapters: `runner.SetSender` for log fan-out, `cmuxHeader` for header, `keyHandler.SetOnModeChange` for footer mode pushes + sidebar error-mode marker (Phase 4), key-adapter goroutine for intent forwarding. Phase 5's notification firing site for **error-mode** is exactly this closure — when `mode == ui.ModeError`, the current code calls `sidebar.EnterErrorMode(ctx)`. Phase 5 must (a) capture the failing step name at this moment ([Phase 5 D13](../feature-specification.md): snapshot at entry, not recomputed on re-fire), and (b) start the re-fire timer and fire the initial notification. The spec ([D12](../feature-specification.md)) commits to a specific ordering: footer-broadcast (already first in this closure) → state-bit + timer-start → notification call.
- **`runCmuxWorkflowAdapted` return path** — returns `int` exit code (0 = completed/loop-broken, 1 = user-quit). This is the **completion vs. abort** signal for Phase 5. The current return-site is the natural place to wire the **completion** notification (on `ExitReasonCompleted` / `ExitReasonLoopBroken`) and the **run-aborted** notification (on `ExitReasonUserQuit` plus any future Phase-6 abort paths).
- **`keyHandler.SetOnModeChange(fn func(Mode, string))`** — Phase 3's extension point. Phase 4 augmented the closure in place (D-2 of Phase 4) rather than calling `SetOnModeChange` twice (which would overwrite). Phase 5 can chain again into the same closure (the same pattern), or refactor the closure into a list-of-hooks if a third effect makes the closure unwieldy.

### `src/cmd/pr9k/cmux_pane.go` — orchestrator pane entry point

- **`runCmuxOrchestratorWith(ctx, socketPath, projectDir, ackTimeout, ch, client, ws)`** — the testable core of the orchestrator pane. The shutdown sequence is:
  1. `runCmuxWorkflowAdapted(...)` returns `exitCode int`.
  2. `ch.Send(interactionchannel.WorkspaceDone{ExitCode: exitCode})` broadcasts to all three display panes.
  3. `awaitDoneAcks(ch.Recv(), ackTimeout)` waits up to `workspaceDoneAckTimeout` for the three ack messages.
  4. Returns to the caller, which closes the workspace.
- **The workspace is NOT closed inside `runCmuxOrchestratorWith`.** The Phase 5 spec ([D11](feature-specification.md)) requires the completion / run-aborted notifications fire "before the workspace is closed." Look up the chain: in production, `cmuxctl.RunPhase1` calls `runCmuxOrchestratorWith` (or its sibling), then on the deferred teardown path issues `WorkspaceClose`. The notification call must land before that close. The natural insertion point is *inside* `runCmuxOrchestratorWith`, between the `runCmuxWorkflowAdapted` return and the `WorkspaceDone` broadcast (or between the broadcast and the function return) — both are still "before close."
- **Sidebar safety-net clear (Phase 4 D-7):** `defer func() { _ = sidebar.ClearAll(context.Background()) }()` immediately after sidebar construction at line 200. Phase 5 may need a parallel mechanism for stopping the re-fire timer on panic / abort paths — a `defer cancelRefire()` next to the sidebar's cleanup is the obvious pattern.

### `src/cmd/pr9k/cmux_sidebar.go` — Phase 4 sidebar adapter (a structural precedent)

- **`cmuxSidebar` struct** — wraps `cmuxctl.CmuxClient`, `cmuxctl.Workspace`, `*logger.Logger`, plus cached state (`lastStepName`, `progressPushed`). Phase 4's spec [D13](../phase-4-sidebar-mirroring/artifacts/decision-log.md#d13-error-mode-suffixes-a-stable-marker-onto-the-status-entry-value) added `EnterErrorMode(ctx)` which mutates the sidebar pill to append `" — awaiting input"`.
- The same struct may be the right *behavioral* peer to a `cmuxNotifier` Phase 5 adds — or Phase 5 may extend `cmuxSidebar` itself if the notification call + state bit + timer all fit cleanly. **This is one of the structural questions for the team.** Phase 4's precedent argues for a *new* struct (single-responsibility); cmux's notification surface is conceptually orthogonal to its sidebar surface.
- Failure-handling pattern (precedent): `EnterErrorMode` returns nil even on RPC failure, logs `_ = s.log.Log("cmuxSidebar", fmt.Sprintf("EnterErrorMode error: %v", err))`. Phase 5's [D7](feature-specification.md) (non-timeout errors logged, run continues) and [D17](feature-specification.md) (sustained non-timeout failures acceptable) are the same shape.

### `src/internal/ui/orchestrate.go` + `src/internal/ui/ui.go` — error-mode and quit flow

- **`runStepWithErrorHandling`** in `orchestrate.go:125` — calls `header.SetStepState(idx, StepFailed)` → `h.SetMode(ModeError)` → waits on `h.Actions` → resolves with continue/retry/quit. `OnModeChange` fires twice: `ModeNormal → ModeError` on entry, `ModeError → ModeNormal` on exit (continue/retry) or `ModeError → ModeQuitConfirm → ...` on quit.
- **`KeyHandler.ForceQuit()`** — invoked by the key-adapter loop when `IntentQuit` arrives. Drives the two-step quit confirmation (`q` then `y`). Phase 5 spec [D5](feature-specification.md) says the re-fire timer stops on the *first* `q` keystroke, not the `y` confirmation. Today the `OnModeChange` fires when the mode transitions to `ModeQuitConfirm` — which is exactly the first-keystroke moment. Phase 5 can hook the timer-stop into the same `OnModeChange` closure: when `mode == ui.ModeQuitConfirm` (and the prior mode was `ModeError`), stop the timer. Cancelled confirmation transitions back to `ModeError` — Phase 5 spec [D5](feature-specification.md) commits to *restarting* the timer in that case.
- **`workflow.RunResult.ExitReason`** — values `ExitReasonCompleted`, `ExitReasonLoopBroken`, `ExitReasonUserQuit`. Phase 5 wires:
  - `Completed` or `LoopBroken` → **completion** notification.
  - `UserQuit` → **run-aborted** notification.
  - Cmux per-call timeout (currently surfaces as a `cmuxctl: ... timed out after ...` error returned from any RPC call in the orchestrator path) → triggers an abort path per parent D15. **Today the orchestrator does not yet handle this systematically** — parent D15 is committed but the abort routing is Phase 6 scope; Phase 5's spec ([D7](feature-specification.md)) commits the behavior, and the team should confirm whether the wiring lands in Phase 5 or in Phase 6 to keep scope honest.

## Gaps and open questions surfaced during discovery

These are surfaced for the team to settle in Round 1 — they are not pre-decided here.

1. **Capability check shape (spec D8).** Spec D8 says the Phase 1 capability check is "extended to cover Phase 5's notification methods." The current `Preflight()` is identify-only; there is no per-method enumeration today. cmux v2 has no `system.capabilities` enumeration RPC. The team must pick a mechanism: (a) probe each method with a benign no-op call at startup, (b) leave the check identify-only and treat the first failed call at runtime as the discovery mechanism (already what D7 commits to for runtime, but D8 asks for a startup gate), or (c) accept that the check is best-effort and document the gap.
2. **Which `notification.*` method targets the pr9k workspace?** Build outline lists six candidates (`notification.create`, `create_for_caller`, `create_for_surface`, `create_for_target`, `dismiss`, `list`). Spec D1 says "target the workspace by its cmux workspace handle." `create_for_target` is the obvious candidate if its `target` accepts a workspace UUID/ref; otherwise `create_for_caller` (the orchestrator pane's surface is in the workspace) may suffice if cmux's "activate notification → focus workspace" behavior is the same. **This MUST be verified against cmux source at commit `2f96c15c2` before the wire call is committed (parent D-R2 precedent).**
3. **Timeout error detection.** `RealClient` returns timeout errors as plain `fmt.Errorf("cmuxctl: %s timed out after %s", ...)` — no typed sentinel. Phase 5 needs to detect "this error was a timeout" to apply spec [D7](feature-specification.md) (non-timeout: log-and-continue) vs. parent D15 (timeout: fatal) vs. spec [D10](feature-specification.md) (abort-path call timeout: log-and-continue). The team must settle: introduce a typed `*TimeoutError`, an exported sentinel `ErrCmuxTimeout`, or string-match. Typed error is the cleanest and matches Phase 4's `*PlaintextError` / `*CmuxError` precedent.
4. **Re-fire timer mechanism.** A `time.Ticker` per error-mode entry is the natural shape; the orchestrator already holds a `ctx` and the existing key-adapter goroutine. A new goroutine that selects on `ticker.C`, `stopChan`, and `ctx.Done()` is the obvious model. The team should pin: where the goroutine lives (cmuxNotifier struct? inside the OnModeChange closure?), how stop is signalled (close a channel? cancel a sub-context?), and how an in-flight notification call's completion-after-stop is handled to satisfy spec [D16](feature-specification.md) (in-flight call completing after answer is non-fatal regardless of outcome).
5. **Run-aborted notification fires from where?** Spec [D11](feature-specification.md) says "before WorkspaceClose, while the handle is valid." Two natural sites: (a) inside `runCmuxOrchestratorWith` just after `runCmuxWorkflowAdapted` returns, with branching on `exitCode`; (b) outside `runCmuxOrchestratorWith` in `RunPhase1`'s teardown path. Phase 4's sidebar `ClearAll` lives in the inner function (a-pattern) — Phase 5 should follow the same pattern unless there's a reason not to.
6. **What does "abort-path call" mean operationally for spec [D10](feature-specification.md)?** D10 says abort-path notification calls treat every failure (including timeout) as non-fatal. The team must define which calls are "abort-path": (a) only the run-aborted notification call itself, (b) any cmux call made after the abort decision is taken, (c) any cmux call made during shutdown regardless of cause. The natural narrow reading is (a) — the run-aborted notification call — plus any explicit shutdown calls Phase 6 adds; broader readings risk silently swallowing late-stage failures.
