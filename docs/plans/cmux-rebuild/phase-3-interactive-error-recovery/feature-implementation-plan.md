# Feature Implementation Plan: Phase 3 — Interactive Error Recovery

Phase 3 makes a failing workflow step in cmux mode interactively recoverable from inside the workspace. **This plan is honest about scope: the Phase 3 spec presumes a running Phase 2 cmux workflow, but Phase 2's end-to-end integration was never wired — the components are unit-tested in isolation, not connected into any running pane process.** This plan therefore *absorbs the Phase 2 happy-path wiring as foundational work* and then layers error recovery on top ([D-1](artifacts/implementation-decision-log.md#d-1-absorb-the-phase-2-end-to-end-integration-into-the-phase-3-plan-as-foundational-work)). The implementation posture is **two ordered slices in a single combined delivery**: slice 1 wires the happy path (closing the Phase 2 gap, demoable alone), slice 2 verifies error recovery; both ship together with the version bump `0.11.0 → 0.12.0` and the doc updates ([D-2](artifacts/implementation-decision-log.md#d-2-work-unit-decomposition-and-sequencing--happy-path-wiring-slice-precedes-error-recovery-slice), [D-11](artifacts/implementation-decision-log.md#d-11-absorb-the-version-bump-0110--0120-and-the-feature-doc--how-to-updates-into-this-delivery)).

When operators run `pr9k --cmux --project-dir <repo>` from inside a cmux session against a project with a real workflow, they observe: the workspace appears and the four panes connect (Phase 1/2 lifecycle), a real workflow runs end-to-end with the header ticking and the log streaming (the Phase 2 deliverable, *now actually wired*), and — when a step exits non-zero in a way that triggers the existing error mode — the header marks the step `[✗]`, the log shows the error output, the footer switches to the continue / retry / quit prompt, and the operator resolves it from the footer pane with exactly the standard-display semantics (continue / retry-with-separator-first / two-step-quit-confirm / cancel-restores-prompt / no auto-timeout / no retry cap). Control keys pressed on the header or log pane are absorbed silently.

## Context

- **Driving constraint:** Phase 2's titular deliverable ("First Real Workflow Runs End-to-End in Cmux") is **not present in running code** — the orchestrator pane stubs `workflow.Run`, the footer state machine and key adapter have zero non-test callers, and the header/log panes ignore pushed state ([.discovery-notes.md](artifacts/.discovery-notes.md) CRITICAL FINDING; verified at `src/cmd/pr9k/cmux_pane.go:113-114`, `:164-193`, and `src/cmd/pr9k/cmux_footer_renderer.go:22-25`). Without this plan, `--cmux` runs an empty four-pane scaffold and a single failing step strands the operator with no recovery. This plan is the smallest slice that delivers a *working, recoverable* cmux run.
- **Stakeholders:**
  - **Operators running pr9k in cmux mode** — care that a failing step is recoverable from inside the workspace with the same muscle memory as the standard display, and that the cmux run actually produces the same workflow behavior and on-disk artifacts.
  - **pr9k maintainers (River + collaborators)** — care that the Phase 2 integration gap is closed honestly (not silently absorbed without acknowledgement), that the shared `Orchestrate` loop is reused unchanged per the narrow-reading ADR, and that the interaction-channel protocol is unchanged so Phase 4/5/6 extend without rework.
  - **Build-phase sequencing** — Phase 4 (sidebar) and Phase 5 (notification) depend on a working error-mode path existing; this plan unblocks them.
- **Future-state concern:** the absorbed wiring adds code volume, not new subsystems; the future-state concerns are inherited from Phase 2 (per-connection goroutine count grows as Phase 4 adds consumers; T4 cross-pane drift budget honored by topology not measurement; protocol skew between phases handled by the JSON `type` discriminator). The new watch item is that the once-stubbed orchestrator path is now the cmux run's critical path — a regression there breaks every subsequent phase.
- **Out-of-scope boundary:** error-mode cmux notification (Phase 5); sidebar failure label (Phase 4); generalized failure handling — display-pane loss, orchestrator loss, channel stalls, hung cmux calls during error mode (Phase 6, unchanged from Phase 2); any change to existing error-mode semantics (continue/retry/quit set, no auto-timeout, no retry cap, retry mechanics, the conditions that do *not* enter error mode); keyboard-driven log selection (`v` mode dropped in cmux per parent D20); `pr9k workflow` builder (run loop only); live-cmux CI integration test (deferred to Phase 6 per OI-1).

## Implementation Approach

This plan **finishes Phase 2's end-to-end integration and then adds error recovery on top** — it does not "thinly add" an error prompt to a working run, because the working run does not exist in cmux process code ([D-1](artifacts/implementation-decision-log.md#d-1-absorb-the-phase-2-end-to-end-integration-into-the-phase-3-plan-as-foundational-work)). The error path is not separable: the *same* `runStepWithErrorHandling` function in `src/internal/ui/orchestrate.go` both completes steps and enters `ModeError`, so wiring the orchestrator to `workflow.Run` necessarily activates the error path — this is why error recovery is absorbed into the same plan rather than tracked as a thin follow-on.

### Architecture and Integration Points

- **Shared `internal/ui` reuse, unchanged (narrow-reading ADR).** The cmux orchestrator pane runs the *same* `internal/ui` machinery the standard path runs: `workflow.Run(executor, header, keyHandler, cfg)`, the shared `Orchestrate` loop, the `StatusHeader` renderer, and `RetryStepSeparator`. No Ralph-specific or cmux-specific recovery logic is added to Go code ([D-9](artifacts/implementation-decision-log.md#trivial-decisions); `docs/adr/20260410170952-narrow-reading-principle.md`). Spec D1–D4 are delivered by *surfacing* this code through the panes, not reimplementing it.
- **`orchChannel` interface expanded in place.** `orchChannel` (`src/cmd/pr9k/cmux_pane.go:27-32`) currently exposes only `AwaitReady`/`Send`/`Recv`/`Close`. It gains `SendStateHeader` / `SendStateLog` / `SendStateFooter`. No new richer interface type is introduced — single concrete need, single production implementation, and `FakeInteractionChannel` already implements the methods (Phase 2 U10) ([D-3](artifacts/implementation-decision-log.md#d-3-expand-the-existing-orchchannel-interface-in-place-rather-than-introduce-a-new-richer-interface)).
- **Adapters between `internal/ui` and the interaction channel.** The orchestrator constructs: a `RunHeader` adapter whose `SetStepState` pushes `StateHeader`; a `StepExecutor`/`Runner` whose `SetSender`-drained log lines push `StateLog`; a `KeyHandler` whose `SetOnModeChange` pushes `StateFooter` and whose `Actions` channel receives footer intents via `newKeyHandlerAdapter`. These adapter types follow `docs/coding-standards/api-design.md` (compile-time interface assertions, adapter types).
- **Footer pane drives from the wired path only.** The footer pane runs the Phase 2 `footerStateMachine` + `newKeyHandlerAdapter` (zero non-test callers today) connected to the interaction channel. The footer renderer's private isolated `KeyHandler` and unread `actions` channel (`src/cmd/pr9k/cmux_footer_renderer.go:22-25`) are removed; the renderer keeps only display responsibilities (size, `?`/`esc` help-expand). The orchestrator reuses the *same* `actions` channel passed to `workflow.Run`, not an isolated one ([D-7](artifacts/implementation-decision-log.md#d-7-remove-the-footer-renderers-isolated-keyhandleractions-channel-drive-the-footer-from-the-wired-path)).
- **No new transport, no new message kinds, no new cmux calls.** Phase 3 reuses the Phase 2 `interactionchannel` package and its `StateHeader`/`StateLog`/`StateFooter`/`Intent`/`WorkspaceDone` set verbatim ([D-10](artifacts/implementation-decision-log.md#trivial-decisions); spec [Coordinations](feature-specification.md#coordinations)).

### Data Model and Persistence

No schema changes, no migrations. The orchestrator pane already creates the per-run logger and artifact directory (`logger.NewLogger(projectDir)` + `<projectDir>/.pr9k/logs/<run-stamp>/` — verified present at `cmux_pane.go` `runCmuxOrchestratorWith`); once `workflow.Run` is wired, the same per-run log file and per-step JSONL artifacts the standard path produces are written, unchanged. Phase 3 introduces no new on-disk artifacts (spec [Coordinations](feature-specification.md#coordinations); parent D17). The interaction-channel socket is the ephemeral Phase 2 socket, unchanged.

### Runtime Behavior

- **Launch and wiring (slice 1).** The orchestrator pane: creates the logger + artifact dir (already wired), `Serve`s the channel and `AwaitReady` (already wired), then — replacing the stub — establishes the `KeyHandler` (cancel = `runner.Terminate`, [D-4](artifacts/implementation-decision-log.md#d-4-construct-the-orchestrators-keyhandler-with-the-runners-terminate-as-the-cancel-function)), sets `SetOnModeChange` and starts the key-adapter goroutine **before** calling `workflow.Run` ([D-6](artifacts/implementation-decision-log.md#d-6-establish-setonmodechange--the-key-adapter-goroutine-before-workflowrun-starts-drain-the-footer-keystroke-goroutine-on-context-cancel-via-waitgroup)), then drives `workflow.Run` with the adapters, then broadcasts `WorkspaceDone` and awaits acks (already wired). Header and log panes consume `StateHeader`/`StateLog` and render. The footer pane runs the state machine + key adapter and renders `StateFooter`.
- **Error path (slice 2, activated by the same wiring).** On a non-zero step exit that triggers error mode, the shared `runStepWithErrorHandling` (`src/internal/ui/orchestrate.go:124-135`) calls `header.SetStepState(idx, StepFailed)` → header pane shows `[✗]` (spec D2); the step's error bytes stream via the log adapter → log pane shows them as ordinary content (spec D3); `h.SetMode(ModeError)` → `StateFooter(ModeError)` pushed → footer shows continue/retry/quit (spec D1). On retry, `runner.WriteToLog(RetryStepSeparator(step.Name))` (`orchestrate.go:135`) runs **before** the step re-runs; the `WriteToLog`→`SendStateLog` adapter is synchronous on the orchestrator goroutine so the separator is enqueued before any retried-step output (spec D3, [D-5](artifacts/implementation-decision-log.md#d-5-the-writetolog--sendstatelog-adapter-is-synchronous-on-the-orchestrator-goroutine)). Quit runs the inherited two-step confirmation in the footer state machine; cancel restores the error prompt (safe because the orchestrator is paused in `ModeError` for the whole excursion — spec D1). The race-window guarantee holds by design: buffered `h.Actions` (cap 10) + synchronous `onModeChange` before the `<-h.Actions` block is the `concurrency.md` "prime the channel before blocking receive" pattern ([D-6](artifacts/implementation-decision-log.md#d-6-establish-setonmodechange--the-key-adapter-goroutine-before-workflowrun-starts-drain-the-footer-keystroke-goroutine-on-context-cancel-via-waitgroup)).
- **Bounded cross-pane desync (accepted).** The header/log/footer signals converge near-simultaneously, not atomically (parent T4). The spec's accepted windows hold once wired: stale-footer just after failure; continue-before-`[✗]`. An additional cosmetic window exists — `Orchestrate` calls `h.SetMode(ModeNormal)` after `<-h.Actions` regardless of action (`orchestrate.go:128`), so on the quit path it briefly pushes `StateFooter(ModeNormal)` before `WorkspaceDone`; this is absorbed by the spec's existing bounded-desync acceptance (spec D4 / parent T4) and needs no code (RAID R4).
- **Control-key absorption (spec D4).** Header and log panes never run the footer state machine and never forward intents, so control keys on them are absorbed silently with no error/bell/notification — true once they are wired as display-only consumers; Phase 3 confirms it holds during error mode.

### External Interfaces

- **CLI:** no new flags or sub-commands. The Phase 2 `pr9k cmux-pane --role=...` sub-command and `--cmux` flag are unchanged from the operator's perspective; their behavior is *completed* (the orchestrator role now runs the workflow).
- **Interaction-channel protocol:** unchanged — no new message kinds; `orchChannel` is expanded with already-existing `interactionchannel` push methods, not new wire types ([D-3](artifacts/implementation-decision-log.md#d-3-expand-the-existing-orchchannel-interface-in-place-rather-than-introduce-a-new-richer-interface), [D-10](artifacts/implementation-decision-log.md#trivial-decisions)).
- **Cmux JSON-RPC:** no new calls; notifications and sidebar updates remain deferred to Phases 5 and 4 (spec [Coordinations](feature-specification.md#coordinations)).
- **Operator-visible output:** the cmux workspace now renders live header/log/footer state and the error-mode prompt; on-disk artifacts at `<projectDir>/.pr9k/logs/<run-stamp>/` unchanged.

## Testing Strategy

The test surface is the Phase 2 fakes (`FakeInteractionChannel`, `FakeDisplayPane`, `FakeFooterKeySource` — committed in Phase 2 U10) plus **one** round-trip integration-style test over `FakeInteractionChannel`, plus reuse of Phase 2's isolated unit tests unchanged ([D-8](artifacts/implementation-decision-log.md#d-8-one-round-trip-integration-test-over-fakeinteractionchannel-live-cmux-deferred)). Live-cmux integration is deferred to Phase 6 (spec OI-1 / parent OQ-2 / Phase 1 OI-2). This rests on behavioral-analyst's finding that the spec's load-bearing guarantees hold by design once wired (B6/B7), so the new test validates the wiring is in place rather than re-deriving the guarantees.

- **Observable behaviors to test:**
  - Slice 1 wiring: orchestrator drives `workflow.Run`; `StateHeader`/`StateLog`/`StateFooter` pushed; header renders the step grid; log streams output; footer renders normal hints (W1–W3 unit tests).
  - Failed-step header: `StateHeader` carrying `StepFailed` renders `[✗]`; a successful retry advances to `[✓]`, a re-failure stays `[✗]` (spec D2).
  - Log ordering: the retry separator (`── <step name> (retry) ─────────────`) is delivered to the log pane before any retried-step output (spec D3; synchronous adapter [D-5](artifacts/implementation-decision-log.md#d-5-the-writetolog--sendstatelog-adapter-is-synchronous-on-the-orchestrator-goroutine)).
  - Footer error mode: `StateFooter(ModeError)` renders continue/retry/quit; `q`→`y` produces one quit intent; `q`→`esc` returns to the error prompt with no intent; a non-confirmation key during quit-confirm is ignored and not buffered (spec D1).
  - Race window: a footer intent produced the instant `SetMode(ModeError)` fires is not dropped — the round-trip test exercises orchestrator `SetMode(ModeError)` → `StateFooter` → footer intent → `Orchestrate` action ([D-8](artifacts/implementation-decision-log.md#d-8-one-round-trip-integration-test-over-fakeinteractionchannel-live-cmux-deferred)); the inherited Phase 2 `TestAdapter_ModeErrorRaceWindow_NoDroppedKeystroke` is reused unchanged for the component-level guarantee.
  - Control-key absorption: keystrokes delivered to header/log panes produce no intent and no error/bell (spec D4) — header/log panes are display-only consumers with no key path.
  - Concurrency: footer-keystroke goroutine exits on context cancel (WaitGroup-drained); mode-change hook established before `workflow.Run`; race detector clean ([D-6](artifacts/implementation-decision-log.md#d-6-establish-setonmodechange--the-key-adapter-goroutine-before-workflowrun-starts-drain-the-footer-keystroke-goroutine-on-context-cancel-via-waitgroup)).
- **Test doubles posture:** reuse the three Phase 2 doubles unchanged; no new double. All `sync.Mutex`-protected per `docs/coding-standards/testing.md`.
- **Edge cases requiring coverage:** retry-fails-again loop re-enters error mode with separator re-written; cancel-quit-during-error restores the same error prompt; stale-footer and continue-before-`[✗]` bounded-desync windows are accepted (asserted as non-blocking, the on-disk artifact is authoritative); quit path's transient `StateFooter(ModeNormal)` flash (R4) is accepted.
- **Test levels:** unit (W1–W3, every component via the doubles); one integration-style round-trip test (W4, the wired composition over `FakeInteractionChannel`); end-to-end live-cmux deferred to Phase 6.
- **Race detector:** `make test` runs `go test -race ./...` per `docs/coding-standards/testing.md`. Goroutines under scrutiny: the key-adapter goroutine, the footer-keystroke goroutine (WaitGroup-drained), the per-connection fan-out goroutines, and the orchestrator goroutine running `Orchestrate`.

## Security Posture

`adversarial-security-analyst` is not engaged for Phase 3. Phase 3 crosses no new trust boundary: it reuses the Phase 2 interaction-channel socket (filesystem-permission-based under the existing `.pr9k/` 0700-mode parent), adds no new cmux JSON-RPC calls, and introduces no new externally controllable input ([D-10](artifacts/implementation-decision-log.md#trivial-decisions); spec [Coordinations](feature-specification.md#coordinations)). The error output streamed to the log pane is the same subprocess output the standard display already renders and the same bytes already written to the on-disk artifact — no new content path is introduced. ## Definition of Done

- [ ] `pr9k --cmux --project-dir <repo>` from inside a cmux session against a real-workflow repo runs the workflow end-to-end: header pane checkboxes tick over and the iteration counter advances, the log pane streams subprocess output, the footer pane shows status line + shortcuts — i.e. the Phase 2 happy-path demo, *actually wired* ([D-1](artifacts/implementation-decision-log.md#d-1-absorb-the-phase-2-end-to-end-integration-into-the-phase-3-plan-as-foundational-work), [D-2](artifacts/implementation-decision-log.md#d-2-work-unit-decomposition-and-sequencing--happy-path-wiring-slice-precedes-error-recovery-slice)).
- [ ] On a step that exits non-zero in a way that triggers the existing error mode: the header marks the step `[✗]` (spec D2), the log shows the error output as ordinary streamed content (spec D3), and the footer switches to the continue/retry/quit prompt (spec D1) — demonstrated end-to-end against a real failing step.
- [ ] Retry writes the `── <step name> (retry) ─────────────` separator to the log **before** any retried-step output (spec D3; [D-5](artifacts/implementation-decision-log.md#d-5-the-writetolog--sendstatelog-adapter-is-synchronous-on-the-orchestrator-goroutine)).
- [ ] Quit from the error prompt runs the inherited two-step confirmation; cancel restores the same error prompt; a non-confirmation key during quit-confirm is ignored and not buffered (spec D1).
- [ ] Quit during an active/error step actually terminates the running subprocess (orchestrator `KeyHandler` cancel = `runner.Terminate`, [D-4](artifacts/implementation-decision-log.md#d-4-construct-the-orchestrators-keyhandler-with-the-runners-terminate-as-the-cancel-function)).
- [ ] Control keys pressed on the header or log pane are absorbed silently — no error, no bell, no notification (spec D4).
- [ ] Bounded-desync acceptances hold (stale-footer-just-after-failure; continue-before-`[✗]`; quit-path transient `StateFooter(ModeNormal)` flash) with the on-disk artifact as the authoritative failure record (spec D2/D4, parent T4/D17).
- [ ] The one round-trip integration test over `FakeInteractionChannel` passes; Phase 2's isolated unit tests reused unchanged still pass ([D-8](artifacts/implementation-decision-log.md#d-8-one-round-trip-integration-test-over-fakeinteractionchannel-live-cmux-deferred)).
