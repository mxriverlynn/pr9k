## ⚠ CRITICAL FINDING — Phase 2's end-to-end integration was never wired

This is the single most load-bearing input to the Phase 3 plan. **The Phase 3 spec's central premise — that Phase 3 "reuses the footer-pane keyboard state machine and the orchestrator-to-footer intent channel that Phase 2 already established and tested" — is only half true. The components exist and are *unit-tested in isolation*; they are NOT wired into any running pane process.**

Evidence (verified in `src/` on the `cmux-rebuild` branch at this commit):

1. **The orchestrator pane never runs the workflow.** `src/cmd/pr9k/cmux_pane.go` `runCmuxOrchestratorWith` contains, verbatim:
   ```go
   // Workflow runs here — real implementation ships in a later work unit.
   exitCode := 0
   ```
   `workflow.Run(...)` is called at exactly one place in `src/cmd/pr9k/`: `main.go:374` — the **standard Bubble Tea path only**. It is not invoked from any cmux code path.

2. **The footer state machine and key adapter have zero non-test callers.** `newFooterStateMachine` (`cmux_footer_machine.go`) and `newKeyHandlerAdapter` (`cmux_key_adapter.go`) are constructed only in `*_test.go`. `runCmuxFooterPaneWith` runs only the `statusline.Runner` and a `WorkspaceDone`/`DoneAck` loop — it does not read keystrokes, does not construct the footer state machine, does not forward intents, does not render `StateFooter`.

3. **The header and log panes do not render pushed state.** `runCmuxDisplayPane` (shared by header and log) only handles `WorkspaceDone` → `DoneAck`. It never consumes `StateHeader` / `StateLog` messages; it never renders a step grid or a log stream.

4. **Phase 2's decomposition has no integration work unit.** Phase 2 plan units U1–U12 are all committed (`git log`: `feat(cmux-p2/U1..U12)`). Each unit delivered a component plus its isolated unit tests using `FakeInteractionChannel` / `FakeDisplayPane` / `FakeFooterKeySource`. **No unit delivered "orchestrator calls `workflow.Run` with the `RunHeader` / `StepExecutor` / `KeyHandler` adapters wired to push `StateHeader` / `StateLog` / `StateFooter`, and the three display panes consume and render those messages."** The orchestrator stub comment ("real implementation ships in a later work unit") confirms it was knowingly deferred; no later Phase 2 unit picked it up. Phase 2's titular deliverable ("First Real Workflow Runs End-to-End in Cmux") is not present in running code.

### What this means for Phase 3

Phase 3 ("Interactive Error Recovery") cannot "thinly add" an error prompt on top of a working happy-path run, because **the happy-path run is not wired** in the cmux process tree. The Phase 3 plan must explicitly decide and sequence one of:

- **(A) Absorb the Phase 2 end-to-end integration into the Phase 3 plan** as foundational work units that precede the error-recovery-specific units (orchestrator → `workflow.Run` + adapters; header/log panes render `StateHeader`/`StateLog`; footer pane runs state machine + key adapter + renders `StateFooter`), then layer the error-recovery surfacing on top.
- **(B) Declare the Phase 2 integration a hard prerequisite** that must be completed as separate Phase 2-completion work before Phase 3 starts.

This is an implementation-planning sequencing/dependency question (resolvable in the plan stage), **plus** a spec-wording correction: the Phase 3 spec and its decision log state Phase 2 "established and tested" the wired path. That is accurate for the *components and their unit tests* but not for the *integrated running path*. The plan must surface this so the spec's "thin reuse" framing is corrected to "reuse the unit-tested components, but the Phase 2 end-to-end wiring is part of this work." This is a candidate user escalation.

## Spec commitments Phase 3 must deliver (per spec + build outline)

1. On a step failure that triggers the existing error mode: footer shows continue/retry/quit; header marks the step `[✗]`; log shows error output + (on retry) the retry separator before the retried step's output (D1, D2, D3).
2. Operator focuses the footer to choose; same semantics as standard display (continue/retry/quit, two-step quit confirm, cancel-restores-error-prompt, no auto-timeout, no retry cap, retry uses same resolved command/prompt) (D1).
3. Control keys on header/log panes absorbed silently — no error, no bell, no notification; no out-of-workspace signal in Phase 3 (notification is Phase 5) (D4).
4. Conditions that do NOT enter error mode (soft-fail-on-timeout, skip, prep-fail) behave as the standard display, unchanged.
5. Accepted bounded cross-pane desync windows (stale footer just after failure; continue-before-`[✗]`); on-disk artifacts are the authoritative failure record and are unchanged (D2, parent T4, parent D17).
6. No new cmux calls, no new on-disk artifacts.
