## Full decisions

### D1: Error recovery reuses the inherited workflow error-mode loop unchanged

- **Question:** Does Phase 3 implement a cmux-specific error-recovery flow, or does it surface pr9k's existing error-mode loop through the panes Phase 2 already wired?
- **Decision:** Phase 3 does not implement a separate cmux error flow. It surfaces pr9k's existing error mode — the same state, the same continue / retry / quit choices, the same no-auto-timeout pause, the same retry mechanics (re-run with the same resolved command and prompt, retry separator written to the log), and the same set of conditions that do *not* enter error mode (soft-fail-on-timeout, user-initiated skip, step-preparation failure) — through the footer-pane keyboard state machine and the orchestrator-to-footer intent channel that Phase 2 already established. A choice the operator makes the instant the prompt appears is not lost; the operator's intents are ordered and the orchestrator acts on the first one.
- **Rationale:** Parent [D1](../../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow) commits cmux mode to being an alternate presentation of the same workflow, not a new workflow — the error-mode loop is part of that workflow and must behave identically. Parent [D20](../../artifacts/decision-log.md#d20-keyboard-state-machine-is-owned-by-the-footer-pane) already places the error mode in the footer pane's surviving keyboard state machine. The Phase 2 footer state machine already implements the error-mode key handling (continue / retry / quit, quit-confirm, restore-on-cancel), and the Phase 2 key adapter already translates footer intents into the orchestrator's recovery actions and pushes mode state back to the footer — including handling the race window where a footer keystroke is pressed the instant error mode is entered. Re-implementing any of this as cmux-specific code would risk semantic drift from the standard display for no observable operator benefit, and would violate the project's narrow-reading principle by adding workflow-specific logic to the cmux presentation layer.
- **Evidence:** parent [D1](../../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow), parent [D20](../../artifacts/decision-log.md#d20-keyboard-state-machine-is-owned-by-the-footer-pane); build-phase outline Phase 3 ("reusing the keyboard state machine Phase 2 already put in the footer pane", "identical to the one the standard pr9k display produces today"); Phase 2 implementation (`src/cmd/pr9k/cmux_footer_machine.go` already handles `ui.ModeError` → continue/retry/quit, quit-confirm, restore-on-cancel; `src/cmd/pr9k/cmux_key_adapter.go` already forwards `IntentContinue`/`IntentRetry`/`IntentQuit` to the orchestrator's `ui.KeyHandler.Actions` and pushes `StateFooter` on mode change; the Phase 2 plan's tested "ModeError race window"); [docs/how-to/recovering-from-step-failures.md](../../../how-to/recovering-from-step-failures.md) (retry uses the same resolved command/prompt; no auto-timeout; cancel-quit returns to error mode; soft-fail-on-timeout, skip, and preparation failures do not enter error mode); [docs/adr/20260410170952-narrow-reading-principle.md](../../../adr/20260410170952-narrow-reading-principle.md).
- **Rejected alternatives:**
  - A cmux-specific error-recovery protocol (a bespoke error message kind, a cmux-only recovery state machine) — rejected; duplicates the existing error-mode loop, risks semantic drift from the standard display, and adds workflow logic to the presentation layer against the narrow-reading principle.
  - Adding an auto-timeout or auto-continue so an unattended cmux error resolves itself — rejected; the standard display deliberately has no auto-timeout, and changing it for cmux mode would make the two presentations behave differently. The unattended-operator gap is addressed by Phase 5's persistent notification, not by changing recovery semantics.

### D2: Header marks the failed step with the standard failure indicator

- **Question:** How does the header pane represent the failing step when the run enters error mode?
- **Decision:** The header pane marks the failing step's checkbox with the same failure indicator the standard display uses — not a cmux-only glyph and not an unmarked step. On retry, the step returns to its in-progress state when the retry begins, matching the standard display's retry-marking behavior (the step stays marked failed from the previous attempt until the retry starts).
- **Rationale:** Parent spec's "Step fails and prompts for operator decision" alternate flow commits the orchestrator to pushing the error state "to the header (which marks the current step as failed)". The header pane's state-push message already carries per-step state values that include the failed state, so representing a failed step is a use of the existing Phase 2 header channel, not a new capability. Using the same indicator the standard display uses keeps cmux mode an alternate presentation of the same run (parent [D1](../../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow)) and preserves operator muscle memory; a distinct cmux-only failure glyph would be gratuitous divergence.
- **Evidence:** parent feature spec "Step fails and prompts for operator decision" and "Error states" ("header marks the failing step"); build-phase outline Phase 3 ("The header pane marks the failing step with the same failure indicator the standard display uses today"); Phase 2 implementation (`internal/interactionchannel.StateHeader.StepStates` carries the integer representations of `ui.StepState`, which already includes the failed state); [docs/how-to/recovering-from-step-failures.md](../../../how-to/recovering-from-step-failures.md) ("The step stays marked `[✗]` from the previous attempt until the retry begins").
- **Rejected alternatives:**
  - A distinct cmux-only failure glyph in the header — rejected; gratuitous divergence from the standard display with no operator benefit (parent [D1](../../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow)).
  - Leaving the step unmarked and signaling failure only in the footer/log — rejected; the build-phase outline explicitly commits the header to reflecting the failure, and a three-surface signal (header + log + footer) is what makes the failure unmissable inside the workspace.

### D3: Log pane shows error output and retry separator as ordinary streamed content

- **Question:** How does the log pane present the failing step's error output and any retry separator — as a special error surface, or as ordinary streamed log content?
- **Decision:** The failing step's error output and the retry separator appear in the log pane as ordinary streamed content — the same bytes the standard display's log body would show, in the same order, with no separate error panel, overlay, or special formatting beyond what the standard log body already produces.
- **Rationale:** Parent spec's "Step fails and prompts for operator decision" commits the orchestrator to pushing the error "to the log (which shows the error)". The Phase 2 log pane already streams the orchestrator's log bytes; the error output and the retry separator are part of that same byte stream in the standard display, so showing them is the existing Phase 2 log behavior with no addition. A separate error panel would diverge from the standard display (parent [D1](../../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow)) and would fragment the operator's single chronological view of the run.
- **Evidence:** parent feature spec "Step fails and prompts for operator decision" and "Error states" ("log shows the error"); build-phase outline Phase 3 ("The log pane shows the error output as a normal part of the streaming log"); Phase 2 implementation (the log pane streams orchestrator log bytes via the existing `StateLog` channel); [docs/how-to/recovering-from-step-failures.md](../../../how-to/recovering-from-step-failures.md) and [docs/features/workflow-orchestration.md](../../../features/workflow-orchestration.md) (the retry separator `── <step name> (retry) ──` is written to the log body before a retry).
- **Rejected alternatives:**
  - A dedicated error panel or overlay in the log pane — rejected; diverges from the standard display and fragments the operator's chronological view for no benefit.
  - Special-casing/highlighting error lines differently in cmux mode — rejected; the standard log body's existing formatting is what the operator already knows; cmux mode is an alternate presentation, not a reformat.

### D4: Control keys on non-control panes are absorbed silently with no notification in Phase 3

- **Question:** When the operator presses a control key while a non-control pane (header or log) is focused — including while the run is blocked in error mode — what happens, and does Phase 3 provide any out-of-workspace signal that an error is waiting?
- **Decision:** The keystroke is absorbed by the focused pane without effect: no error, no terminal bell, and no notification. Only the footer pane drives pr9k. Phase 3 adds no out-of-workspace signal that an error prompt is waiting: there is no cmux notification and no sidebar failure label. An operator whose focus is away from the footer when a step fails must notice the stalled run and focus the footer pane on their own. The directing notification that closes this gap is explicitly Phase 5's deliverable, not Phase 3's.
- **Rationale:** Parent [D8](../../artifacts/decision-log.md#d8-footer-pane-owns-keyboard-input) and parent [D20](../../artifacts/decision-log.md#d20-keyboard-state-machine-is-owned-by-the-footer-pane) already establish that only the footer forwards control intents and that control keys on non-control panes are absorbed without effect. The build-phase outline's Phase 3 "What we build" explicitly states the absorbed keystroke produces "no error, no notification", and Phase 3's "Connects to" makes the error-mode notification a Phase 5 trigger. The parent edge-case row for this condition references the persistent error-mode notification, but that notification does not exist until Phase 5 — so in Phase 3 the honest, evidence-grounded behavior is silent absorption with the in-workspace footer prompt as the only signal. Building any part of the Phase 5 notification early would violate the phased build's slice boundaries and the YAGNI rule; emitting an error/bell on a non-control keystroke would be a gratuitous new behavior the standard display does not have.
- **Evidence:** parent [D8](../../artifacts/decision-log.md#d8-footer-pane-owns-keyboard-input), parent [D20](../../artifacts/decision-log.md#d20-keyboard-state-machine-is-owned-by-the-footer-pane); parent feature spec edge-case row "Operator presses a control key … while focus is on the header or log pane" (absorbed without effect, no error, no notification); build-phase outline Phase 3 "What we build" ("the keystroke is absorbed without effect — no error, no notification") and "Connects to" ([Phase 5](../build-phase-outline.md#phase-5) owns the persistent error-mode notification); parent [D6](../../artifacts/decision-log.md#d6-fire-cmux-notifications-at-named-lifecycle-moments) / [D19](../../artifacts/decision-log.md#d19-error-mode-notifications-direct-the-operator-to-the-control-pane) (the notification and its "Focus the pr9k control pane to respond" directive are notification-surface decisions, deferred to Phase 5).
- **Rejected alternatives:**
  - Fire (any part of) the Phase 5 error-mode notification in Phase 3 so an unattended operator is alerted — rejected; violates the phased build's slice boundaries and pulls Phase 5 scope forward without evidence it is needed before Phase 5 ships.
  - Emit a terminal bell or visible error when a control key is pressed on a non-control pane — rejected; gratuitous behavior the standard display does not have, and noisy for an operator who is intentionally scrolling the log pane.
  - Auto-focus the footer pane when an error fires — rejected at parent [D19](../../artifacts/decision-log.md#d19-error-mode-notifications-direct-the-operator-to-the-control-pane) (forcing focus changes is hostile to an operator inspecting the log when the error appears); Phase 3 does not revisit this.
