# Implementation Decision Log: Phase 3 — Interactive Error Recovery

This file records every implementation decision committed while planning Phase 3 — Interactive Error Recovery. Behavioral and implementation statements live in [../feature-implementation-plan.md](../feature-implementation-plan.md) — this file captures the question, rationale, evidence, and rejected alternatives for each decision. Round-by-round history lives in [implementation-iteration-history.md](implementation-iteration-history.md).

Phase 3 inherits the spec's four evidence-settled decisions (spec [D1–D4](../feature-specification.md)) unchanged; this log records only **implementation** decisions made while planning *how* to deliver them. The dominant input is the verified critical finding that Phase 2's end-to-end integration was never wired (see [.discovery-notes.md](.discovery-notes.md)) — the plan must finish Phase 2's integration as foundational work before any error-recovery surfacing is observable.

## Trivial decisions

- D-9: Reuse the shared `internal/ui` `Orchestrate` loop, `StatusHeader` renderer, and `RetryStepSeparator` unchanged — Phase 3 surfaces the existing error-mode loop through the cmux panes; it adds no Ralph-specific or cmux-specific recovery logic to Go code (`docs/adr/20260410170952-narrow-reading-principle.md`; spec [D1](../feature-specification.md#d1-error-recovery-reuses-the-inherited-workflow-error-mode-loop-unchanged), [D2](../feature-specification.md#d2-header-marks-the-failed-step-with-the-standard-failure-indicator), [D3](../feature-specification.md#d3-log-pane-shows-error-output-and-retry-separator-as-ordinary-streamed-content)). ## Full decisions

### D-1: Absorb the Phase 2 end-to-end integration into the Phase 3 plan as foundational work

- **Question:** The Phase 3 spec presumes a running Phase 2 cmux workflow ("a workflow is running inside a Phase 2 cmux workspace") that interactive error recovery layers on top of. The verified critical finding is that Phase 2's end-to-end integration was never wired — the components are unit-tested in isolation but not connected into any running pane process. Does the Phase 3 plan **absorb** the Phase 2 happy-path integration as foundational work units that precede the error-recovery units, or treat it as a **separate Phase 2-completion prerequisite** done before Phase 3 starts?
- **Decision:** The Phase 3 plan absorbs the Phase 2 end-to-end integration as foundational work units (orchestrator → `workflow.Run` with `RunHeader`/`StepExecutor`/`KeyHandler` adapters + `orchChannel` interface expansion; header/log panes consume and render `StateHeader`/`StateLog`; footer pane runs the state machine + key adapter and renders `StateFooter`), then layers the error-recovery-specific verification on top. "Phase 3 done" means a real workflow runs end-to-end in a cmux workspace **and** a failing step is interactively recoverable per spec D1–D4 — the happy-path wiring is in scope for this plan, not a separately tracked prerequisite.
- **Rationale:** The user resolved the escalated Open Question (OQ-1) directly: absorb. Independently, behavioral-analyst found the error-recovery path is not separable from the shared `Orchestrate` loop — the *same code path* at `src/internal/ui/orchestrate.go` emits step-success / `SetMode(ModeDone)` AND `SetStepState(StepFailed)` / `SetMode(ModeError)`; wiring the orchestrator to `workflow.Run` necessarily activates the error path (B-Q4 / C4). A separate-prerequisite framing would create a dependency chain on work no other plan owns (Phase 2's units U1–U12 are all committed and none picked up the integration; the orchestrator stub comment confirms it was knowingly deferred — `src/cmd/pr9k/cmux_pane.go:113-114`), and would leave Phase 3 unable to demonstrate any of its spec behaviors. Absorbing keeps the slice demoable: slice 1 (happy-path wiring) closes the Phase 2 gap and is demoable alone; slice 2 (error recovery) builds on slice 1.
- **Evidence:** **User input** (OQ-1 resolved: absorb the Phase 2 integration as foundational work units, layer error recovery on top). behavioral-analyst B1–B4, B-Q4, C1/C4 (claim ledger, [implementation-iteration-history.md](implementation-iteration-history.md) R1). Verified code: `src/cmd/pr9k/cmux_pane.go:113-114` (`// Workflow runs here — real implementation ships in a later work unit.` / `exitCode := 0`); `workflow.Run` called only at `src/cmd/pr9k/main.go:374` (standard Bubble Tea path); `newFooterStateMachine`/`newKeyHandlerAdapter` zero non-test callers; `runCmuxDisplayPane` (`cmux_pane.go:164-193`) handles only `WorkspaceDone`→`DoneAck`. Phase 2 plan units U1–U12 (no integration unit) — `docs/plans/cmux-rebuild/phase-2-real-workflow-runs/feature-implementation-plan.md`. [.discovery-notes.md](.discovery-notes.md) CRITICAL FINDING.
- **Rejected alternatives:**
  - Treat the Phase 2 end-to-end integration as a separate Phase 2-completion prerequisite, completed before Phase 3 begins — rejected by user input (OQ-1). Also weak on evidence: no plan owns that prerequisite work, the orchestrator stub was knowingly deferred with no later unit picking it up, and behavioral-analyst showed the error path is the same `Orchestrate` code path as the happy path so the two cannot be cleanly separated into independently shippable plans (B-Q4 / C4).
  - Implement a cmux-specific error-recovery flow that does not depend on the unwired Phase 2 happy-path — rejected; duplicates the inherited error-mode loop, risks semantic drift from the standard display, and violates the narrow-reading principle (`docs/adr/20260410170952-narrow-reading-principle.md`; spec [D1](../feature-specification.md#d1-error-recovery-reuses-the-inherited-workflow-error-mode-loop-unchanged) rejected the same alternative at spec stage).

### D-3: Expand the existing `orchChannel` interface in place rather than introduce a new richer interface

- **Question:** The orchestrator pane must push `StateHeader` / `StateLog` / `StateFooter` over the interaction channel, but the current `orchChannel` interface (`src/cmd/pr9k/cmux_pane.go:27-32`) exposes only `AwaitReady` / `Send` / `Recv` / `Close`. Expand `orchChannel` in place, or introduce a new dedicated richer interface type for the wired orchestrator?
- **Decision:** Expand the existing `orchChannel` interface in place to add the state-push methods (`SendStateHeader` / `SendStateLog` / `SendStateFooter`) needed by the wired orchestrator. Do not introduce a separate richer interface type.
- **Rationale:** There is a single concrete need (the wired orchestrator) and a single production implementation (`*interactionchannel.Channel`); the existing `FakeInteractionChannel` test double already implements `SendStateHeader`/`SendStateLog`/`SendStateFooter` from Phase 2 U10, so expanding `orchChannel` in place requires no new test double and no second consumer. A new dedicated richer interface with one implementation and one consumer is the single-implementation-interface anti-pattern (YAGNI rule doc): completeness/symmetry is not evidence. The simpler version (expand in place) satisfies the same evidenced need (orchestrator must push state) as the larger version (new interface) with strictly less surface.
- **Evidence:** YAGNI ledger Step 7.5 simpler-version replacement #1. behavioral-analyst B5, B11-h3, C3 ([implementation-iteration-history.md](implementation-iteration-history.md) R1). Verified code: `src/cmd/pr9k/cmux_pane.go:27-32` (`orchChannel` lacks `SendStateHeader`/`SendStateLog`/`SendStateFooter`); `FakeInteractionChannel` already implements them (Phase 2 U10 — Phase 2 plan [D-14](../../phase-2-real-workflow-runs/artifacts/implementation-decision-log.md#d-14-three-test-doubles-with-hooks-scoped-to-planned-tests)); `docs/coding-standards/api-design.md` (adapter types, compile-time interface assertions). [`plugins/han/references/yagni-rule.md`](../../../../../plugins/han/references/yagni-rule.md) (single-implementation interface anti-pattern).
- **Rejected alternatives:**
  - Introduce a new dedicated richer interface type for the wired orchestrator — rejected (simpler version satisfies the same evidence): single implementation, single consumer, no second concrete use; the single-implementation-interface anti-pattern. `FakeInteractionChannel` already satisfies the expanded method set so the new type would add surface with no test or production benefit.
- **Specialist owner:** `behavioral-analyst`.
- **Revisit criterion:** Reopen if a second concrete consumer of the orchestrator-side push surface appears (e.g., Phase 4 sidebar mirroring needing a distinct fan-in type) with a divergent contract from `orchChannel`.
- **Dissent (if any):** None recorded.

### D-4: Construct the orchestrator's `KeyHandler` with the runner's `Terminate` as the cancel function

- **Question:** When the orchestrator pane constructs the `ui.KeyHandler` it passes to `workflow.Run`, what cancel function does it supply — `nil` (as the disconnected footer renderer currently does), or the workflow runner's `Terminate`?
- **Decision:** The orchestrator pane constructs its `KeyHandler` with the workflow runner's `Terminate` as the cancel function, mirroring the standard path at `src/cmd/pr9k/main.go:226` (`ui.NewKeyHandler(runner.Terminate, actions)`). The footer renderer's existing `nil`-cancel `KeyHandler` (`src/cmd/pr9k/cmux_footer_renderer.go:22`) is not the handler the orchestrator uses.
- **Rationale:** behavioral-analyst found that a `nil`-cancel `KeyHandler` would make quit-during-an-active-step fail to kill the running subprocess — the quit intent would resolve in the state machine but the in-flight step process would not be terminated, leaving the run unable to abort cleanly during error mode or any active step (B9 / C9). The standard path already constructs the handler with `runner.Terminate` (`main.go:226`); cmux mode is an alternate presentation of the same run (parent D1 / spec D1), so it must preserve the same abort semantics. This is an implementation constraint that protects spec D1's quit semantics, not a behavior change.
- **Evidence:** behavioral-analyst B9, C9 ([implementation-iteration-history.md](implementation-iteration-history.md) R1). Verified code: `src/cmd/pr9k/main.go:226` (`keyHandler := ui.NewKeyHandler(runner.Terminate, actions)`); `src/cmd/pr9k/cmux_footer_renderer.go:22` (`h := ui.NewKeyHandler(nil, actions)` — disconnected renderer). Spec [D1](../feature-specification.md#d1-error-recovery-reuses-the-inherited-workflow-error-mode-loop-unchanged) (quit uses the same semantics as the standard display); parent D1 (alternate presentation, same workflow).
- **Rejected alternatives:**
  - Construct the orchestrator `KeyHandler` with `nil` cancel (as the footer renderer currently does) — rejected; quit-during-active-step would not terminate the running subprocess, breaking spec D1's quit semantics (behavioral-analyst B9/C9).
- **Specialist owner:** `behavioral-analyst`.
- **Revisit criterion:** Reopen if the workflow runner's termination contract changes such that `Terminate` is no longer the correct cancel function for the standard path (which would be detected at `main.go:226` first).
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-7
- **Referenced in plan:** Implementation Approach (Runtime Behavior), Decomposition and Sequencing (W1), RAID Log (Risks)

### D-5: The `WriteToLog` → `SendStateLog` adapter is synchronous on the orchestrator goroutine

- **Question:** The shared `Orchestrate` path writes the retry separator with `runner.WriteToLog(RetryStepSeparator(step.Name))` (`src/internal/ui/orchestrate.go:135`) **before** re-running the step. Spec D3 requires the separator to reach the log pane before any retried-step output. Is the adapter that turns `WriteToLog` calls into `SendStateLog` pushes synchronous on the orchestrator goroutine, or async-dispatched?
- **Decision:** The `WriteToLog` → `SendStateLog` adapter executes synchronously on the orchestrator goroutine (the same goroutine that runs `Orchestrate`), not via an async dispatch/queue that could reorder relative to the subsequent step start.
- **Rationale:** behavioral-analyst found the spec D3 separator-before-output ordering is sound **only if** the adapter is synchronous on the orchestrator goroutine: `Orchestrate` calls `WriteToLog(RetryStepSeparator(...))` then re-runs the step sequentially (`orchestrate.go:135` then loop), so if the `WriteToLog`→`SendStateLog` send happens synchronously before `Orchestrate` proceeds to start the retried step, the separator is enqueued onto the log channel before any retried-step output; an async dispatch could let the step start and emit output before the separator send is processed, violating spec D3's stated ordering requirement (B7 / C8). The interaction channel already preserves per-connection delivery order, so a synchronous enqueue is sufficient — no extra ordering machinery is needed.
- **Evidence:** behavioral-analyst B7, C8 ([implementation-iteration-history.md](implementation-iteration-history.md) R1). Verified code: `src/internal/ui/orchestrate.go:135` (`runner.WriteToLog(RetryStepSeparator(step.Name))`) executed sequentially before the retry loop iteration. Spec [D3](../feature-specification.md#d3-log-pane-shows-error-output-and-retry-separator-as-ordinary-streamed-content) (retry separator emitted before any retried-step output; per-pane log delivery order preserved). [.discovery-notes.md](.discovery-notes.md) (`StateLog` drop-oldest, serial per-connection delivery). `docs/coding-standards/concurrency.md` (non-blocking sends; snapshot-then-unlock).
- **Rejected alternatives:**
  - Async-dispatch the `WriteToLog`→`SendStateLog` adapter (queue + separate sender goroutine) — rejected; introduces a reordering window where the retried step could emit output before the separator send is processed, violating spec D3's stated separator-before-output requirement (behavioral-analyst B7/C8).
- **Specialist owner:** `behavioral-analyst`.
- **Revisit criterion:** Reopen if the interaction channel's per-connection serial delivery guarantee is weakened, or if measured log throughput under a real workflow makes a synchronous send a latency problem (then a bounded async design that still preserves separator-before-output ordering would be evaluated).
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** —
- **Referenced in plan:** Implementation Approach (Runtime Behavior), Decomposition and Sequencing (W2), RAID Log (Risks), Testing Strategy

### D-6: Establish `SetOnModeChange` + the key-adapter goroutine before `workflow.Run` starts; drain the footer-keystroke goroutine on context cancel via WaitGroup

- **Question:** What concurrency-establishment ordering and shutdown discipline does the orchestrator↔footer bridge require so that (a) a first-step `SetMode(ModeError)` is not missed and (b) the footer's keystroke goroutine does not leak?
- **Decision:** The orchestrator path establishes `h.SetOnModeChange` (the hook that turns `SetMode` into a `SendStateFooter` push) and starts the key-adapter goroutine **before** `workflow.Run` is called. The footer pane's keystroke-reading goroutine exits on context cancel and is joined via `sync.WaitGroup` drain before the pane process returns.
- **Rationale:** behavioral-analyst flagged two concurrency hazards: (h1) if `SetOnModeChange` and the key-adapter goroutine are established *after* `workflow.Run` starts, a first-step failure that fires `SetMode(ModeError)` before the hook is set would not push `StateFooter`, stranding the operator with no error prompt — the fix is the canonical "establish the observer before the producer starts" ordering (`docs/coding-standards/concurrency.md:71-78`); (h2) the footer keystroke goroutine must exit on context cancel and be WaitGroup-drained (`docs/coding-standards/concurrency.md:24-37`) so it does not leak when the pane shuts down (B11-h1, B11-h2 / C10). behavioral-analyst confirmed the race-window guarantee (spec D1) otherwise holds by design once wired: buffered `h.Actions` (cap 10) plus a synchronous `onModeChange` before the blocking `<-h.Actions` receive is exactly the `concurrency.md` "prime the channel before blocking receive" pattern, so wiring introduces no new race risk beyond honoring this establishment ordering (B6 / C7).
- **Evidence:** behavioral-analyst B6, B11-h1, B11-h2, C7, C10 ([implementation-iteration-history.md](implementation-iteration-history.md) R1). `docs/coding-standards/concurrency.md` (lines ~24-37 WaitGroup drain; lines ~71-78 establish-before-start ordering; "prime the channel before blocking receive"). Verified code: `src/internal/ui/orchestrate.go:124-128` (`header.SetStepState(idx, StepFailed)`, `h.SetMode(ModeError)`, `action := <-h.Actions`); footer renderer's `actions := make(chan ui.StepAction, 10)` cap-10 buffer (`src/cmd/pr9k/cmux_footer_renderer.go:22`). Phase 2 tests `TestAdapter_SetMode_PushesStateFooter`, `TestAdapter_ModeErrorRaceWindow_NoDroppedKeystroke` (spec [D1](../feature-specification.md#d1-error-recovery-reuses-the-inherited-workflow-error-mode-loop-unchanged) evidence).
- **Rejected alternatives:**
  - Establish the mode-change hook / key-adapter lazily (after `workflow.Run` starts) and accept the first-step-failure gap — rejected; a step that fails on the first attempt before the hook is set would push no `StateFooter`, stranding the run with no visible prompt (behavioral-analyst B11-h1; `concurrency.md:71-78`).
  - Let the footer keystroke goroutine exit implicitly on process teardown without an explicit WaitGroup join — rejected; goroutine-leak / race-detector violation against `docs/coding-standards/concurrency.md:24-37` and `docs/coding-standards/testing.md` (race detector mandatory).
- **Specialist owner:** `behavioral-analyst`.
- **Revisit criterion:** Reopen if a future refactor moves mode-change notification off the synchronous `SetMode` path (e.g., a batched mode-change publisher), which would re-open the race-window analysis (B6/C7).
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-7
- **Referenced in plan:** Implementation Approach (Runtime Behavior), Decomposition and Sequencing (W1, W3), RAID Log (Risks), Testing Strategy

### D-7: Remove the footer renderer's isolated `KeyHandler`/`actions` channel; drive the footer from the wired path

- **Question:** The cmux footer renderer constructs its own private `ui.KeyHandler` with an unread `actions` channel (`src/cmd/pr9k/cmux_footer_renderer.go:22-25`) and `HandleKey` handles only `?`/`esc`. The wired footer pane must run the real footer state machine + key adapter and forward intents to the orchestrator. Keep the renderer's isolated handler and add a parallel wired path, or remove the isolated handler and drive the footer entirely from the wired path?
- **Decision:** Remove the footer renderer's isolated `KeyHandler` and its unread `actions` channel. The footer pane runs the Phase 2 `footerStateMachine` + `newKeyHandlerAdapter` (currently zero non-test callers) wired to the interaction channel; the orchestrator must reuse the *same* `actions` channel passed to `workflow.Run`, not the footer renderer's isolated one. The renderer keeps only its display responsibilities (size, help-expand render); keyboard handling moves to the wired state machine.
- **Rationale:** behavioral-analyst found the renderer's private `KeyHandler` is disconnected (unread `actions` channel, `HandleKey` handles only `?`/`esc`, no state-machine delegation) and that the orchestrator must reuse the same `actions` channel passed to `workflow.Run` — not the renderer's isolated one — or footer intents would never reach `Orchestrate`'s `<-h.Actions` receive (B3, B11-h4 / C2). Two `KeyHandler`s (one isolated in the renderer, one in the wired path) is a second, contradictory source of keyboard truth — the same "two specialists relying on mutually incompatible beliefs about the system" failure the inconsistency check guards against, here as two code paths that cannot both own keyboard input. Removing the isolated handler eliminates the contradiction and is the precondition for the footer-pane wiring (W3) to work at all.
- **Evidence:** behavioral-analyst B3, B11-h4, C2 ([implementation-iteration-history.md](implementation-iteration-history.md) R1). Verified code: `src/cmd/pr9k/cmux_footer_renderer.go:22-25` (`actions := make(chan ui.StepAction, 10); h := ui.NewKeyHandler(nil, actions); h.SetStatusLineActive(true)`), `HandleKey` switch handles only `"?"`/`"esc"`; `newFooterStateMachine`/`newKeyHandlerAdapter` zero non-test callers (`src/cmd/pr9k/cmux_footer_machine.go`, `cmux_key_adapter.go`); `src/internal/ui/orchestrate.go:127` (`action := <-h.Actions` — the orchestrator's receive must be on the channel the footer adapter sends to). Spec [D1](../feature-specification.md#d1-error-recovery-reuses-the-inherited-workflow-error-mode-loop-unchanged) (footer-pane state machine + intent channel reused). Depends on D-4 (the wired `KeyHandler` is the one with `runner.Terminate`) and D-6 (establishment ordering).
- **Rejected alternatives:**
  - Keep the renderer's isolated `KeyHandler` and add a parallel wired path alongside it — rejected; two keyboard-truth sources with the orchestrator potentially receiving on the wrong `actions` channel; footer intents would not reach `Orchestrate` (behavioral-analyst B11-h4/C2).
  - Route the wired path through the renderer's existing `nil`-cancel handler — rejected; conflicts with D-4 (the wired handler must carry `runner.Terminate`) and the renderer's handler handles only `?`/`esc`.
- **Specialist owner:** `behavioral-analyst`.
- **Revisit criterion:** Reopen if a future design legitimately needs a footer-local key handler distinct from the wired state machine (none is evidenced now; the renderer's `?`/`esc` help-expand is display state, not an intent path).
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-8
- **Referenced in plan:** Implementation Approach (Architecture and Integration Points, Runtime Behavior), Decomposition and Sequencing (W3), RAID Log (Issues), Testing Strategy

### D-8: One round-trip integration test over `FakeInteractionChannel`; live-cmux deferred

- **Question:** Phase 2's tests cover the footer state machine, key adapter, and fan-out **in isolation**; none exercises the wired composition (orchestrator `SetMode(ModeError)` → `StateFooter` push → footer intent → `Orchestrate` action). What new test coverage does the wired error-recovery path get — a full new test harness / matrix, or a single round-trip integration-style test — and does any live-cmux test land in Phase 3?
- **Decision:** Add **one** round-trip integration-style test over the existing `FakeInteractionChannel` that drives the wired composition end-to-end: orchestrator enters `SetMode(ModeError)` → `StateFooter` carrying `ModeError` is pushed → a footer intent (continue/retry/quit) is produced → `Orchestrate` consumes the corresponding action. Reuse Phase 2's isolated unit tests unchanged for the components. No new test harness, no matrix duplicating Phase 2's isolated coverage. Live-cmux integration remains deferred to Phase 6 (spec OI-1 / parent OQ-2 / Phase 1 OI-2).
- **Rationale:** junior-developer flagged that "no new message kinds / race window holds" is verified for components in isolation but the adapter-construction wiring is new code unit tests never exercised; an integration test over the wired path is needed and the gap is an integration risk (Q3, Q4 / C12). behavioral-analyst confirmed the guarantees hold *by design* once wired (B6/B7), so the test validates the wiring is actually in place rather than re-deriving guarantees. One round-trip test satisfies that evidenced need; a full new harness or a matrix re-running Phase 2's component cases would duplicate existing isolated coverage (symmetry/completeness — not evidence under the YAGNI rule). The YAGNI "tests for code paths that don't exist yet" anti-pattern does not apply: the wired path *will* exist after W1–W3, so the test is for real code, just deferred in authoring order to after the wiring units.
