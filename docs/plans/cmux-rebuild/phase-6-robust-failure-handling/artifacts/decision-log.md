## Full decisions

### D1: Orchestrator-survivable failures converge on one clean abort sequence

- **Question:** when the orchestrator survives a failure (display-pane death, operator pane-close, channel stall, cmux call timeout), what does it do — and is the response the same across all of them?
- **Decision:** all orchestrator-survivable failures converge on a single clean-abort sequence. The orchestrator makes a **single one-way transition into an aborting state**; this transition happens at most once per run and is checked by every failure-detection path (the cmux-call path, the channel-stall path, the display-loss path). The first detection to make the transition wins — its failure is the one named in the diagnostic — and every later detection observes the aborting state and is absorbed. Having transitioned, the orchestrator: lets any in-flight cmux call finish ([D10](#d10-the-orchestrator-finishes-any-in-flight-cmux-call-before-running-the-abort-sequence)), terminates the running step's subprocess ([D15](#d15-the-abort-terminates-the-running-step-subprocess-target-repo-side-effects-are-left-as-reached)), writes the classified diagnostic ([D5](#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic)), fires the run-aborted notification exactly once ([D9](#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)), clears the Phase 4 sidebar entries, broadcasts the aborted outcome to the panes ([D13](#d13-the-clean-abort-broadcasts-the-aborted-outcome-to-the-panes-for-prompt-exit)), and exits non-zero. The workspace stays open. No failure mode gets a bespoke response.
- **Rationale:** the build-outline Phase 6 entry's central insight is that "the value is in covering all of them together — leaving any one out means an operator can still hit a confusing state." A single convergence point is the simplest design that guarantees no failure mode produces an uncovered partial state, and it makes the abort behavior testable as one path rather than five. The single one-way transition was added after review (F3): the "exactly once" guarantee on the run-aborted notification is only sound if every failure-detection path checks one shared abort gate — without it, two near-simultaneous detections on different code paths could each believe they were first and each run the sequence.
- **Evidence:** build-outline [Phase 6](../../build-phase-outline.md#phase-6) ("the same clean outcome"); parent [D10](../../artifacts/decision-log.md#d10-display-pane-loss-aborts-the-run), [D15](../../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal), [D24](../../artifacts/decision-log.md#d24-operator-pane-close-is-treated-as-display-loss); [Phase 5 D1](../../phase-5-lifecycle-notifications/artifacts/decision-log.md#d1-three-notification-classes-and-their-targeting) (run-aborted notification); the existing user-quit abort path in the cmux orchestration code already fires run-aborted and clears the sidebar — Phase 6 generalizes that one path to every survivable failure.
- **Rejected alternatives:**
  - **Per-mode bespoke handling** — rejected; multiplies the surface area, makes coverage gaps likely, and gives the operator inconsistent end states.
  - **Abort only on display loss, warn-and-continue on the others** — rejected for the reason parent [D15](../../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal) rejected warn-and-continue: a degraded run diverges the operator's view from the real workflow state.
  - **No shared abort gate, rely on each detection path being mutually exclusive in practice** — rejected after review (F3); near-simultaneous detections on independent paths are possible and would break the exactly-once guarantee.

### D2: The interaction-channel stall threshold is 45 seconds

- **Question:** how long does the orchestrator or a display pane wait on a silent-but-not-disconnected interaction channel before declaring it lost?
- **Decision:** **45 seconds** of unexpected silence; the boundary is inclusive — the channel is declared lost *at or after* 45 seconds. The threshold applies symmetrically — the orchestrator detecting a silent pane, and a pane detecting a silent orchestrator. A clean disconnect (a process exits, the connection breaks) is detected *promptly*, within the channel's normal read cycle and far below the threshold; the 45-second threshold is only for the alive-but-silent case.
- **Rationale:** the operator selected the "longer (30–60 second)" band over matching the ~8-second cmux per-call timeout ([OQ-4](../../build-phase-outline.md#oq-4) Option A) and over an operator-configurable value. The longer band is forgiving of the busiest moments of a Claude step, where the channel can legitimately go quiet; the build-outline OQ-4 entry names exactly this concern as the risk of the short option. 45 seconds is the midpoint of the chosen band — short enough that a real stall surfaces inside a minute, long enough to clear the forgiveness bar the operator asked for. A single fixed value (rather than a range left to implementation) keeps failure-mode tests deterministic and the documentation concrete, matching how parent [D27](../../artifacts/decision-log.md#d27-cmux-per-call-timeout-value) pinned the cmux timeout. The inclusive boundary was pinned after review (F12) so the implementation and its tests agree on the exactly-45-second case.
- **Evidence:**
  - User confirmation on 2026-05-22 selecting the "longer (30–60 seconds)" band over "match the cmux timeout (~8s)" and "operator-configurable".
  - Build-outline [OQ-4](../../build-phase-outline.md#oq-4): the spec commits to "the channel has a stall threshold" but leaves the value open; the team is to settle it before Phase 6 ships.
  - Parent [D27](../../artifacts/decision-log.md#d27-cmux-per-call-timeout-value): precedent for pinning a single fixed value at the spec level rather than leaving a range.
  - Code survey: `internal/interactionchannel` currently detects only clean disconnects (EOF / broken connection) and has no mid-run stall threshold — the threshold is new work for Phase 6.
- **Rejected alternatives:**
  - **Match the cmux per-call timeout (~8 seconds)** — rejected by the operator; too aggressive for the quiet stretches of a long Claude step, risking false-positive aborts.
  - **Operator-configurable threshold** — rejected by the operator; adds an operator-facing configuration surface with no evidence anyone wants to change it, against the YAGNI reasoning parent [D27](../../artifacts/decision-log.md#d27-cmux-per-call-timeout-value) applied to the cmux timeout. Demoted to [Deferred (YAGNI)](../feature-specification.md#deferred-yagni).
- **Linked technical notes:** —
- **Driven by findings:** F12
- **Dependent decisions:** D3, D4
- **Referenced in spec:** Alternate Flows and States, Edge Cases and Failure Modes, Coordinations

### D3: A healthy-but-quiet channel is never mistaken for a stalled one

- **Question:** the stall threshold ([D2](#d2-the-interaction-channel-stall-threshold-is-45-seconds)) declares a channel lost after 45 seconds of silence — but a normal workflow step can produce no output for far longer than 45 seconds, and a run paused at an error-mode prompt can sit idle indefinitely. How is a legitimately idle channel kept from triggering a false abort, and who keeps it alive?
- **Decision:** the **orchestrator emits a content-independent liveness signal to every display pane** on a fixed cadence well below the 45-second threshold, in *every* workflow phase — while a step runs, between steps, while the run is paused at a Phase 3 error-mode prompt, and during the done-state wait. "Silence" for the purpose of the stall threshold means the absence of that liveness signal (or of any other expected message), not the absence of workflow output. A pane therefore treats the channel as healthy as long as it has received *any* message — liveness signal or content — within the threshold window. A long-running quiet step, or a run paused waiting for an operator decision, keeps the channel demonstrably alive and never trips the threshold. The liveness signal must be running before the stall timer begins counting on either side. The cadence value is implementation-owned; the behavioral commitments are (a) the orchestrator is the emitter, (b) the signal is independent of workflow content, (c) it runs in every phase, and (d) an idle-but-healthy channel is never declared stalled.
- **Rationale:** without this guard, [D2](#d2-the-interaction-channel-stall-threshold-is-45-seconds)'s threshold would false-abort every workflow whose steps are quiet for 45+ seconds — which is most real workflows, since a single Claude step routinely runs minutes with sparse output — and would abort any run left paused at an error-mode prompt for more than 45 seconds, which is the precise situation Phase 3 / Phase 5's persistent error notification is designed to survive. The build-outline [OQ-4](../../build-phase-outline.md#oq-4) entry names the quiet-step risk directly. The review surfaced two further consequences (F1): the orchestrator must be the emitter (the panes are renderers and have no workflow state to signal liveness from), and the signal must continue during the error-mode pause (F1 / edge-case review) or a paused run would self-abort. The spec must commit to the behavioral obligation even though the cadence mechanism is implementation detail — this is the behavioral guarantee that makes D2 correct.
- **Evidence:**
  - Build-outline [OQ-4](../../build-phase-outline.md#oq-4): the named risk that a stall threshold could be tripped by a busy/quiet Claude step.
  - Parent [T4](../../artifacts/feature-technical-notes.md#t4-display-processes-update-independently): display processes update only when the orchestrator pushes — so an absence of content pushes is normal, not a fault, and the orchestrator is the side with the run state.
  - [Phase 3 — Interactive Error Recovery](../../phase-3-interactive-error-recovery/feature-specification.md) and [Phase 5](../../phase-5-lifecycle-notifications/feature-specification.md): a run can be legitimately paused at an error prompt for an unbounded time; the channel must stay healthy through that pause.
  - Code survey: `internal/interactionchannel` has no heartbeat today; the liveness signal is new work for Phase 6.
- **Rejected alternatives:**
  - **Treat any 45-second content silence as a stall** — rejected; false-aborts normal workflows and paused error prompts. This is the failure D3 exists to prevent.
  - **Make the threshold long enough to outlast any step** — rejected; there is no safe upper bound on step duration or on how long a run sits at an error prompt, and a very long threshold defeats the purpose of detecting a real stall promptly.
  - **Have the display panes emit the liveness signal** — rejected (F1); the panes are renderers with no authoritative run state, and a pane emitting liveness would only prove the pane is alive, not that the orchestrator–pane channel is carrying the orchestrator's traffic.
- **Linked technical notes:** —
- **Driven by findings:** F1
- **Dependent decisions:** —
- **Referenced in spec:** Actors and Triggers, Alternate Flows and States, Edge Cases and Failure Modes, Coordinations

### D4: Orchestrator process death is the documented exception to the clean-abort outcome

- **Question:** the clean-abort sequence ([D1](#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence)) is run *by the orchestrator*. What happens when the orchestrator process itself dies and cannot run it — including when it dies partway through the sequence?
- **Decision:** orchestrator death (crash, force-kill, host shutdown) is the explicit exception to the clean-abort outcome. No in-process cleanup runs: no run-aborted notification fires, the sidebar entries are not cleared, no aborted-outcome broadcast is sent. Each of the three display panes detects the lost interaction channel — promptly on a clean disconnect, or within the 45-second stall threshold ([D2](#d2-the-interaction-channel-stall-threshold-is-45-seconds)) if the channel goes silent without disconnecting — independently renders a final line containing "run aborted" on its own pane, and exits. The workspace persists as an orphan with stale sidebar entries; the operator dismisses it manually. **Partial abort is a sub-case of this decision:** if the orchestrator dies *partway through* its own clean-abort sequence, the operator observes whatever steps completed before death (the notification may have fired but the sidebar not cleared, etc.); the abort sequence is not transactional, and this partial state is handled, from the operator's standpoint, identically to full orchestrator death — an orphan workspace to dismiss manually.
- **Rationale:** under Architecture A ([parent D-R1](../../artifacts/decision-log.md#d-r1-orchestrator-is-the-in-pane-pr9k-process-no-hidden-orchestrator-pane-supersedes-d13d-3d-4-hidden-pane-parts)) the orchestrator is the only process holding both the cmux workspace handle and the authority to fire notifications and clear the sidebar. When it dies, no surviving pr9k process can complete that cleanup — the display panes are renderers connected only to the interaction channel, not to cmux's control surface. The honest spec position is to name this as a documented exception rather than pretend a uniform outcome. The "run aborted" line on each pane is the substitute signal so the operator sees the run ended rather than a silently frozen display; the orphan workspace is tolerated and handed to [Phase 7](../../build-phase-outline.md#phase-7)'s advisory. The partial-abort sub-case was added after review (F4): an orchestrator can die at any point, including mid-sequence, and the spec must not imply the only partial state is "death before any cleanup."
- **Evidence:**
  - Build-outline [Phase 6](../../build-phase-outline.md#phase-6): the orchestrator-death bullet ("each display pane detects the lost channel ... renders a 'run aborted' line ... and exits") and the force-kill bullet ("leaves the workspace as an orphan with no cleanup").
  - Parent spec [Edge Cases](../../feature-specification.md#edge-cases-and-failure-modes): the "orchestrator pane dies" and SIGKILL rows.
  - Parent [D-R1](../../artifacts/decision-log.md#d-r1-orchestrator-is-the-in-pane-pr9k-process-no-hidden-orchestrator-pane-supersedes-d13d-3d-4-hidden-pane-parts): the orchestrator is the sole cmux client.
  - Parent [T5](../../artifacts/feature-technical-notes.md#t5-cmux-workspace-persists-after-pane-exit): the workspace persists after its panes exit, which is what makes the orphan inspectable.
  - [Phase 5 Edge Cases](../../phase-5-lifecycle-notifications/feature-specification.md#edge-cases-and-failure-modes): Phase 5 explicitly makes "no commitment about a notification firing" on the orchestrator-death path and delegates it here.
- **Rejected alternatives:**
  - **Have a display pane fire the run-aborted notification on the orchestrator's behalf** — rejected; the display panes are not cmux control clients and giving them the workspace handle and notification authority would duplicate the cmux integration into three more processes for one failure mode.
  - **Auto-close the orphan workspace from the next pr9k launch** — rejected; this is parent-deferred auto-cleanup ([parent D11](../../artifacts/decision-log.md#d11-orphan-workspaces-from-crashes-are-not-auto-cleaned)) and would discard forensic state.
  - **Make the abort sequence transactional so partial abort cannot occur** — rejected; an orchestrator can be force-killed at any instruction boundary, and no in-process design can make a multi-step cmux interaction atomic against SIGKILL.
  - **Claim a uniform clean outcome for all failures including orchestrator death** — rejected as dishonest; the spec must state where cleanup genuinely cannot run.
- **Linked technical notes:** —
- **Driven by findings:** F4
- **Dependent decisions:** D12
- **Referenced in spec:** Outcome, Alternate Flows and States, Edge Cases and Failure Modes, User Interactions, Coordinations

### D5: Mid-run cmux failures are classified to an accurate operator diagnostic

- **Question:** when a cmux API call fails *mid-run* (a structured cmux v2 error envelope, or a plaintext access-denial line), what does the operator-facing diagnostic say — and what happens for an error code the classifier does not recognize?
- **Decision:** the orchestrator classifies the failure to a specific, actionable cause and names that cause in the abort diagnostic written to the per-run log file and the launching terminal. The recognized classes are at minimum **access denied**, **a named missing method**, and **an authentication failure** — the same classes the startup capability check already recognizes from the cmux v2 protocol. It does not fall back to the generic "cmux version is incompatible" catch-all the startup check uses for a different condition. An error code that matches **no recognized class** is reported as an *unclassified cmux error* with the raw cmux error code preserved verbatim in the diagnostic, so the operator and a maintainer still have the exact code for forensics. If the mid-run failure prevents the orchestrator from continuing, the clean-abort sequence ([D1](#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence)) runs with the classified (or unclassified-with-raw-code) cause as the named reason. The exact diagnostic strings are pinned by the implementation plan.
- **Rationale:** the build-outline Phase 6 entry calls for cmux v2 errors and the plaintext `ERROR:` access denial to be "classified to accurate operator guidance rather than the catch-all 'version incompatible'." A generic message sends the operator to upgrade cmux when the real cause was, e.g., the socket access mode changing or a transient auth failure — wasting their time on the wrong fix. The classification vocabulary already exists in pr9k's cmux control client (structured error codes and the plaintext access-denial line are recognized at startup); Phase 6's commitment is that the *mid-run abort path* uses that same classification. The unknown-code fallback was added after review (F10): committing to "accurate classification" without a defined behavior for an unrecognized code would leave the commitment non-falsifiable and risk a *worse* operator message than a raw code for any cmux error the classifier has not yet learned.
- **Evidence:**
  - Build-outline [Phase 6](../../build-phase-outline.md#phase-6), bullet 3: "cmux v2 errors ... and the pre-request plaintext `ERROR:` ... are classified to accurate operator guidance rather than the catch-all 'version incompatible'."
  - Parent [D-R2](../../artifacts/decision-log.md#d-r2-cmux-v2-protocol-is-the-contract-of-record): the cmux v2 `{ok,result,error}` envelope with string error codes, and the plaintext `ERROR:` line, are the contract of record.
  - Code survey: pr9k's cmux control client already models structured cmux errors and the plaintext access-denial line, and the startup preflight already classifies auth and missing-method codes — Phase 6 extends that classification to the mid-run abort diagnostic; the mechanism is discoverable from the existing control-client code.
- **Rejected alternatives:**
  - **Use the generic "version incompatible" message for every mid-run cmux failure** — rejected; misdirects the operator's remediation.
  - **Surface the raw cmux error envelope verbatim with no classification for recognized codes** — rejected; the raw code/message is in the log for forensics, but the operator-facing diagnostic should be the actionable interpretation for codes the classifier knows.
  - **Leave the unrecognized-code case unspecified** — rejected (F10); a non-falsifiable classification commitment, and an undefined behavior for the most likely real-world surprise (a cmux error code the classifier predates).
- **Linked technical notes:** —
- **Driven by findings:** F10
- **Dependent decisions:** —
- **Referenced in spec:** Primary Flow, Alternate Flows and States, Edge Cases and Failure Modes, User Interactions

## Trivial decisions

- **D6:** Abort-path cmux calls treat every failure as non-fatal. The run-aborted notification call and the sidebar-clear calls made *during* the abort sequence cannot themselves trigger a second abort — every failure of them, including a timeout, is logged to the per-run log file and shutdown continues. A partial sidebar clear (one entry cleared, one not) is an acceptable degraded state under this rule. Direct reuse of [Phase 5 D10](../../phase-5-lifecycle-notifications/artifacts/decision-log.md#d10-abort-path-notification-calls-treat-every-failure-including-timeout-as-non-fatal-explicit-exception-to-parent-d15), generalized from the notification call to every abort-path call. Driven by findings: F11 (partial-clear edge case). — Referenced in spec: Primary Flow, Edge Cases and Failure Modes, Coordinations.
- **D7:** The operator's cmux close-pane gesture on a pr9k pane is treated identically to a display pane process dying — the run aborts via the clean-abort sequence. The constraint "closing a pr9k pane closes the run" is stated in the in-run help modal and the cmux mode setup how-to. Inherited unchanged from [parent D24](../../artifacts/decision-log.md#d24-operator-pane-close-is-treated-as-display-loss). — Referenced in spec: Alternate Flows and States, Edge Cases and Failure Modes, User Interactions.
- **D8:** A cmux per-call timeout outside the abort path is fatal and triggers the clean-abort sequence; the timeout value is the shipped fixed value in the 5–10 second range, not operator-configurable in this release. Inherited unchanged from [parent D15](../../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal) and [parent D27](../../artifacts/decision-log.md#d27-cmux-per-call-timeout-value); reaffirmed per the build-outline Phase 6 precondition and not re-litigated. — Referenced in spec: Alternate Flows and States, Edge Cases and Failure Modes, Coordinations.
- **D9:** The run-aborted notification fires exactly once per aborted run, regardless of how many failure conditions are observed. Exactly-once is guaranteed by the single one-way abort-state transition in [D1](#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence): the first detection to transition wins and is named in the diagnostic; later detections are absorbed. The run-completed state is recorded the moment the workflow finishes — before any terminal notification or outcome broadcast — so a failure observed in the post-run window is measured against an already-completed run and does not trigger a spurious run-aborted notification. Sequenced from [Phase 5 D1](../../phase-5-lifecycle-notifications/artifacts/decision-log.md#d1-three-notification-classes-and-their-targeting). Driven by findings: F3, F7. — Referenced in spec: Outcome, Primary Flow, Alternate Flows and States, Edge Cases and Failure Modes.
- **D10:** The orchestrator finishes any cmux API call already in flight before running the abort sequence, so cmux is left in a consistent state. The wait is bounded by that call's existing per-call timeout — it is not extended. The in-flight call's result (success, error, or its own timeout) only signals "the call is done, proceed"; a timeout of that call after a failure has already been detected is not a second fatal trigger and does not change the named diagnostic cause. Inherited from the parent spec's "display pane dies while the orchestrator is still running" edge-case row; the bound and the timeout-during-wait clarification were added after review (F5). Driven by findings: F5. — Referenced in spec: Outcome, Primary Flow, Edge Cases and Failure Modes, Coordinations.
- **D11:** No display respawn and no recovery flow — a lost display pane is not respawned, a stalled channel is not re-established; the run aborts. Inherited from [parent D10](../../artifacts/decision-log.md#d10-display-pane-loss-aborts-the-run)'s rejected alternatives (state replay across the channel is non-trivial with no demonstrated need). — Referenced in spec: Primary Flow, Out of Scope, Coordinations.
- **D12:** The orchestrator's diagnostic surface on its own death is the launching terminal and the per-run log file. Under Architecture A the orchestrator runs in the operator's launching terminal, so its stderr and final error land there; the full output is preserved on disk under `<projectDir>/.pr9k/logs/<stamp>/`. A force-kill may truncate that file short of the kill moment, and a truncated file carries no completion marker, so it cannot always be distinguished from a log that ended for another reason — a documented limitation of the force-kill path. Derived from [parent D-R1](../../artifacts/decision-log.md#d-r1-orchestrator-is-the-in-pane-pr9k-process-no-hidden-orchestrator-pane-supersedes-d13d-3d-4-hidden-pane-parts) and [parent D17](../../artifacts/decision-log.md#d17-log-file-artifacts-are-unchanged-in-cmux-mode); the truncation-indistinguishability note was added after review (F12). Driven by findings: F12. — Referenced in spec: Outcome, Alternate Flows and States, Edge Cases and Failure Modes, User Interactions.
- **D13:** On the clean-abort path the orchestrator broadcasts the aborted outcome to the three display panes over the interaction channel, so each pane renders its final state and exits promptly rather than lingering until its own 45-second stall threshold fires. Without the broadcast, a clean abort would leave the panes alive for up to 45 seconds — contradicting [D2](#d2-the-interaction-channel-stall-threshold-is-45-seconds)'s "clean disconnect is prompt" intent. The existing cmux orchestration code already broadcasts a workspace-done signal with an exit code on the graceful path; Phase 6 routes the abort path through the same broadcast. Added after review (F6). Driven by findings: F6. — Referenced in spec: Outcome, Primary Flow, Edge Cases and Failure Modes, Coordinations.
- **D14:** Pre-run failures — a workspace or pane that cannot be created, the readiness handshake timing out — are out of Phase 6 scope; they are handled by Phase 1's lifecycle teardown, which tears down anything already created in cmux and exits non-zero without firing a run-aborted notification (no run had started). Relatedly, the workspace-close call is not part of the abort sequence: the abort leaves the workspace open per [parent D14](../../artifacts/decision-log.md#d14-workspace-closure-is-operator-initiated), and the close call runs only in the post-dismissal teardown after the operator dismisses the workspace; if that close call fails, the workspace is left as an orphan. Derived from the parent spec's "cmux's API rejects a request mid-flow" edge-case row and [parent D14](../../artifacts/decision-log.md#d14-workspace-closure-is-operator-initiated) / [parent D22](../../artifacts/decision-log.md#d22-prior-workspace-is-captured-and-restored). Added after review (F2). Driven by findings: F2. — Referenced in spec: Actors and Triggers, Primary Flow, Edge Cases and Failure Modes, Out of Scope.
- **D15:** The abort terminates the running workflow step's subprocess through pr9k's existing subprocess-termination path; the target repository is left in whatever state the terminated step had reached (in-progress git operations, Docker state, partial file writes are not rolled back). This is identical to a standard-display abort — cmux mode changes only the presentation surface, not the workflow's interaction with the target repository ([parent D1](../../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow)). Added after review (F8). Driven by findings: F8. — Referenced in spec: Outcome, Primary Flow, Coordinations, Out of Scope.
