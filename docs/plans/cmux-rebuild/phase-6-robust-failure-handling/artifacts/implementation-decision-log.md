## Full decisions

### D-1: The abort gate is a `sync.Once`-guarded one-way transition with the failure cause captured in the `Do` closure

- **Question:** spec [D1](../feature-specification.md#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence) commits a "single one-way transition into an aborting state" checked by every failure-detection path — the cmux-call-timeout path, the channel-stall path (on per-connection goroutines), the display-loss path (on per-connection goroutines), and the mid-run cmux-error path. What concrete primitive realizes that gate so every path checks it race-free under `-race`, and how is the winning detection's cause carried to the diagnostic?
- **Decision:** the abort gate is a `sync.Once` owned by the cmux orchestration layer (a small `abortGate` struct in `src/cmd/pr9k/`). Each failure-detection path calls `gate.trigger(cause)`; the first caller's `cause` is captured into a field **inside the `Do` closure**, so exactly one cause is recorded and it is the cause of the first detection to win the transition. Later callers run `Do` as a no-op and observe the gate already tripped — their failure is absorbed without effect, satisfying spec D1's "first detection wins, later detections absorbed." An exported `IsAborting() bool` accessor (reading a `sync/atomic` flag set inside the `Do` closure) lets tests and the abort-routing code observe the gate state without re-triggering it. The post-run-window race (spec [D9](../feature-specification.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)) is closed by a separate `atomic.Bool runCompleted` flag — see [D-2](#d-2-a-runcompleted-atomicbool-closes-the-post-run-window-race).
- **Rationale:** `sync.Once` is the standard-library primitive whose entire contract is "this runs at most once, and concurrent callers block until the first completes." Capturing the cause inside the `Do` closure makes "the first detection's cause is the one named in the diagnostic" a structural property, not a discipline the callers must maintain — there is no window where a second cause can overwrite the first. The failure-detection paths run on heterogeneous goroutines (the orchestrator's single `Run()` goroutine for cmux-call timeouts; per-connection `readLoop` goroutines for channel stall and display loss), exactly the multi-goroutine convergence `docs/coding-standards/concurrency.md`'s "mutually exclusive state flags: first-flag-wins" pattern is written for. An atomic-CAS-plus-manual-state alternative would re-implement what `sync.Once` already guarantees and would leave the cause-capture race for the implementer to get right. `IsAborting()` is the test-observability seam `test-engineer` F-C asked for.
- **Evidence:** CL-1 (Evidenced) — `concurrency-analyst` C1, C6; `test-engineer` F-C; `junior-developer` P6-002, P6-009. `docs/coding-standards/concurrency.md` "Mutually exclusive state flags: first-flag-wins". Spec [D1](../feature-specification.md#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence) (single one-way transition), spec [D9](../feature-specification.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run) (exactly-once). Go 1.26.2 `sync.Once` / `sync/atomic`. Discovery notes gap 3 (the team must pin the concrete primitive).
- **Rejected alternatives:**
  - **Atomic compare-and-swap on an `int32` state word plus a separately-assigned cause field** — rejected; the cause assignment is not covered by the CAS, leaving a race where a second detection could write its cause between the winner's CAS and the winner's cause write. `sync.Once`'s closure captures both atomically.
  - **A `chan struct{}` closed by the first detection** — rejected; closing a channel is a one-way signal but carries no payload, so the cause would still need a separate race-prone field; `sync.Once` carries the cause in the closure and gives the same one-way semantics.
  - **A `sync.Mutex`-guarded `aborting bool` + `cause string`** — rejected; correct but heavier — every detection path would lock, check, and conditionally write; `sync.Once` expresses "exactly once" directly and the `Do` body runs lock-free for all callers after the first.
- **Specialist owner:** `concurrency-analyst`.
- **Revisit criterion:** reopen if Phase 7+ introduces a failure-detection path that must run *concurrently with* the abort sequence (rather than being absorbed by it) — at that point the gate would need a richer state machine than `sync.Once`'s binary tripped/not-tripped.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-2, D-3, D-4, D-5
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, Runtime Behavior — Abort detection and routing), Decomposition and Sequencing (W2, W3), Testing Strategy, RAID Log (Risks R1)

### D-2: A `runCompleted` `atomic.Bool` closes the post-run-window race

- **Question:** spec [D9](../feature-specification.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)'s edge cases require that a display-pane death observed *after* the workflow has finished but *before* the terminal outcome is broadcast must **not** fire a spurious run-aborted notification. The abort gate ([D-1](#d-1-the-abort-gate-is-a-synconce-guarded-one-way-transition-with-the-failure-cause-captured-in-the-do-closure)) by itself would still let a post-run pane loss trip the gate. What prevents that?
- **Decision:** a separate `atomic.Bool runCompleted` flag is set the moment `workflow.Run()` returns — *before* any terminal notification fires and before the `WorkspaceDone` broadcast. Every failure-detection path checks `runCompleted` before calling `gate.trigger(cause)`: if the run has already completed, the detection is dropped. The flag is an `atomic.Bool` (not part of the `sync.Once` gate) because it is written by the orchestrator's `Run()` goroutine and read by the per-connection detection goroutines, and it must be set-and-visible independently of whether the abort gate ever trips.
- **Rationale:** the abort gate answers "has an abort started?"; it does not answer "is there still a run to abort?". A pane that dies in the post-run window is a real event the detection goroutine observes, and without the `runCompleted` check it would win the gate transition and fire `FireRunAborted` on top of an already-fired completion notification — the exact spurious-notification failure spec D9's edge-case row forbids. Setting the flag before the terminal notification (rather than after) is the sequencing commitment spec D9 names: the post-run window must be closed at the instant `Run()` returns, not at the instant the notification finishes. `atomic.Bool` is the minimal correct primitive for a single-writer, multi-reader boolean per `docs/coding-standards/concurrency.md`.
- **Evidence:** CL-1 (Evidenced) — `concurrency-analyst` C6; `junior-developer` P6-009. Spec [D9](../feature-specification.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run) (run-completed state recorded the moment the workflow finishes, before any terminal notification or broadcast). `docs/coding-standards/concurrency.md` (mutex-protected / atomic writes for shared state). Spec edge-case rows: "display pane dies in the brief window after the workflow has finished" and "display pane's stall timer fires at the same moment the run completes".
- **Rejected alternatives:**
  - **Fold the post-run guard into the `sync.Once` abort gate** — rejected; the gate's job is "abort starts once," a one-way latch; the run-completed state is an orthogonal fact that must be observable even when no abort ever occurs. Overloading the gate would conflate two independent conditions.
  - **Have the detection goroutines check `RunResult` after `Run()` returns** — rejected; `RunResult` is produced on the orchestrator goroutine and is not published to the detection goroutines on a defined happens-before edge; an explicit `atomic.Bool` set at the return site is the defined edge.
  - **Accept the cosmetic spurious notification** — rejected; spec D9 explicitly forbids a second run-aborted notification, and the post-run window is wide enough (notification + broadcast latency) to be hit in practice.
- **Specialist owner:** `concurrency-analyst`.
- **Revisit criterion:** reopen if a future phase makes the post-run teardown itself long-running or interruptible such that "completed" is no longer a single instant — at that point a richer run-state enum may be needed.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-4
- **Referenced in plan:** Outcome, Implementation Approach (Runtime Behavior — Abort detection and routing), Decomposition and Sequencing (W4), Testing Strategy, RAID Log (Risks R2)

### D-3: The liveness emitter is a 10-second-cadence goroutine started after `AwaitReady`; the per-connection stall timer lives in `readLoop`

- **Question:** spec [D2](../feature-specification.md#d2-the-interaction-channel-stall-threshold-is-45-seconds) commits a 45-second stall threshold and spec [D3](../feature-specification.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one) commits an orchestrator-emitted content-independent liveness signal on a sub-threshold cadence in every workflow phase. `internal/interactionchannel` has no heartbeat and no stall threshold today. Where does the liveness emitter goroutine live, what is its cadence, where does the stall timer live, and how does the emitter satisfy spec D3's "running before the stall timer counts" ordering?
- **Decision:** two coordinated mechanisms.
  1. **Liveness emitter** — a goroutine started in `runCmuxOrchestratorWith` *after* `ch.AwaitReady` returns and *before* `runCmuxWorkflowAdapted` is called. It ticks on a fixed exported constant `LivenessCadence = 10 * time.Second` and broadcasts a `Liveness{}` message ([D-6](#d-6-liveness-is-a-new-zero-field-message-type-with-wire-constant-liveness)) to every connected pane on each tick. It is scoped to a `context.WithCancel`-derived context and joined on a `WaitGroup` at orchestrator shutdown, following the existing `cmux_workflow.go` ctx/cancel/wg precedent. Because the emitter starts before the workflow runs and before any stall timer begins counting, spec D3's ordering requirement is satisfied structurally.
  2. **Stall timer** — a `time.Timer` per connection, living inside that connection's `readLoop` goroutine on **both** sides (orchestrator and display pane). It is created with the threshold, and on every received message — `Liveness{}`, `StateHeader/Log/Footer`, `WorkspaceDone`, `Ready`, `Intent`, `DoneAck` — it is reset with the Stop-drain-Reset idiom. The threshold and an `onStall` callback are injected (constructor parameter, defaulting to the exported `StallThreshold = 45 * time.Second`) so tests run with a short threshold; production always uses the fixed constant ([D-12](#d-12) note on test injectability vs. operator configuration).
- **Rationale:** the orchestrator is the only process with authoritative run state (spec D3 rationale; parent T4), so it must be the emitter — the panes are renderers. Starting the emitter after `AwaitReady` and before the workflow run is the single point where every connection exists and no workflow output has yet flowed; it makes "liveness running before the stall timer counts" a placement fact rather than a runtime check. A 10-second cadence sits comfortably below 45 seconds: even two consecutive missed ticks (20s) plus jitter stay well inside the threshold, and the emitter keeps ticking through `Terminate()`'s ≤13-second SIGTERM/SIGKILL grace window so a terminating step never produces a false stall (CL-3 resolution). The stall timer belongs in `readLoop` because that is the one goroutine per connection that already observes every inbound message — resetting the timer there means "any message keeps the channel healthy" (spec D3) is enforced at the single chokepoint, with no extra synchronization. The Stop-drain-Reset idiom is the `time.Timer` correctness pattern for resetting a timer that may have already fired.
- **Evidence:** CL-3 (Evidenced) — `concurrency-analyst` C2; `test-engineer` F-B, T2, G2; `junior-developer` P6-001. CL-4 (Evidenced) — `concurrency-analyst` C3; `test-engineer` F-A, T1, T13, T14; `junior-developer` P6-001. Spec [D2](../feature-specification.md#d2-the-interaction-channel-stall-threshold-is-45-seconds) (45s inclusive threshold, symmetric), spec [D3](../feature-specification.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one) (orchestrator emits, content-independent, every phase, running before the timer counts). Discovery notes: `channel.go` per-connection read/write/watcher goroutine model; `channel.go:269–286` `readLoop`; `cmux_workflow.go:179–186` ctx/cancel/wg precedent; "no stall threshold, no heartbeat, no liveness mechanism of any kind" today. `docs/coding-standards/concurrency.md` (WaitGroup drain, non-blocking sends); `docs/coding-standards/testing.md` (no `time.Sleep` — injectable threshold required).
- **Rejected alternatives:**
  - **Have the display panes emit liveness** — rejected (spec D3 rejected alternative; `concurrency-analyst` C2); a pane emitting liveness proves only the pane is alive, not that the orchestrator→pane channel carries the orchestrator's traffic, and the panes hold no run state.
  - **A single stall timer at the `Channel` level rather than per-connection** — rejected; spec D2's threshold is per-channel-direction and symmetric; a connection that goes silent must be detected independently of the others, which a per-connection `readLoop` timer gives directly.
  - **Reset the stall timer from the watcher goroutine instead of `readLoop`** — rejected; the watcher does not see every inbound message; `readLoop` is the single goroutine that does, so resetting there avoids cross-goroutine signalling.
  - **An operator-configurable cadence / threshold** — rejected; spec [Deferred (YAGNI)](../feature-specification.md#deferred-yagni) already defers operator-tunable thresholds. The injected constructor parameters exist only for test determinism, not as a production knob.
- **Specialist owner:** `concurrency-analyst`.
- **Revisit criterion:** reopen if operators report false-positive aborts under busy hosts (spec D2 reopen trigger) — the cadence or threshold constant changes, not the mechanism; or if a future non-cmux display backend needs a different liveness transport.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-6
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, Runtime Behavior — Liveness and stall detection), Decomposition and Sequencing (W1, W2), Testing Strategy, RAID Log (Risks R3, Assumptions A1)

### D-4: An abort detected on a channel goroutine interrupts the synchronous `Run()` loop via `Terminate()` + `ActionQuit`, routed by a new `ExitReasonAborted`

- **Question:** `workflow.Run()` drives initialize → iteration loop → finalize purely synchronously on a single goroutine and is unaware of the interaction channel. An infrastructure abort (display loss, channel stall, cmux timeout, mid-run cmux error) is detected on a *different* goroutine — the orchestrator's cmux-call path or a per-connection `readLoop`. How does that detection interrupt the in-progress synchronous `Run()` loop and route to the `FireRunAborted` → `ClearAll` → `WorkspaceDone` abort sequence?
- **Decision:** when a failure-detection path wins the abort gate ([D-1](#d-1-the-abort-gate-is-a-synconce-guarded-one-way-transition-with-the-failure-cause-captured-in-the-do-closure)), the `Do` closure performs two actions, in order: (1) calls `runner.Terminate()`, which delivers SIGTERM→SIGKILL to the running step's subprocess and unblocks the synchronous subprocess wait inside `Run()`; (2) sends `ActionQuit` on the existing action channel `ui.Orchestrate` reads, so the loop exits its iteration sequence rather than advancing to the next step. `workflow.Run()` then returns a `RunResult` carrying a **new** `ExitReason` value, `ExitReasonAborted`, distinct from `ExitReasonUserQuit`. `runCmuxWorkflowAdapted` branches on `ExitReasonAborted` (alongside the existing `UserQuit` / `Completed` / `LoopBroken` branches) to run the abort sequence: write the classified diagnostic, `FireRunAborted`, `ClearAll`, broadcast `WorkspaceDone{Aborted: true}` ([D-5](#d-5-panes-render-a-shared-run-aborted-token-aborted-bool-on-workspacedone-carries-the-clean-abort-path)), exit non-zero.
- **Rationale:** `Run()` cannot be made channel-aware without inverting the synchronous design the workflow package is built on; the realistic interrupt is to make the thing `Run()` *is* blocked on — the step subprocess — return, then steer the loop with the signal it already understands. `Runner.Terminate()` is exactly spec [D15](../feature-specification.md#d15-the-abort-terminates-the-running-step-subprocess-target-repo-side-effects-are-left-as-reached)'s "terminate the running step's subprocess through pr9k's existing path" — it is reused as-is, not modified. The two-step `Terminate()` + `ActionQuit` mirrors the existing `keyHandler.ForceQuit()` shape, so the abort path reuses a proven interrupt sequence. A *new* `ExitReasonAborted` is required because overloading `ExitReasonUserQuit` to also mean "infrastructure abort" is a routing-correctness defect: Phase 5 maps `UserQuit → FireRunAborted` and the operator-quit and infrastructure-abort paths must remain distinguishable for the diagnostic, for exit-code reasoning, and for any future per-class handling. The new constant is additive to the `ExitReason` enum and changes no existing branch.
- **Evidence:** CL-2 (Evidenced) — `concurrency-analyst` C4; `junior-developer` P6-003. Discovery notes: `workflow/run.go` (`Run()` synchronous, single goroutine; `RunResult.ExitReason ∈ {Completed, LoopBroken, UserQuit}`); `workflow/workflow.go` `Runner.Terminate()` (SIGTERM→3s→SIGKILL); existing `keyHandler.ForceQuit()` two-step interrupt. Spec [D15](../feature-specification.md#d15-the-abort-terminates-the-running-step-subprocess-target-repo-side-effects-are-left-as-reached) (existing subprocess-termination path). Spec [D1](../feature-specification.md#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence) (converge on one abort sequence). Discovery notes gap 4 (new `ExitReason` / abort routing flagged as an open implementation question). YAGNI Step-7.5 sweep: the sentinel-only alternative was considered and rejected as a routing-correctness defect risk.
- **Rejected alternatives:**
  - **Overload `ExitReasonUserQuit` to also mean infrastructure abort (sentinel-only, no new constant)** — rejected; strictly simpler in line count, but it conflates two genuinely different outcomes — an operator who pressed `q` and an infrastructure failure the operator never saw — and Phase 6's diagnostic, exit-code reasoning, and the spec's "name the cause" commitment all need them distinct. The YAGNI simpler-version test does not save this: a smaller version that loses a required distinction is not a valid simpler version.
  - **Make `workflow.Run()` select on a channel-abort signal** — rejected; inverts the synchronous design of the workflow package and forces every step executor to become abort-aware; `Terminate()` + `ActionQuit` interrupts the loop without touching the workflow package's contract.
  - **Have the detection goroutine call `FireRunAborted` / `ClearAll` directly without going through `Run()` return** — rejected; would run the abort sequence concurrently with a still-executing `Run()` loop, racing the sidebar and notification calls; routing through `Run()`'s return point serializes the abort sequence after the loop has stopped.
- **Specialist owner:** `concurrency-analyst`.
- **Revisit criterion:** reopen if the per-failure-class exit-code taxonomy (spec [Deferred (YAGNI)](../feature-specification.md#deferred-yagni)) is un-deferred — at that point `ExitReasonAborted` may need to fan out into per-cause sub-values.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** D-5
- **Referenced in plan:** Outcome, Implementation Approach (Architecture and Integration Points, Runtime Behavior — Abort detection and routing), Decomposition and Sequencing (W3, W4), Testing Strategy, RAID Log (Risks R4)

### D-5: Panes render a shared `run aborted` token; an `Aborted bool` on `WorkspaceDone` carries the clean-abort path

- **Question:** spec [D4](../feature-specification.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome) requires each display pane to render a final line containing the token `run aborted` on lost-channel detection (the orchestrator-death path), and spec [D13](../feature-specification.md#d13-the-clean-abort-broadcasts-the-aborted-outcome-to-the-panes-for-prompt-exit) requires the clean-abort path to broadcast the aborted outcome so panes exit promptly instead of waiting out the 45-second stall threshold. The header/log/footer panes render differently and `WorkspaceDone` today carries only `ExitCode int`. How do panes render `run aborted` on *both* paths, what carries the clean-abort signal, and how is the token kept testable?
- **Decision:** three coordinated pieces.
  1. **Shared token constant** — a single exported `const RunAbortedToken = "run aborted"` (in `interactionchannel` or a shared cmux package) is the one source of the token. Every pane composes its final line to contain it; tests assert against the constant, not a literal, satisfying spec User Interactions F16.
  2. **`Aborted bool` on `WorkspaceDone`** — `WorkspaceDone` gains an `Aborted bool` field alongside the existing `ExitCode int`. On the clean-abort path the orchestrator broadcasts `WorkspaceDone{ExitCode: <non-zero>, Aborted: true}`; on the graceful path it broadcasts `Aborted: false` exactly as today. The field is additive — existing graceful-path code sets it implicitly to the zero value `false`.
  3. **Pane render + return** — `runCmuxDisplayPaneWith` and `runCmuxFooterPaneWith` select on a `stalledCh` (fed by the stall timer of [D-3](#d-3-the-liveness-emitter-is-a-10-second-cadence-goroutine-started-after-awaitready-the-per-connection-stall-timer-lives-in-readloop)) and on `WorkspaceDone`. On either a `stalledCh` fire (orchestrator-death / stalled-channel path) or a `WorkspaceDone{Aborted: true}` (clean-abort path), the pane renders its final line containing `RunAbortedToken` and **returns** — it does not block on `<-ctx.Done()`. The footer pane's machine select loop gains the same `stalledCh` arm.
- **Rationale:** the two paths must converge on the same operator-visible token (`run aborted` in each pane) but reach it differently — on orchestrator death there is no orchestrator to broadcast anything, so the pane's own stall timer is the trigger; on a clean abort the orchestrator is alive and the broadcast lets the pane exit immediately rather than lingering up to 45 seconds (spec D13's whole purpose). Reusing `WorkspaceDone` rather than inventing a second terminal message is the minimal change — the graceful path already broadcasts `WorkspaceDone` and the panes already handle it; an `Aborted bool` is one additive field. A shared exported constant for the token is required because three panes plus the test suite all reference it; a duplicated string literal would let one pane drift and silently break the spec F16 testability commitment. The panes must *return* (not park on `ctx.Done()`) so the pane processes actually exit and cmux shows their pane-exit state — a pane that renders `run aborted` but stays alive contradicts spec D4's "renders … and exits."
- **Evidence:** CL-7 (Evidenced) — `concurrency-analyst` C8, C9; `test-engineer` F-E, T7, T14, G5; `devops-engineer` F-003; `junior-developer` P6-005. Spec User Interactions F16 (final line contains the token `run aborted`), spec [D4](../feature-specification.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome) (each pane renders the line and exits), spec [D13](../feature-specification.md#d13-the-clean-abort-broadcasts-the-aborted-outcome-to-the-panes-for-prompt-exit) (broadcast for prompt exit). Discovery notes: `cmux_pane.go:264–303` `runCmuxDisplayPaneWith`; `WorkspaceDone` currently `ExitCode int` only; the graceful path already broadcasts `WorkspaceDone` with an exit code; discovery gap 6 (pane-side `run aborted` rendering). `docs/coding-standards/go-patterns.md` (typed/shared constants for serialized values).

### D-6: Liveness is a new zero-field `Liveness{}` message type with wire constant `"liveness"`

- **Question:** spec [D3](../feature-specification.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one)'s content-independent liveness signal needs a wire representation. Is it a new `Message` type, or a reuse of an existing one (e.g., an empty `StateHeader`/`StateLog`/`StateFooter`)?
- **Decision:** a new `Message` type `Liveness{}` with no fields, carrying a typed wire-type constant `"liveness"` registered in `framing.go`'s `UnmarshalMessage` dispatch. It implements the `Message` interface (`WireType() string` returning `"liveness"`, plus the unexported `sealed()` marker). The stall timer's reset logic ([D-3](#d-3-the-liveness-emitter-is-a-10-second-cadence-goroutine-started-after-awaitready-the-per-connection-stall-timer-lives-in-readloop)) treats a received `Liveness{}` identically to any content message — it resets the timer and is otherwise discarded by the pane (no render effect).
- **Rationale:** spec D3 commits the signal to be **content-independent** — it must not carry or imply workflow output. Reusing `StateHeader`/`StateLog`/`StateFooter` would violate that directly: those messages drive pane rendering, so an empty one sent every 10 seconds would either flicker the pane or force every render path to special-case "empty means liveness," coupling the heartbeat to the render layer. A zero-field dedicated type is the smallest message that says exactly "the channel is alive" and nothing else; the pane discards it after resetting the stall timer. A typed wire constant (`"liveness"`) follows `docs/coding-standards/go-patterns.md`'s typed-string-constant rule for serialized enum values, and the additive `UnmarshalMessage` case does not touch existing message dispatch.
- **Evidence:** CL-5 (Evidenced) — `concurrency-analyst` C7; `test-engineer` F-B, T11; `junior-developer` P6-008. Spec [D3](../feature-specification.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one) (content-independent signal). Discovery notes: `messages.go` (`Message` interface = `WireType() string` + `sealed()`; existing orch→pane types `StateHeader`/`StateLog`/`StateFooter`/`WorkspaceDone`); `framing.go` (`"type"` discriminator, `UnmarshalMessage` dispatch). `docs/coding-standards/go-patterns.md` (typed string constants for serialized enums).
- **Rejected alternatives:**
  - **Reuse an empty `StateHeader`/`StateLog`/`StateFooter`** — rejected; those messages drive rendering, so a periodic empty one couples the heartbeat to the render layer and risks pane flicker; spec D3's content-independence is violated.
  - **Send a raw framing-level keepalive byte below the `Message` layer** — rejected; the stall timer resets on received `Message`s in `readLoop`; a sub-`Message` keepalive would need a parallel detection path and bypass the typed-message contract `interactionchannel` is built on.
  - **A `Liveness` message carrying a sequence number or timestamp** — rejected (YAGNI); the stall timer needs only "a message arrived," not its ordinal; a payload nobody reads is a configuration-knob anti-pattern. Zero fields is the simpler version that satisfies the same evidence.
- **Specialist owner:** `concurrency-analyst`.
- **Revisit criterion:** reopen if a future phase needs round-trip latency measurement or gap detection across liveness ticks — at that point a sequence number becomes evidence-justified.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1

### D-11: Abort-diagnostic durability is a `bufio` flush before subsequent abort steps; `os.Exit()` is prohibited on the abort path

- **Question:** the classified abort diagnostic (spec [D5](../feature-specification.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic), spec [D12](../feature-specification.md#d12-the-orchestrators-diagnostic-surface-on-its-own-death-is-the-launching-terminal-and-the-per-run-log-file)) is written to the per-run log file, which is `bufio.Writer`-buffered. On an orchestrator-survivable abort the orchestrator continues running cmux calls after writing the diagnostic. What guarantees the diagnostic is durable before those subsequent steps, and how is the deferred `log.Close()` flush protected?
- **Decision:** two rules.
  1. **Flush after the diagnostic write** — the classified abort diagnostic is written via `logger.Log()` followed by an explicit `bufio` flush (the logger exposes a flush, or the diagnostic is written through `log.Writer()` directly) *before* the abort sequence proceeds to `FireRunAborted` / `ClearAll`. This ensures the diagnostic survives even if a later abort step or a subsequent crash truncates the buffered tail.
  2. **No `os.Exit()` on the abort path** — the abort path returns through the normal `cobra` `RunE` error→exit-code chain (`cmux_pane.go:127`) so the deferred `log.Close()` (`cmux_pane.go:169`) runs and flushes the buffer. `os.Exit()` is prohibited anywhere on the abort path because it skips deferred functions, including the `log.Close()` flush, and would lose the buffered diagnostic tail.
- **Rationale:** the per-run log file is the single authoritative post-mortem surface (spec D12; spec [Deferred (YAGNI)](../feature-specification.md#deferred-yagni) defers structured/JSON abort records, metrics, and dashboards — see [D-12](#d-12) note). Because the logger is `bufio`-buffered (discovery notes `logger.go`), a diagnostic written but not flushed is lost on a force-kill — exactly the truncation spec D12 documents. An explicit flush after the diagnostic write narrows that window to the single most important line. Prohibiting `os.Exit()` keeps the deferred `Close()` (which flushes) on every orchestrator-survivable exit path; the `cobra` `RunE` error-return chain already produces a non-zero exit code without `os.Exit()`. An explicit `fsync` syscall was considered and rejected as over-engineering — see [D-12](#d-12) YAGNI note; the `bufio` flush satisfies the same durability evidence for the orchestrator-survivable path.
- **Evidence:** CL-9 (Evidenced) — `devops-engineer` F-001, F-002, F-004. Discovery notes: `logger.go:49,95,116` (`bufio.Writer` buffering); `cmux_pane.go:169` (deferred `Close()`); `cmux_pane.go:127` (`cobra` `RunE` error→exit-code chain). Spec [D5](../feature-specification.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic), spec [D12](../feature-specification.md#d12-the-orchestrators-diagnostic-surface-on-its-own-death-is-the-launching-terminal-and-the-per-run-log-file). `docs/coding-standards/error-handling.md` (package-prefixed messages, file paths in I/O errors).
- **Rejected alternatives:**
  - **An explicit `fsync`/`sync()` syscall on the abort-path log write** — rejected (YAGNI simpler-version test); speculative hardening against OS page-cache loss with no demonstrated incidence. A `bufio.Flush()` satisfies the same evidence — diagnostic durability on the orchestrator-survivable path. Recorded in [Deferred (YAGNI)](../feature-implementation-plan.md#deferred-yagni).
  - **`os.Exit(non-zero)` directly from the abort path for a fast exit** — rejected; skips the deferred `log.Close()` flush and loses the buffered diagnostic tail — the opposite of the durability goal.
  - **Rely only on the deferred `log.Close()` flush, no explicit flush after the diagnostic** — rejected; a crash between the diagnostic write and the deferred `Close()` would lose the diagnostic; the explicit flush narrows the loss window to nearly zero for the one line that matters most.
- **Specialist owner:** `devops-engineer`.
- **Revisit criterion:** reopen if a maintainer debugging a real abort reports the flushed diagnostic was still lost (page-cache loss on host crash) — at that point an `fsync` becomes evidence-justified.
- **Dissent (if any):** None recorded.
- **Driven by rounds:** R1
- **Dependent decisions:** —
- **Referenced in plan:** Implementation Approach (Runtime Behavior — Abort path, Diagnostics), Decomposition and Sequencing (W4, W5), Operational Readiness, Definition of Done, Deferred (YAGNI)
