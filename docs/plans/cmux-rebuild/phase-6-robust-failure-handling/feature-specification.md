# Feature Specification: Phase 6 — Robust Failure Handling

Phase 6 of the [pr9k cmux mode build outline](../build-phase-outline.md). The multi-process cmux architecture has more ways to fail than the single-process standard display: a display pane can die, the in-pane orchestrator process can die, the channel between them can stall, a cmux API call can hang, and the operator can close a pr9k pane with cmux's own close-pane gesture. Phase 6 makes every one of those failure modes produce a predictable, clean outcome instead of a confusing partial state — the run aborts, a "run aborted" notification fires when the orchestrator survives to fire it, the workspace ends in an inspectable aborted state, sidebar entries are cleared, and the workspace stays open so the operator can inspect what happened.

This phase hardens the working core that Phases 1–5 built. It introduces no new operator-facing feature — it makes the features already shipped survive the failure cases the multi-process design exposes.

Builds on:

- [Phase 2 — First Real Workflow Runs End-to-End in Cmux](../phase-2-real-workflow-runs/feature-specification.md): the running workflow, the three display panes, and the local interaction channel that this phase hardens against loss and stall.
- [Phase 4 — Sidebar Mirroring](../phase-4-sidebar-mirroring/feature-specification.md): the sidebar status and progress entries that the abort sequence clears as part of cleanup.
- [Phase 5 — Lifecycle Notifications](../phase-5-lifecycle-notifications/feature-specification.md): the run-aborted notification path, which this phase reuses for every failure it can recover ([Phase 5 D15](../phase-5-lifecycle-notifications/artifacts/decision-log.md#d15-failure-modes-that-bypass-orchestrator-shutdown-are-phase-6-scope) explicitly delegates these paths to Phase 6).

> **Architecture A (parent D-R1).** The orchestrator is the in-pane pr9k process the operator launched inside cmux — there is no separate hidden orchestrator pane. The only cmux-spawned processes are the three display panes (header, log, footer). This shapes every failure mode below: a failure the orchestrator process *survives* is handled by the orchestrator; the death of the orchestrator process itself is the one failure no in-process cleanup can cover ([parent D-R1](../artifacts/decision-log.md#d-r1-orchestrator-is-the-in-pane-pr9k-process-no-hidden-orchestrator-pane-supersedes-d13d-3d-4-hidden-pane-parts)).

## Outcome

Every failure mode of the cmux multi-process architecture resolves to one of two clean outcomes, determined solely by whether the orchestrator process is alive to run cleanup ([D1](artifacts/decision-log.md#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence), [D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)):

- **Orchestrator-survivable failure** — a display pane process dies, the operator closes a pr9k pane with cmux's close-pane gesture, the interaction channel stalls, or a cmux API call times out. The orchestrator detects the failure, finishes any cmux API call already in flight so cmux is left consistent ([D10](artifacts/decision-log.md#d10-the-orchestrator-finishes-any-in-flight-cmux-call-before-running-the-abort-sequence)), then runs **one** abort sequence: it terminates the running workflow step's subprocess ([D15](artifacts/decision-log.md#d15-the-abort-terminates-the-running-step-subprocess-target-repo-side-effects-are-left-as-reached)), fires the run-aborted notification exactly once ([D9](artifacts/decision-log.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)), clears the Phase 4 sidebar entries, broadcasts the aborted outcome to the display panes so they show a final state and exit promptly ([D13](artifacts/decision-log.md#d13-the-clean-abort-broadcasts-the-aborted-outcome-to-the-panes-for-prompt-exit)), and exits with a non-zero status. The workspace stays open per [parent D14](../artifacts/decision-log.md#d14-workspace-closure-is-operator-initiated); when the operator dismisses it, the prior workspace is restored per [parent D22](../artifacts/decision-log.md#d22-prior-workspace-is-captured-and-restored).

- **Orchestrator death** — the orchestrator process itself crashes or is force-killed. No in-process cleanup can run: no run-aborted notification fires, the orchestrator does not clear the sidebar entries, and the orchestrator does not broadcast an outcome ([D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)). The three display panes each detect the lost interaction channel — promptly on a clean disconnect, or within the stall threshold if the channel goes silent without disconnecting — render a "run aborted" line on their own pane, and exit. The workspace stays open as an orphan with stale sidebar entries; the operator dismisses it manually. The orchestrator's final error message is in the operator's launching terminal and in the per-run log file ([D12](artifacts/decision-log.md#d12-the-orchestrators-diagnostic-surface-on-its-own-death-is-the-launching-terminal-and-the-per-run-log-file)).

"Aborted state" is not a distinct cmux workspace property — cmux exposes no workspace-level "failed" flag. The operator-observable end state of an aborted run is the *combination* of: the run-aborted notification (on the survivable path), the cleared sidebar entries, the display panes showing their final content, and pr9k's non-zero exit status. There is no persistent cmux-side "aborted" badge; the workspace simply stays open with its panes' final content visible until the operator dismisses it.

The clean-abort sequence reuses surfaces Phases 4 and 5 already built — the run-aborted notification ([Phase 5 D1](../phase-5-lifecycle-notifications/artifacts/decision-log.md#d1-three-notification-classes-and-their-targeting)) and the sidebar-clear path ([Phase 4](../phase-4-sidebar-mirroring/feature-specification.md)). Phase 6 adds detection and convergence so that every failure path lands on the same outcome rather than each one producing its own partial state.

Phase 6 introduces no on-disk artifact and no change to the header, log, or footer panes' normal rendering. The per-run log file under `<projectDir>/.pr9k/logs/<stamp>/` is unchanged in content and location ([parent D17](../artifacts/decision-log.md#d17-log-file-artifacts-are-unchanged-in-cmux-mode)); a force-killed orchestrator may leave that file truncated short of the kill moment, but all content written before the kill is intact ([D12](artifacts/decision-log.md#d12-the-orchestrators-diagnostic-surface-on-its-own-death-is-the-launching-terminal-and-the-per-run-log-file)).

## Actors and Triggers

- **Primary actor:** the human operator running pr9k in cmux mode against a target repository — the same actor Phases 1–5 establish. The operator is mostly a *bystander* to Phase 6: the failure modes are detected and handled by pr9k, and the operator's only action is to dismiss the workspace afterward (and, for an orphaned workspace, to dismiss it manually).
- **Triggers** — the failure modes Phase 6 handles, grouped by outcome class:
  - **Orchestrator-survivable:** a display pane process exits or crashes mid-run; the operator closes a pr9k pane using cmux's own close-pane gesture; the interaction channel between orchestrator and a display pane stalls (silent past the stall threshold) or breaks; a cmux API call does not return within the per-call timeout; a cmux API call returns a structured error or a plaintext access-denial line mid-run.
  - **Orchestrator death:** the orchestrator process crashes, or is terminated by a signal it cannot run cleanup for (force-kill), or the host shuts down under it.
- **Preconditions:**
  - **A pr9k cmux run is underway.** The workspace exists, the three display panes have completed the readiness handshake and are connected, and the orchestrator is advancing the workflow — the steady state Phase 2 establishes. Failures *before* the run is underway (a workspace or pane cannot be created, the readiness handshake fails) are handled by Phase 1's lifecycle teardown and are out of Phase 6 scope ([D14](artifacts/decision-log.md#d14-pre-run-failures-are-phase-1-scope-not-phase-6)).
  - The cmux per-call timeout from [parent D15](../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal) / [parent D27](../artifacts/decision-log.md#d27-cmux-per-call-timeout-value) is in effect on every cmux API call.
  - The local interaction channel is the bidirectional path Phase 2 settled; Phase 6 adds the stall threshold and a content-independent liveness signal to it ([D3](artifacts/decision-log.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one)).

## Primary Flow

The primary flow is the **clean-abort sequence** for an orchestrator-survivable failure. It is the single path that every such failure converges on ([D1](artifacts/decision-log.md#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence)); the per-mode entry points are covered under [Alternate Flows and States](#alternate-flows-and-states).

1. The orchestrator detects a failure: a display pane has died, the operator has closed a pr9k pane, the interaction channel has stalled or broken, or a cmux API call has timed out. The orchestrator makes a **single one-way transition into an aborting state**; that transition can happen at most once per run, and it is checked by every failure-detection path. The first detection to make the transition wins — its failure is the one named in the diagnostic — and every later detection observes the aborting state and is absorbed without effect ([D1](artifacts/decision-log.md#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence), [D9](artifacts/decision-log.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)).
2. If the orchestrator has a cmux API call in flight at the moment of detection, it lets that call run to its result before proceeding, so cmux is not left mid-operation. That wait is bounded by the call's existing per-call timeout — it is not extended — and the call's result (success, error, or even its own timeout) only signals "the call is done, proceed"; a timeout of the in-flight call after a failure has already been detected is **not** a new fatal event and does not change the named diagnostic cause ([D10](artifacts/decision-log.md#d10-the-orchestrator-finishes-any-in-flight-cmux-call-before-running-the-abort-sequence)).
3. The orchestrator stops advancing the workflow and terminates the running workflow step's subprocess through pr9k's existing subprocess-termination path; the target repository is left in whatever state that step had reached, exactly as a standard-display abort would leave it ([D15](artifacts/decision-log.md#d15-the-abort-terminates-the-running-step-subprocess-target-repo-side-effects-are-left-as-reached)).
4. The diagnostic for the detected failure — naming the specific cause ([D5](artifacts/decision-log.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic)) — is written to the per-run log file under `<projectDir>/.pr9k/logs/<stamp>/` and to the orchestrator's launching terminal.
5. The orchestrator fires the **run-aborted** notification exactly once ([D9](artifacts/decision-log.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run), [Phase 5 D1](../phase-5-lifecycle-notifications/artifacts/decision-log.md#d1-three-notification-classes-and-their-targeting)). This call is an abort-path call: any failure of it — including a timeout — is logged and shutdown continues, so the abort cannot recurse ([D6](artifacts/decision-log.md#d6-abort-path-cmux-calls-treat-every-failure-as-non-fatal), [Phase 5 D10](../phase-5-lifecycle-notifications/artifacts/decision-log.md#d10-abort-path-notification-calls-treat-every-failure-including-timeout-as-non-fatal-explicit-exception-to-parent-d15)).
6. The orchestrator clears the Phase 4 sidebar entries (the step-name status entry and the iteration progress entry). These are also abort-path calls and are treated the same way: failure is logged, shutdown continues ([D6](artifacts/decision-log.md#d6-abort-path-cmux-calls-treat-every-failure-as-non-fatal)).
7. The orchestrator broadcasts the aborted outcome to the three display panes over the interaction channel, so each pane renders its final state and exits promptly rather than waiting out the stall threshold ([D13](artifacts/decision-log.md#d13-the-clean-abort-broadcasts-the-aborted-outcome-to-the-panes-for-prompt-exit)). It does **not** respawn the lost display, re-establish a stalled channel, or otherwise attempt recovery ([D11](artifacts/decision-log.md#d11-no-display-respawn-and-no-recovery-flow)).
8. The orchestrator exits with a non-zero status. The workspace stays open ([parent D14](../artifacts/decision-log.md#d14-workspace-closure-is-operator-initiated)). The operator inspects the final pane state and the per-run log file, then dismisses the workspace; on dismissal the prior workspace is restored to focus ([parent D22](../artifacts/decision-log.md#d22-prior-workspace-is-captured-and-restored)). If the workspace-close call that runs as part of that post-dismissal teardown fails, the workspace is left as an orphan for the operator to dismiss through cmux's own controls ([D14](artifacts/decision-log.md#d14-pre-run-failures-are-phase-1-scope-not-phase-6)).

## Alternate Flows and States

### A display pane process dies mid-run

- **Entry condition:** the header, log, or footer pane's process exits or crashes while the orchestrator is still running.
- **Sequence:** the orchestrator detects the loss — promptly on a clean process exit (the interaction channel disconnects and the loss is detected within the channel's normal read cycle, far below the stall threshold), or within the stall threshold if the pane stops responding without disconnecting ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds)). It then runs the [Primary Flow](#primary-flow) clean-abort sequence. The loss is treated as fatal regardless of which of the three panes died — Phase 6 does not distinguish "footer died" from "log died"; any display loss aborts the run ([parent D10](../artifacts/decision-log.md#d10-display-pane-loss-aborts-the-run)).
- **Exit:** workspace stays open; operator dismisses it.

### Operator closes a pr9k pane with cmux's close-pane gesture

- **Entry condition:** the operator uses cmux's own close-pane control on the header, log, or footer pane.
- **Sequence:** identical to a display pane process dying — the close removes the pane's process, the orchestrator detects the loss, and the clean-abort sequence runs ([D7](artifacts/decision-log.md#d7-operator-pane-close-is-treated-identically-to-display-pane-loss), [parent D24](../artifacts/decision-log.md#d24-operator-pane-close-is-treated-as-display-loss)). pr9k does not distinguish an accidental close from a process crash and does not prompt for confirmation — cmux exposes no hook that would let pr9k intercept the gesture.
- **Operator-facing disclosure:** because this is a foot-gun for operators with tmux/iTerm pane-close muscle memory, the constraint "closing a pr9k pane closes the run" is stated explicitly in the in-run help modal and in the cmux mode setup how-to ([D7](artifacts/decision-log.md#d7-operator-pane-close-is-treated-identically-to-display-pane-loss)).
- **Exit:** workspace stays open; operator dismisses it.

### The interaction channel stalls

- **Entry condition:** the interaction channel between the orchestrator and a display pane stops delivering messages while both processes are still alive — a saturated channel, a socket-level error that does not surface as a disconnect, or a wedged process.
- **Sequence:** the side that is waiting (the orchestrator awaiting a pane, or a pane awaiting the orchestrator) treats the channel as lost once it has gone **45 seconds or more** without an expected message ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds)). A channel that is merely *quiet* — a long-running step producing no output, or a run paused at an error-mode prompt — does **not** trip the threshold: the orchestrator emits a content-independent liveness signal to every display pane on a fixed cadence well below 45 seconds, in *every* workflow phase including a paused error-mode prompt, so an idle-but-healthy channel is never mistaken for a stalled one ([D3](artifacts/decision-log.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one)). When the orchestrator is the detecting side, it runs the clean-abort sequence. When a display pane is the detecting side, it follows the orchestrator-death flow below (a stalled channel is, from the pane's vantage point, indistinguishable from a dead orchestrator).
- **Exit:** workspace stays open; operator dismisses it.

### A cmux API call times out

- **Entry condition:** a cmux API call neither succeeds nor fails within the per-call timeout — the socket is alive but cmux is hung.
- **Sequence:** the timeout is fatal per [parent D15](../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal); it triggers the clean-abort sequence ([D8](artifacts/decision-log.md#d8-cmux-per-call-timeout-is-fatal-and-uses-the-shipped-fixed-value)). The one exception is a cmux call made *during* the abort sequence itself (the run-aborted notification, the sidebar clears): a timeout there is non-fatal so the abort cannot recurse ([D6](artifacts/decision-log.md#d6-abort-path-cmux-calls-treat-every-failure-as-non-fatal)).
- **Exit:** workspace state is whatever cmux preserved at the moment it became unresponsive; operator dismisses it. The per-call timeout value is the shipped fixed value in the 5–10 second range, not operator-configurable in this release ([parent D27](../artifacts/decision-log.md#d27-cmux-per-call-timeout-value), [D8](artifacts/decision-log.md#d8-cmux-per-call-timeout-is-fatal-and-uses-the-shipped-fixed-value)).

### A cmux API call returns a structured or plaintext error mid-run

- **Entry condition:** a cmux API call returns a structured cmux v2 error envelope, or cmux emits a plaintext access-denial line, after the run is already underway — for example, the socket's access mode changed under the run, or a method became unavailable.
- **Sequence:** the orchestrator classifies the error to a specific, actionable diagnostic — access denied, a named missing method, an authentication failure — rather than the generic "version incompatible" catch-all the *startup* capability check uses for a different condition ([D5](artifacts/decision-log.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic), [parent D-R2](../artifacts/decision-log.md#d-r2-cmux-v2-protocol-is-the-contract-of-record)). An error code that does not match any recognized class is reported as an unclassified cmux error with the raw code preserved in the diagnostic. A mid-run error that prevents the orchestrator from continuing triggers the clean-abort sequence; the abort diagnostic names the classified cause. This is an instance of the general classification rule in [D5](artifacts/decision-log.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic), not a separate behavior.
- **Exit:** workspace stays open; operator reads the classified diagnostic in the launching terminal and the per-run log file, then dismisses the workspace.

### The orchestrator process dies (crash or force-kill)

- **Entry condition:** the orchestrator process crashes, is terminated by a signal it cannot run cleanup for, or the host shuts down under it.
- **Sequence:** no in-process cleanup runs — no run-aborted notification, no sidebar clear, no aborted-outcome broadcast ([D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)). Each of the three display panes detects the lost interaction channel: promptly if the orchestrator's death cleanly disconnects the channel, or within the **45-second** stall threshold if the channel goes silent without a clean disconnect ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds)). Each surviving pane independently renders a final line containing "run aborted" on its own pane and exits — the operator sees the same line in each of the three panes, rendered without coordination between them. The workspace stays open ([parent T5](../artifacts/feature-technical-notes.md#t5-cmux-workspace-persists-after-pane-exit)) as an orphan: its sidebar entries remain stale because the actor that clears them is dead, and the prior workspace is **not** restored automatically.
- **Diagnostic surface:** the orchestrator runs in the operator's launching terminal (Architecture A — [parent D-R1](../artifacts/decision-log.md#d-r1-orchestrator-is-the-in-pane-pr9k-process-no-hidden-orchestrator-pane-supersedes-d13d-3d-4-hidden-pane-parts)), so its stderr and final error message land in that terminal's scrollback. The per-run log file under `<projectDir>/.pr9k/logs/<stamp>/` holds the full orchestrator output; a force-kill may truncate it short of the kill moment, but content written before the kill is intact ([D12](artifacts/decision-log.md#d12-the-orchestrators-diagnostic-surface-on-its-own-death-is-the-launching-terminal-and-the-per-run-log-file)).
- **Exit:** the operator dismisses the orphan workspace manually. The orphan is recognizable by its `pr9k-` workspace title prefix and is the input to [Phase 7](../build-phase-outline.md#phase-7)'s startup advisory.

### The orchestrator dies partway through its own abort sequence

- **Entry condition:** the orchestrator detects an orchestrator-survivable failure and begins the clean-abort sequence, then itself crashes or is force-killed before the sequence completes.
- **Sequence:** the abort sequence is not transactional — the operator observes whatever steps completed before the orchestrator died. They may, for example, see the run-aborted notification (if it fired) but a stale sidebar entry (if the clear had not yet run). This partial-abort outcome is acknowledged, not prevented: from the operator's standpoint it is handled identically to the orchestrator-death flow above — the workspace is an orphan to dismiss manually, the launching terminal and the per-run log file hold the diagnostic ([D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)).
- **Exit:** operator dismisses the orphan workspace manually.

### Multiple failure modes are detected near-simultaneously

- **Entry condition:** more than one failure condition is observable in the same short window — for example, a cmux call times out *and* a display pane has died, or a channel stall is followed by a display disconnect.
- **Sequence:** the single one-way transition into the aborting state ([Primary Flow](#primary-flow) step 1) guarantees exactly one abort sequence runs and the run-aborted notification fires exactly once ([D9](artifacts/decision-log.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)). The detection that wins the transition is the one named in the diagnostic; subsequent detections are absorbed without effect. The operator never sees two run-aborted notifications for one run.
- **Exit:** workspace stays open; operator dismisses it.

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| A display pane process exits cleanly mid-run. | The interaction channel disconnects; the orchestrator detects the loss within the channel's normal read cycle — promptly, far below the stall threshold — and runs the clean-abort sequence ([D1](artifacts/decision-log.md#d1-orchestrator-survivable-failures-converge-on-one-clean-abort-sequence), [parent D10](../artifacts/decision-log.md#d10-display-pane-loss-aborts-the-run)). |
| A display pane process wedges without exiting (alive but unresponsive). | The orchestrator detects the stall once the channel to that pane has been silent for 45 seconds or more, then runs the clean-abort sequence ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds)). |
| A workflow step runs for several minutes producing no output. | The orchestrator's liveness signal keeps the channel from being declared stalled; no false abort fires ([D3](artifacts/decision-log.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one)). |
| The run is paused at an error-mode prompt (Phase 3) for longer than 45 seconds. | The liveness signal continues during the error-mode pause, so the paused-but-healthy run is never mistaken for a stalled channel; no abort fires and the error-mode prompt survives ([D3](artifacts/decision-log.md#d3-a-healthy-but-quiet-channel-is-never-mistaken-for-a-stalled-one)). |
| The operator closes a pr9k pane with cmux's close-pane gesture. | Treated identically to a display pane process dying — the run aborts via the clean-abort sequence. Documented in the help modal and the setup how-to ([D7](artifacts/decision-log.md#d7-operator-pane-close-is-treated-identically-to-display-pane-loss), [parent D24](../artifacts/decision-log.md#d24-operator-pane-close-is-treated-as-display-loss)). |
| A cmux API call does not return within the per-call timeout. | The timeout is fatal and triggers the clean-abort sequence ([D8](artifacts/decision-log.md#d8-cmux-per-call-timeout-is-fatal-and-uses-the-shipped-fixed-value), [parent D15](../artifacts/decision-log.md#d15-cmux-api-per-call-timeout-is-fatal)). |
| The orchestrator has a cmux call in flight when a failure is detected, and that in-flight call then times out. | The orchestrator waits for the in-flight call to resolve (bounded by its own per-call timeout); the timeout signals "the call is done, proceed" — it is not a second fatal trigger and does not change the diagnostic cause, which remains the first detected failure ([D10](artifacts/decision-log.md#d10-the-orchestrator-finishes-any-in-flight-cmux-call-before-running-the-abort-sequence)). |
| A cmux call made *during* the abort sequence (run-aborted notification, sidebar clear) fails or times out. | Treated as non-fatal: logged to the per-run log file, shutdown continues. The abort cannot recurse ([D6](artifacts/decision-log.md#d6-abort-path-cmux-calls-treat-every-failure-as-non-fatal)). |
| One sidebar-clear call succeeds and the other fails during the abort. | Acceptable degraded state per [D6](artifacts/decision-log.md#d6-abort-path-cmux-calls-treat-every-failure-as-non-fatal): the failure is logged, shutdown continues, and the operator may see one stale sidebar entry after the abort. The per-run log file is the authoritative record that the run aborted. |
| A cmux call returns a structured cmux v2 error or a plaintext access-denial line mid-run. | The orchestrator classifies it to a specific diagnostic (access denied, named missing method, auth failure); if it prevents continuing, the clean-abort sequence runs with the classified cause in the diagnostic ([D5](artifacts/decision-log.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic)). |
| A cmux call returns an error code that matches no recognized class. | Reported as an unclassified cmux error, with the raw cmux error code preserved verbatim in the diagnostic and the per-run log file; the clean-abort sequence runs ([D5](artifacts/decision-log.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic)). |
| The interaction channel stalls while the orchestrator is the waiting side. | The orchestrator declares the channel lost after 45 seconds or more of silence and runs the clean-abort sequence ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds)). |
| The interaction channel stalls while a display pane is the waiting side. | The pane declares the channel lost after 45 seconds or more of silence, renders a "run aborted" line, and exits — the orchestrator-death flow, because a stalled channel is indistinguishable from a dead orchestrator from the pane's side ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds), [D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)). |
| The orchestrator process crashes mid-run. | No cleanup runs. Each display pane detects the lost channel, renders a "run aborted" line, and exits. The workspace stays open as an orphan with stale sidebar entries; the prior workspace is not restored ([D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)). |
| The orchestrator crashes partway through its own abort sequence. | Whatever abort steps completed before the crash are what the operator observes (a partial-abort state); from the operator's standpoint it is handled as the orchestrator-death orphan path ([D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)). |
| The orchestrator is force-killed (a signal that bypasses cleanup). | Same as a crash. Additionally, the per-run log file may be truncated short of the kill moment; content written before the kill is intact. A truncated log carries no completion marker, so an operator cannot always distinguish a force-kill-truncated log from one that ended for another reason — a documented limitation of the force-kill path ([D12](artifacts/decision-log.md#d12-the-orchestrators-diagnostic-surface-on-its-own-death-is-the-launching-terminal-and-the-per-run-log-file)). |
| The host shuts down under a running pr9k cmux run. | Treated as orchestrator death — no cleanup, orphan workspace, panes exit when the host stops them. The orphan is recognized by [Phase 7](../build-phase-outline.md#phase-7)'s startup advisory on the next launch. |
| Two or more failure modes are detected in the same short window. | The single one-way transition into the aborting state guarantees one abort sequence runs; the run-aborted notification fires exactly once; the detection that won the transition is named in the diagnostic ([D9](artifacts/decision-log.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)). |
| A display pane dies *while the orchestrator already has a cmux call in flight*. | The orchestrator lets the in-flight call run to its result before starting the abort, so cmux is left in a consistent state ([D10](artifacts/decision-log.md#d10-the-orchestrator-finishes-any-in-flight-cmux-call-before-running-the-abort-sequence)). |
| The run-aborted notification call itself times out during the abort. | Non-fatal per [D6](artifacts/decision-log.md#d6-abort-path-cmux-calls-treat-every-failure-as-non-fatal); shutdown continues to the aborted-outcome broadcast and non-zero exit. The operator's signal that the run ended is the final pane state and the per-run log file. |
| A display pane dies in the brief window after the workflow has finished but before the run's terminal outcome has been broadcast. | No abort fires — the run-completed state is recorded the moment the workflow finishes, before any terminal notification or broadcast, so a pane loss in that window is observed against an already-completed run and does not trigger a spurious run-aborted notification ([D9](artifacts/decision-log.md#d9-the-run-aborted-notification-fires-exactly-once-per-aborted-run)). |
| A display pane's stall timer fires at the same moment the run completes, before the completion outcome reaches that pane. | An acceptable cosmetic race: the pane may render "run aborted" for a run that actually completed. The completion notification fires before the outcome broadcast, so cmux's notification surface still correctly shows completion; the workspace stays open and the per-run log file is authoritative ([D13](artifacts/decision-log.md#d13-the-clean-abort-broadcasts-the-aborted-outcome-to-the-panes-for-prompt-exit)). |
| A display pane dies *after* the run has already completed and the workspace is in its done state. | No abort fires — the run has already ended. The dead pane's slot shows cmux's pane-exit state; the operator dismisses the workspace as normal. |
| The workspace-close call fails during the post-dismissal teardown (cmux rejected it). | The orchestrator (if still alive at teardown) records the failure; the workspace is left as an orphan for the operator to dismiss through cmux's own controls, and [Phase 7](../build-phase-outline.md#phase-7)'s advisory reports it on the next launch. Workspace closure is not part of the abort sequence — the abort leaves the workspace open per [parent D14](../artifacts/decision-log.md#d14-workspace-closure-is-operator-initiated); the close call belongs to teardown after the operator dismisses ([D14](artifacts/decision-log.md#d14-pre-run-failures-are-phase-1-scope-not-phase-6)). |
| A failure occurs before the run is underway (workspace/pane creation fails, the readiness handshake times out). | Out of Phase 6 scope — handled by Phase 1's lifecycle teardown, which tears down anything already created in cmux and exits non-zero; no run-aborted notification fires because no run had started ([D14](artifacts/decision-log.md#d14-pre-run-failures-are-phase-1-scope-not-phase-6)). |

## User Interactions

Phase 6 is largely invisible to the operator by design — its job is to convert confusing partial-failure states into the clean outcomes Phases 4 and 5 already render. The operator-facing surfaces are:

- **Affordances:**
  - **Run-aborted notification (cmux notification surface):** on an orchestrator-survivable failure, the same run-aborted notification Phase 5 defines fires once ([Phase 5 D1](../phase-5-lifecycle-notifications/artifacts/decision-log.md#d1-three-notification-classes-and-their-targeting)). Phase 6 adds no new notification class and no new notification text.
  - **"Run aborted" line in a display pane:** on orchestrator death, each surviving display pane renders a final line containing "run aborted" on its own pane before exiting, so an operator looking at the workspace sees that the run ended rather than a silently frozen display ([D4](artifacts/decision-log.md#d4-orchestrator-process-death-is-the-documented-exception-to-the-clean-abort-outcome)). The exact wording and styling are pinned by the implementation plan; the spec-level commitment is that each pane's final rendered line contains the token "run aborted".
  - **Launching terminal:** the orchestrator's final error message and exit status appear in the terminal the operator ran `pr9k --cmux` from ([D12](artifacts/decision-log.md#d12-the-orchestrators-diagnostic-surface-on-its-own-death-is-the-launching-terminal-and-the-per-run-log-file)).
  - **In-run help modal and cmux setup how-to:** both state the known constraint that closing a pr9k pane closes the run ([D7](artifacts/decision-log.md#d7-operator-pane-close-is-treated-identically-to-display-pane-loss)).
- **Feedback:**
  - On an orchestrator-survivable abort: the run-aborted notification surfaces, the sidebar entries clear, each display pane shows its final state, and the workspace stays open for inspection. The sidebar shows the last live step and iteration values between the abort trigger and the sidebar clear — a brief, expected transient.
  - On orchestrator death: each display pane shows a "run aborted" line; the launching terminal shows the orchestrator's final output; the sidebar entries remain stale. An operator who was away when the orchestrator died returns to a workspace whose panes are in cmux's pane-exit state and whose sidebar still shows the last live values — the documented consequence of the cleanup actor being dead. The authoritative signal that the run ended is the "run aborted" line in each pane, the launching terminal, and the per-run log file.
- **Error states:**
  - The per-run log file under `<projectDir>/.pr9k/logs/<stamp>/` is the authoritative post-mortem surface for every failure mode and carries the classified diagnostic ([D5](artifacts/decision-log.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic), [parent D17](../artifacts/decision-log.md#d17-log-file-artifacts-are-unchanged-in-cmux-mode)).
  - pr9k always exits non-zero on any Phase 6 failure path that the orchestrator survives to set an exit code for. The exit status is "non-zero" without a per-failure-class distinction in this release — see [Deferred (YAGNI)](#deferred-yagni).

## Out of Scope

- **Respawning a lost display pane / stateful recovery.** A lost display is not respawned and a stalled channel is not re-established — the run aborts ([D11](artifacts/decision-log.md#d11-no-display-respawn-and-no-recovery-flow), [parent D10](../artifacts/decision-log.md#d10-display-pane-loss-aborts-the-run)). State replay across the interaction channel is non-trivial and no failure mode is demonstrated recoverable.
- **A confirmation prompt before the operator's pane-close gesture.** cmux exposes no hook that lets pr9k intercept the close gesture ([parent D24](../artifacts/decision-log.md#d24-operator-pane-close-is-treated-as-display-loss)); the constraint is disclosed in documentation instead.
- **Automatic cleanup of orphan workspaces.** Orphans from orchestrator death, force-kill, partial abort, or a failed teardown-close are tolerated, not cleaned up; the operator dismisses them manually and [Phase 7](../build-phase-outline.md#phase-7)'s advisory reports them ([parent D11](../artifacts/decision-log.md#d11-orphan-workspaces-from-crashes-are-not-auto-cleaned)).
- **Per-pane-role failure handling.** Phase 6 does not treat "footer pane died" differently from "log pane died" — any display loss aborts the run identically ([parent D10](../artifacts/decision-log.md#d10-display-pane-loss-aborts-the-run)).
- **Pre-run failure handling.** Failures before the run is underway — workspace/pane creation rejected, the readiness handshake timing out — are Phase 1's lifecycle-teardown responsibility, not Phase 6's ([D14](artifacts/decision-log.md#d14-pre-run-failures-are-phase-1-scope-not-phase-6)).
- **Cleaning up target-repository side-effects of an aborted run.** Git commits, branch pushes, and Docker state the workflow produced before the abort are left as they were; pr9k does not roll them back. This is unchanged from a standard-display abort ([D15](artifacts/decision-log.md#d15-the-abort-terminates-the-running-step-subprocess-target-repo-side-effects-are-left-as-reached), [parent D1](../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow)).
- **Distinguishing abort sub-reasons in the run-aborted notification text.** Already deferred at the [Phase 5 spec level](../phase-5-lifecycle-notifications/feature-specification.md#deferred-yagni); the operator reads the per-run log file for the sub-reason. Phase 6 names the cause in the *log diagnostic*, not in the notification text.
- **Notifications for the orchestrator-death path.** The orchestrator is the only actor that fires notifications; when it is dead, no notification fires. The display panes' "run aborted" line and Phase 7's advisory are the substitute signals.

## Deferred (YAGNI)

### Operator-configurable failure-detection thresholds

- **Item:** exposing the interaction-channel stall threshold ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds)) and the cmux per-call timeout ([parent D27](../artifacts/decision-log.md#d27-cmux-per-call-timeout-value)) as operator-tunable settings.
- **Why deferred:** the simpler-version test. Both values are fixed in this release. Adding a configuration surface for numbers most operators will never change adds operator-facing surface area with no evidence anyone wants it — the same YAGNI reasoning [parent D27](../artifacts/decision-log.md#d27-cmux-per-call-timeout-value) applied to the cmux timeout. The stall threshold was deliberately set into the forgiving 30–60 second band ([D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds)) precisely so the fixed value tolerates busy hosts without configuration.
- **Reopen when:** operators report false-positive aborts in normal use, or report that 45 seconds is too slow to surface a real stall in their environment — a single credible report is enough to revisit, since the fix is a value change, not a redesign.

### Per-failure-mode recovery flows

- **Item:** mode-specific recovery — respawning a dead display pane and replaying its state, re-establishing a stalled channel, or reconnecting to a hung cmux socket — instead of the uniform abort.
- **Why deferred:** the evidence test fails. No failure mode is demonstrated recoverable in practice, and recovery would introduce stateful replay logic across the interaction channel ([parent D10](../artifacts/decision-log.md#d10-display-pane-loss-aborts-the-run) rejected this for display loss). The uniform abort is the strictly simpler behavior that satisfies the same evidence: the operator gets a clean, inspectable end state and re-launches.
- **Reopen when:** a specific failure mode is shown to recur often enough and to be cleanly recoverable — for example, operators report a transient channel stall under a known load pattern that a single reconnect attempt would survive.

### A per-failure-class exit-code taxonomy

- **Item:** distinct, documented process exit codes per failure class — for example, one code for an operator-quit, another for an infrastructure abort (display loss, channel stall, cmux timeout) — so a script wrapping pr9k can branch on the exit code without parsing the log.
- **Why deferred:** the evidence test fails. pr9k's exit-code contract today is "non-zero on failure", inherited unchanged from the standard display ([parent D1](../artifacts/decision-log.md#d1-cmux-mode-is-an-alternate-presentation-not-a-new-workflow): cmux mode keeps the same exit codes). No operator or calling script has been described that needs to branch on the abort *class*. Adding a taxonomy now is speculative interface surface; the classified cause is already in the per-run log diagnostic ([D5](artifacts/decision-log.md#d5-mid-run-cmux-failures-are-classified-to-an-accurate-operator-diagnostic)).
- **Reopen when:** an operator or an automation wrapping pr9k reports needing to make a programmatic decision (retry, alert, escalate) based on *why* a cmux run aborted, and the per-run log diagnostic is too coarse a surface for that decision.

## Open Items

- **Live-cmux CI smoke test for Phase 6's timing-sensitive failure modes (test-strategy item, not a feature behavior).** [OQ-2](../build-phase-outline.md#oq-2) committed Phases 1–5 to mocked tests with a mandatory manual in-pane gate, and explicitly flagged Phase 6 to "revisit whether a live macOS-runner CI smoke test is worth adding." Phase 6's failure modes — the 45-second stall threshold, the liveness-signal guard, near-simultaneous multi-failure detection — are the most timing-sensitive in the build and the least convincing under mocked cmux. The recommended resolution, consistent with how OQ-2 was resolved for Phases 1–5, is to continue mocked tests, keep the manual in-pane gate mandatory for any change touching the cmux control client or the interaction channel, and write a manual test script that specifically exercises (a) a deliberately quiet step that must *not* false-abort, (b) a deliberate channel wedge that must abort within the stall window, and (c) a near-simultaneous pane-death + cmux-timeout that must produce exactly one run-aborted notification. Whether to add a live macOS-runner CI smoke test remains a team decision. This does not change any behavior in this spec; it is recorded here so implementation planning picks it up. Not a blocker for the spec.

## Summary

- **Outcome delivered:** every failure mode of the cmux multi-process architecture resolves to one of two clean outcomes. When the orchestrator survives the failure (display-pane death, operator pane-close, channel stall, cmux call timeout), it runs one abort sequence — finish any in-flight cmux call, terminate the running step's subprocess, fire run-aborted once, clear the sidebar, broadcast the aborted outcome to the panes, exit non-zero, leave the workspace open. When the orchestrator itself dies, the display panes detect the lost channel, render a "run aborted" line, and exit, leaving an inspectable orphan workspace whose diagnostic lives in the launching terminal and the per-run log file.
- **Actor:** the human operator running pr9k in cmux mode — mostly a bystander to Phase 6, whose only action is to dismiss the workspace afterward.
- **Decisions settled:** see [the decision log](artifacts/decision-log.md) — 15 decisions total. 5 full decisions (D1–D5) covering the clean-abort convergence and single abort-guard, the 45-second stall threshold, the healthy-but-quiet-channel liveness guard, the orchestrator-death exception including partial abort, and mid-run cmux-error classification. 10 trivial decisions (D6–D15) inherited or sequenced from parent and Phase 5 decisions.
- **YAGNI deferrals:** 3 — operator-configurable failure-detection thresholds, per-failure-mode recovery flows, and a per-failure-class exit-code taxonomy. Each carries a named reopening trigger.
- **Technical notes captured:** none — every load-bearing mechanic is either already a parent technical note (T1 cmux calls can hang silently, T4 display processes are independent, T5 cmux workspace persists after pane exit) or discoverable from the existing cmux control and interaction-channel code.
- **Reviewers consulted:** `junior-developer`, `edge-case-explorer`, `devops-engineer`, `test-engineer` — see [team-findings.md](artifacts/team-findings.md).
- **Settled by user input:** the interaction-channel stall threshold band (30–60 seconds, pinned to 45 seconds) — [D2](artifacts/decision-log.md#d2-the-interaction-channel-stall-threshold-is-45-seconds).
- **Key adjustments after review:** the liveness-signal obligation was made explicit (orchestrator emits it on a fixed sub-threshold cadence in every workflow phase, including error-mode pauses); a single one-way abort-guard was added so the run-aborted notification provably fires once; the in-flight-call wait was bounded and the timeout-during-wait race resolved; the aborted-outcome broadcast was added so panes exit promptly instead of waiting out the stall threshold; the post-run-window and pre-run-window gaps were closed; target-repository side-effects on abort were addressed via the existing subprocess-termination path; the non-observable phrase "failed state" was replaced with the concrete observable end state; a partial-abort outcome was acknowledged; an unclassified-cmux-error fallback was added; and the exit-code taxonomy was deferred under YAGNI.
